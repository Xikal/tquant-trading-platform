## 一、总体结论

### 1.1 项目成熟度：中等偏上

该项目从最初"做T工具"的原型起点，已演进为一个包含多策略低吸引擎、完整模拟盘系统、Agent 工具注册表、统一认证体系、Web/App 双端前端的生产级平台。核心策略管线（priority_board → candidate → signals → screening）已经过多次重构，具备分层枚举、因子权重、家族共振去重等相对成熟的特性。模拟盘系统（PaperAccount / Order / Position / Trade / Performance / Matching / RiskControl）已完整运行。

但项目在两个维度上严重欠账：**安全边界**（多个路由模块缺乏认证、SSE 令牌暴露在 URL、auth_secret 空默认值回退到 database_url）和**策略验证**（11 个策略缺少 PBO 样本外检验，回测置信度未知）。

### 1.2 最大优势

策略引擎的**分层设计**（核心/辅助/研究/因子四层 + 家族共振去重 + 双窗口绩效权重）思路清晰，与市场上大多数"一把梭排名"的做法有本质区别。模拟盘的**撮合引擎和风控规则**贴近 A 股真实约束（T+1、涨跌停边界、滑点分桶、佣金印花税过户费），比大多数开源量化项目更真实。

### 1.3 最大风险

按严重程度排序：

1. **安全**：`settings.py` 的 GET 端点零认证暴露 LLM 配置和运行环境信息；`auth_secret_key` 默认为空且回退到 `database_url`——任何能读到代码库的人都能伪造令牌；4 个路由模块在路由器级别无认证依赖（analysis/research/instruments/screeners/agent）。
2. **策略过拟合**：11 个策略中至少 4 个（deep_pullback、trend_rebound、divergence_consensus、limit_up_breakout_retrace）未经过严格的样本外 Walk-forward 验证。当前"绩效权重"依赖的 60+20 日回看窗口，本质上仍是样本内统计。
3. **运维脆弱**：无 Git 版本控制、无 CI/CD、无数据库自动备份、HTTP 明文传输、无结构化日志。

### 1.4 最值得继续投入的方向

模拟盘自动化交易闭环（AutoTrader → 实盘信号验证 → 样本外 PBO 检验 → 策略迭代）。这是从"研究工具"变成"交易辅助系统"的关键一步。

### 1.5 3 个最优先事项

1. 补齐全路由认证 + 修复 auth_secret_key 回退链（安全底线）
2. `git init` + CI/CD 流水线 + 数据库每日备份（运维底线）
3. 建立策略样本外验证管线（StrategyValidationPipeline + PBO 检验）（策略置信度底线）

## 二、立即处理（本周内）

### SEC-1：`settings.py` GET 端点零认证暴露敏感信息

**文件**：`backend/app/api/routes/settings.py` 第 28-31 行、第 82-128 行

**问题**：`GET /api/settings` 和 `GET /api/settings/runtime` 没有任何认证依赖。前者返回 LLM 配置信息（是否已配置、endpoint 类型），后者返回数据库后端类型、CORS origins、数据源配置和运行环境路径。

**影响**：任何能访问服务器的人（含内网扫描、爬虫）都能获取部署拓扑信息，为后续攻击提供情报。

**修复**：为这两个端点添加 `Depends(require_admin_auth)`。`settings.py` 路由器级别设置 `dependencies=[Depends(get_current_user)]`。

**验证**：`curl http://43.143.243.97:18090/api/settings` 应返回 401。

### SEC-2：`auth_secret_key` 默认空值 + 危险回退链

**文件**：`backend/app/core/config.py` 第 46 行、`backend/app/services/auth_service.py`

**问题**：`auth_secret_key: str = ""` 默认空字符串。当其为空时，`auth_service.py` 的 `_auth_secret()` 方法依次尝试 `admin_api_token` → `database_url` 作为 HMAC 签名密钥。`database_url` 的前缀（`sqlite:///./data/t_quant.db`）是高度可预测的——任何读过项目 `config.py` 的人都能伪造有效令牌。

**修复**：
```python
auth_secret_key: str = ""  # 启动时若仍为空，拒绝启动并打印明确错误
```
在 `main.py` 的 `lifespan()` 中添加启动检查：
```python
if not settings.auth_secret_key or settings.auth_secret_key == "":
    raise RuntimeError("AUTH_SECRET_KEY must be set in .env. Generate with: python -c 'import secrets; print(secrets.token_urlsafe(64))'")
```
同时移除 `_auth_secret()` 中的回退链——不要从 `admin_api_token` 或 `database_url` 派生密钥。

**验证**：清空 `.env` 中的 `AUTH_SECRET_KEY`，重启服务应拒绝启动。

### SEC-3：SSE 认证令牌通过 URL 查询参数传递

**文件**：`backend/app/api/routes/intraday.py` 第 46 行

**问题**：`token: str = Query(default="")`——SSE 流连接的认证令牌作为 URL 查询参数传递。查询参数会被 nginx 访问日志、云负载均衡器日志和浏览器历史记录明文记录。

**修复**：改为 cookie-based 认证：
```python
@router.get("/stream")
def stream_intraday_confirmations(
    ...
    token: str = Cookie(default="", alias="auth_token"),
    ...
):
```
或使用临时流令牌交换：客户端先 `POST /intraday/subscribe`（Bearer 认证），获取一次性 `stream_token`，再传给 SSE 连接。

**验证**：grep nginx 日志不应出现 auth token。

### OPS-1：无版本控制

**问题**：项目无 `.git` 目录。30K+ 行的生产系统没有版本控制，无法回滚、无法协作、无法审计。

**修复**：

### OPS-2：数据库无自动备份

**问题**：SQLite 数据库（`data/t_quant.db`，含所有模拟盘交易记录和用户数据）无自动备份。

**修复**：创建 `scripts/backup-db.sh`，加入 cron 每日 3:00 执行：


## 三、高优先级优化（2 周内）

### STRAT-1：缺失策略样本外验证管线

**影响模块**：所有 11 个策略的置信度未知

**当前状态**：`docs/codex-prompt-模拟盘自动交易.md` 和 `docs/下一步演进计划-策略验证与盘中增强.md` 中规划的 `StrategyValidationPipeline` 未实现。策略的"绩效权重"依赖的 60+20 日回看窗口是样本内统计——策略可能因为过拟合历史而在实盘中表现骤降。

**需要**：
- `backend/app/services/paper/validation.py`：历史信号回放 + PBO 检验（Probability of Backtest Overfitting）
- 区分样本内（前 70% 交易日）和样本外（后 30% 交易日）
- 输出：交易笔数、胜率、净胜率、利润因子、Sharpe、PBO 概率、按市场状态分组

**预期收益**：排除 2-3 个过拟合策略，提升实盘信号可靠性。

### STRAT-2：`_rebuild_materialized_snapshot` 是死代码

**文件**：`backend/app/services/low_buy/screening.py` 第 26-34 行

**问题**：方法体为 `return None`，docstring 声称"重建物化快照"。调用方 `refresh_full_scan_cache` 假定返回有效数据。

**修复**：要么实现该方法（重建 `LowBuyScreenerResponse`），要么删除并清理所有调用方。

### PAPER-1：模拟盘浮点精度累积误差

**影响**：`backend/app/services/paper/` 下 50+ 处 `float()` 转换

**文件**：`order.py` 第 72/83 行（价格）、第 176-182 行（费用）、`position.py` 第 56/62/74 行（成本基准）、`account.py` 第 27-29 行（现金）

**问题**：匹配引擎用 `Decimal` 计算，写入数据库时转为 `float`，读出时再转回 `Decimal`。这个往返 `Decimal → float → Decimal` 在数百笔模拟交易中累积精度损失。

**修复**：将 `PaperOrder.price`、`PaperTrade.commission` 等字段改为 SQLAlchemy `Numeric` 类型存储，或至少确保计算路径中不经过 `float`。

### PAPER-2：执行器部分失败无事务回滚

**文件**：`backend/app/services/paper/executor.py` 第 21-52 行

**问题**：`execute_plan` 循环中单个 `create_order` 调用包含自己的 `db.flush()` 调用。如果订单 B 在 `order.py` 内部抛出 `ValueError`（在第 41-46 行被捕获），已创建的订单 A 的 `flush()` 数据已经存在。外层的 `except Exception`（第 49 行）只能捕获未被内层 `except ValueError` 捕获的异常。

**修复**：将 `execute_plan` 重构为显式事务边界：
```python
def execute_plan(self, account_id, planned_orders, dry_run=False):
    try:
        for order_spec in planned_orders:
            self.order_service.create_order(...)
        if not dry_run:
            self.order_service.db.commit()
    except Exception:
        self.order_service.db.rollback()
        raise
```

### AUTH-1：多个路由模块在路由器级别无认证

**文件**：`analysis.py` 第 12 行、`research.py` 第 22 行、`instruments.py` 第 9 行、`screeners.py` 第 16 行、`agent.py` 第 29 行

**问题**：这些路由模块在路由器级别均设置了 `dependencies=[Depends(get_current_user)]`。但 `settings.py` 没有（`router = APIRouter()` 空依赖）。此外，路由器级别依赖只是第一道防线——个别端点可能因遗漏而未受保护。

**修复**：为所有未在路由器级别设置认证依赖的路由模块添加：
```python
router = APIRouter(prefix="/xxx", dependencies=[Depends(get_current_user)])
```

### PERF-1：SQLite + 自动交易并发风险

**文件**：`backend/app/core/config.py` 第 34 行、第 73 行

**问题**：`database_url: str = "sqlite:///./data/t_quant.db"` + `paper_auto_trading_interval: int = 120`。SQLite 不支持并发写操作。当 AutoTrader 执行 120 秒循环提交交易时，用户的 API 请求可能遇到 `database is locked`。

**修复**：
- 短期：将 SQLite journal 模式改为 WAL（`PRAGMA journal_mode=WAL`）
- 中期：为自动交易使用独立数据库连接池，超时时间设为 30 秒
- 长期：迁移到 PostgreSQL/MySQL 用于生产部署

## 五、长期演进建议

### 5.1 策略体系

1. **建立持续 Walk-forward 验证**：每月自动对全部 11 个策略运行 5 折时间序列交叉验证。PBO 概率 > 0.3 的策略应降级为研究或废弃。这是确保实盘信号不会因过拟合而导致灾难性失败的唯一方法。
2. **整合成交额流动性分桶**：不应使用统一的滑点假设（5bps 股票 / 2bps ETF）。按日均成交额对股票进行分桶（< 5000 万 / 5000 万-2 亿 / > 2 亿），并为每个桶建模单独的滑点。此举可防止小盘股策略在回测中出现虚假的"超额收益"。
3. **增加板块热度维度**：当前"市场状态"（priority_board 中的 directional_bias）仅是方向性的（bullish/neutral/bearish）。缺少板块级别的热度（主线/次主线/轮动/退潮）限制了 intraday_confirmer 和 sector_mainline 策略的效力。

### 5.2 模拟盘

1. **Phase 1（已部分完成）**：PaperAccount / Order / Position / Trade 模型 + Executor + 撮合引擎 + 风控 ✓
2. **Phase 2（2-4 周）**：StrategyValidationPipeline（样本外回放 + PBO）+ Hermes AutoTrader（基于 Agent 的自动交易编排）+ 飞书通知集成
3. **Phase 3（1-3 月）**：实时分钟线确认（SSE 推送）+ 风险熔断器（连续亏损自动暂停）+ 多账户/多策略对比

### 5.3 Agent 架构

当前 Agent 工具注册表（6 个工具，全部只读 + 1 个预留通知）设计合理。建议：

1. **短期**：为通知工具实现飞书适配器——完成 `local_safe_api.py` 中第 35 行的存根（"notification adapter not configured"）→ 以此作为 Agent 飞书集成的概念验证。
2. **中期**：为 AutoTrader 添加 `read_and_recommend` 工具（Agent 读取 priority_board → 输出 sized_order 计划 → 人类审核 → 执行）。Agent 本身不应直接下单——它只输出需要人类确认的建议。
3. **长期**：Provider 抽象层（`backend/app/agent_providers/`）已允许在 `local_safe_api.py`（确定性规则）、Hermes（本地 LLM）和 OpenClaw（云端 Agent）之间切换。保持这一层清晰——永远不要让 Agent 直接访问数据库或 shell。所有工具必须仅通过 HTTP API 端点操作，且需接受正常的认证/授权检查。

### 5.4 数据质量

1. **停牌检测**：当前 `pool.py` 中的 `_is_excluded_symbol` 仅检查名称前缀。不存在实时停牌检查。`BoardCandidate` 数据类需要有 `is_suspended` 字段，由市场数据服务填充。
2. **涨跌停检测**：策略管线不检查个别候选股是否处于涨停或跌停。一只处于涨停的股票永远无法成交，但可能在回测中被计为"成功信号"。
3. **数据新鲜度**：MarketDataService 不追踪行情数据的时间戳属性。陈旧的行情数据（超过 120 秒）在 `PaperMatchingEngine` 中被拒绝，但策略筛选器仍在使用。

### 5.5 性能架构

1. **物化快照**：当前 `_rebuild_materialized_snapshot` 返回 None。实现真正的物化快照（每小时或每次行情更新时完全重建一次），将使 `priority_board` 的 p99 延迟从 ~600ms 降低到 ~15ms。
2. **基准缓存**：2 分钟 TTL 的 priority_board 基准缓存可接受。但应添加事件驱动的失效——当 `first_board` 策略的 60 日绩效窗口滚动时，手动触发缓存刷新。
3. **数据库索引**：`paper_orders` 和 `paper_trades` 表中按 `account_id + trade_date` 的复合查询常见但未建立索引。`CREATE INDEX idx_paper_trades_account_date ON paper_trades(account_id, trade_time)`。

### 5.6 Web/App 产品体验

1. **统一加载态**：部分页面在 API 调用期间展示骨架屏，其他页面则留空。统一使用 `skeleton-line` CSS 类。
2. **离线模式**：移动端应有本地行情缓存。当前 Capacitor 应用完全依赖网络请求——所有数据在离线时丢失。使用 Capacitor Storage API 缓存最近已知的好数据。
3. **错误恢复**：API 调用失败后没有自动重试策略。在 `client.ts` 中添加带有指数退避的自动重试（最多 2 次）。

## 六、策略专项结论

### 6.1 保留生产策略（核心层）

| 策略 | 状态 | 理由 |
|------|------|------|
| `first_board` | **保持核心** | 最清晰的入场逻辑（首板后第一次回踩），优先级榜主力。与 `volume_shrink` 形成互补（结构 vs 量价）。 |
| `volume_shrink` | **保持核心** | 量价关系信号独立于 `first_board` 的结构信号，跨家族共振价值高。量能萎缩特征在不同市场环境下相对稳定。 |
| `classic_retrace` | **保持核心** | 原始低吸法——十日涨停 + 缩量回踩 + 均线支撑。经过最长时间的市场检验，信号数量充足。 |
| `divergence_consensus` | **保持核心** | 分歧转一致信号在震荡市和修复市下表现优异。家族归属独立（分歧家族），不与其他策略信号相关。 |

### 6.2 辅助生产策略

| 策略 | 状态 | 理由 |
|------|------|------|
| `ma_support` | **保持辅助（0.65x 权重）** | 均线支撑是良好的补充信号，但独立使用时胜率偏低。作为"结构确认"的加分项更有价值。 |
| `breakout_support` | **保持辅助** | 位置支撑逻辑清晰，但信号频率低。保留在辅助层，不给 buy_now（仅 soft_buy_now + near_entry）。 |
| `late_session_strong_support` | **保持辅助，观察中** | 新策略。日线 + 盘中确认的双验证设计合理。需要更多样本外数据验证。当前不给 buy_now，仅 near_entry。 |

### 6.3 研究验证策略（不参与优先榜）

| 策略 | 状态 | 理由 |
|------|------|------|
| `limit_up_breakout_retrace` | **保留研究** | 平台突破 + 缩量洗盘 + 二次转强的三层条件过于苛刻。信号频率极低（月均 < 3 个），样本量不足以通过 PBO 检验。保留用于月度策略评审参考。 |
| `core_midcap_vwap_ma5_retrace` | **保留研究** | 中军容量股为核心标的是正确的方向，但"盘中站回 VWAP"的执行条件需要分钟线数据持续提供。待 IntradayDataService 补齐后再升为辅助。 |
| `sector_mainline_first_divergence_low_buy` | **保留研究** | 主线分歧逻辑理论上最有 alpha，但板块主线生命周期（启动→发酵→高潮→分歧→退潮）的人工判断与量化指标之间的鸿沟需要至少 3 个月的回测数据才能缩小。当前不宜进入生产。 |

### 6.4 降级为辅助因子

| 策略 | 状态 | 理由 |
|------|------|------|
| `deep_pullback` | **已降级为因子** | 错杀回撤本质上是极高风险的交易。作为独立策略，其胜率不足以覆盖止损成本。作为 `risk_aware_bonus` 因子，可在核心策略已给出买入信号时提供额外的风险溢价加仓依据。 |
| `trend_rebound` | **已降级为因子** | N 字回拉信号频率低且回撤大。作为 `momentum_bonus` 因子为已有核心信号的标的提供动量加分，比独立信号更有价值。 |

### 6.5 新策略优先级

| 策略 | 优先级 | 理由 |
|------|--------|------|
| `late_session_strong_support` | **P1**（已存在于优先榜辅助层） | 日线强收盘 + 盘中确认，隔日冲高兑现。适合 T+1 制度。需要更多 20 日窗口的绩效数据。 |
| `core_midcap_vwap_ma5_retrace` | **P2**（研究层） | 中军容量股回踩逻辑正确，但执行条件依赖分钟线数据——当前数据基础设施不支持。 |
| `sector_mainline_first_divergence_low_buy` | **P2**（研究层） | 主线分歧是 alpha 最强但最难量化的策略。需要板块主线生命周期的量化模型——这是一个独立的研究项目。 |

### 6.6 今日做 T 倾向预测

当前 `priority_board.directional_bias` 仅给出市场方向性（bullish/neutral/bearish），不包含个股级别的 T 倾向（正 T / 反 T / 观望）。建议增加一个整合函数，输入：

- 个股量价结构（VWAP 偏离、量比、振幅）
- 市场情绪（涨跌比、涨停家数、炸板率）
- 板块热点（所属板块排名、板块内个股协同）
- 个股地位（龙头/中军/跟风）
- 持仓成本（浮盈/浮亏百分比、持仓天数）
- 可用数量（T+1 锁仓量 vs 可用量）

输出：正 T 得分 / 反 T 得分 / 观望得分。这个函数应由 `stock-analysis-specialist` 角色定义规则，`trading-quant-lead` 量化验证。

### 8.1 数据模型评估

| `PaperDailyReport` | 良好 | LLM 点评存储已实现 |

### 8.2 撮合规则评估

- 佣金 0.025%（最低 5 CNY）：正确。但多笔同日同代码订单每笔都收最低 5 CNY，高于真实券商（收一次）。
- 印花税 0.05%（仅卖出）：正确。A 股印花税为单边征收。
- 过户费 0.001%：正确。
- 滑点：股票 5bps、ETF 2bps。应改为按成交额分桶（见 5.1.2）。
- 涨停/跌停拒绝：已实现。买入时 `current_price >= up_limit` 拒绝，卖出时 `current_price <= down_limit` 拒绝。
- T+1 计算：使用了交易日历，方向正确。但比较逻辑使用 `date.today()` 而非上个交易日的实际日期——在周末假期仍有微小偏差。

### 8.3 风控评估

当前风控规则（`PaperRiskControlService`）设计合理：

- 单笔最大 30% 账户资产 ✓
- 单票最大 40% 总仓位 ✓
- 单日买入上限 60% 账户资产 ✓
- 单日最多 20 笔委托 ✓
- 高风险事件自动阻止新增委托 ✓

建议增加：
- 连续亏损熔断（连续 3 笔亏损 → 暂停 60 分钟）。已在演进计划中规划，尚未实现。
- 单日最大亏损限制（当日损失 > 3% 账户资产 → 停止交易）。当前不存在此限制。
- 波动率自适应仓位（高波动率市场 → 减少单笔仓位）。当前使用固定的 30%/40%/60% 阈值，不因市场变化而调整。

### 8.4 Hermes Agent 集成

当前 Agent 只能访问只读 API（6 个只读工具 + 1 个已禁用通知工具）。AutoTrader 的设计是正确的——Agent 不直接下单。

**Phase 1（先只读）**：Agent 读取 priority_board → 生成 sized_order 计划 → 人类在 Web 端审核 → 手动执行。Agent 输出应有明确声明："本建议由 AI 生成，不构成交易指令，请结合自身判断执行。"

**Phase 2（半自动）**：Agent 仅在选择 `dry_run=false` 时才能提交订单。每次执行前需要二次确认（Web 端弹出确认对话框，或在模拟盘设置中开启"允许 Agent 自动执行"开关）。所有 Agent 提交的订单在 `PaperOrder` 上标记 `source = "agent"` 以便事后审计。

**Phase 3（全自动，仅在模拟盘）**：Agent 可在交易时间内自动提交订单，但需满足所有以下条件：
- `paper_auto_trading_enabled = true`
- `agent_enable_write_tools = true`
- 风险熔断器未触发（连续错误 < 3 次）
- 每日风控限制未达上限
- 所有操作记录在 `paper_agent_audit_log` 表中

**永远不允许**：Agent 访问真实交易账户、数据库（除通过 API）、shell 或文件系统。代理权限边界必须由 `AgentPolicy` 和 Provider 层的工具白名单强制执行。

### 8.5 绩效指标评估

| 指标 | 公式 | 准确性 |
|------|------|--------|
| 胜率 | `wins / (wins + losses)` | 正确 |
| 净胜率 | `(wins - losses) / total_trades` | 正确——使用 `net_win_rate_pct` 而非原始胜率作为主要指标是正确的。胜率对交易数量敏感，净胜率更稳健 |
| 平均收益 | `avg(trade_returns)` | 正确 |
| 利润因子 | `gross_profit / gross_loss` | 正确，但应注意小样本下利润因子可能过度乐观 |
| 最大回撤 | 峰值到谷值的下降百分比 | 计算公式需要验证——确保使用净值曲线的滚动最大回撤，而非单笔最大亏损 |
| Sharpe | 未实现 | 模拟盘需要 Sharpe 比率（至少月度）来比较不同策略的风险调整后收益 |

### 8.6 分阶段落地路线

**第 1-2 周**：修复浮点精度（PAPER-1）+ 事务边界（PAPER-2）+ 实现 `_rebuild_materialized_snapshot` → 优先榜延迟降至 < 100ms

**第 3-4 周**：StrategyValidationPipeline（PBO）+ 将 3 个研究层策略从"有信号无验证"迁移到"有样本外统计"

**第 5-8 周**：Hermes AutoTrader Phase 1（只读推荐）→ Agent 在 Web 端展示 sized_order 建议，人类手动执行

**第 9-12 周**：IntradayConfirmer 数据源补齐 + SSE 推送 → 分钟线确认信号实时推送到前端

## 九、Agent 专项结论

### 9.1 当前最适配 Agent

对于该项目，当前最优选择是 **Hermes（本地部署）+ OpenAI 兼容 Provider 作为回退**：

- Hermes：本地运行在云服务器上，零 API 费用，适合每日收盘日报生成和盘前简报生成。延迟可接受（1-3 秒），这些任务无需实时响应。
- OpenAI 兼容 Provider：当 Hermes 不可用时回退，或用于更复杂的分析任务（策略季度评审、因子分析）。
- **不建议 OpenClaw 或 LangGraph**：当前项目不需要多 Agent 编排或复杂的工作流。单一 Agent 处理明确定义的任务（生成报告、输出交易建议）就够了。LangGraph 的图状态管理为此项目增加了不必要的复杂性。

### 9.2 推荐部署方式

| 组件 | 部署 | 理由 |
|------|------|------|
| Hermes (LLM) | 本地 Docker 容器在云服务器上 | 零 API 费用，数据隐私，报告生成延迟可接受 |
| Agent Provider | FastAPI 进程内 `AgentProvider` 接口 | 通过配置切换 Hermes / OpenAI / Anthropic。`local_safe_api.py` 已实现此模式 |
| 飞书 Bot | 通过 Agent 通知工具连接 | 同样通过 Provider 层路由——Agent 不直接与飞书交互 |

### 9.3 Tool Registry 设计评审

当前 6 个工具（全部只读 + 1 个已禁用的通知工具）是靠谱的基线。建议增加：

```
ToolDefinition(

    method="GET",
```

### 9.4 可替换 Agent 架构

```
                    ┌─────────────────────┐
                    │   AgentProvider     │  ← 抽象接口
                    │   (Protocol)        │
                    └──────┬──────────────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    LocalSafeApi    HermesProvider   OpenAIProvider
    (确定性规则)     (本地 LLM)       (云端 LLM)
```

当前 `local_safe_api.py` 通过 `AgentToolInvokeRequest` 调用本地 API 端点。要让 Hermes 工作，需要实现：

1. `HermesProvider.build() -> prompt`：将自然语言查询映射到工具调用指令
2. `HermesProvider.invoke() -> AgentToolResult`：执行工具调用并返回结果
3. `HermesProvider.process_response() -> ChatReply`：将工具结果格式化为用户友好的响应

Provider 切换通过 `config.py` 中的 `agent_provider: str = "local_safe_api"` 控制——在此添加 `"hermes"` 和 `"openai"` 作为选项，后端无需修改。

### 9.5 安全边界（不可妥协）

| 边界 | 规则 |
|------|------|
| 数据库访问 | Agent 绝对不能直接查询数据库。所有数据访问必须通过 API 端点，并接受正常的认证检查 |
| Shell 访问 | Agent 绝不能执行 shell 命令。Provider 层绝不能暴露 `subprocess` 或 `os.system` |
| 真实交易 | Agent 绝不能连接到真实券商 API。Agent 和真实账户之间必须始终由人类隔开 |
| 文件系统 | Agent 绝不能读取或写入文件。所有数据通过 API 响应返回 |
| 通知 | Agent 只能通过通知工具（`send_test_notification` 及其替换者）发送消息——不能直接与飞书/钉钉/邮件交互 |
| 审计 | 每个 Agent 工具调用必须记录：时间戳、user_id、tool_name、input_arguments（脱敏）、result_summary、provider_name |

## 十、代码质量专项结论

### 10.1 代码结构问题

**文件**：`backend/app/services/low_buy/service.py` 第 26-40 行

`_LowBuyRuntime` 继承自 13 个 Mixin 类。菱形 MRO 未显式文档化。如果任何两个 Mixin 定义了相同的方法名，解析顺序完全取决于 Python C3 线性化——容易引入难以调试的 bug。

**建议**：为 Mixin 方法命名添加前缀（如 `_priority_board_*`、`_screening_*`）以避免意外覆盖。在最顶层的 `_LowBuyRuntime` 类中添加明确的 MRO 示意图注释。

**文件**：`backend/app/services/low_buy/candidate.py` 第 668-768 行

`_build_candidate_risks` 和 `_build_candidate_tags` 分别有 60 行和 47 行，包含主要策略的重复分支逻辑。`limit_up_breakout_retrace` 和 `divergence_consensus` 的风险文本几乎相同。

**建议**：提取共享的风险级别和标签模板，使用策略键到模板映射的字典，而非 if/elif 链。

### 10.2 类型安全

**文件**：整个 `backend/app/services/paper/` 目录

在 `Decimal` 和 `float` 之间往返转换的 50+ 处实例造成静默精度损失。`position.py` 第 56 行的 `cost_basis = float(new_cost_basis)` 是最明显的例子——`new_cost_basis` 在 4 行前还是 `Decimal`。

**建议**：不要通过在边界处转换来绕过类型限制。将 SQLAlchemy 列类型从 `Float` 改为 `Numeric(18, 4)`，并在整个计算管道中保持 `Decimal`。

### 10.3 错误处理

**文件**：`backend/app/core/schema_compat.py` 第 49、61、95、164 行

Schema 迁移函数在异常时执行 `except Exception as e: logger.warning(...)` ——然后继续执行。如果前一步迁移失败（例如：ALTER TABLE ADD COLUMN 失败），后续步骤可能依赖于刚刚应该添加的列。数据库可能进入不一致状态，但迁移报告"成功"。

**建议**：区分预期错误（列已存在 → 跳过）和意外错误（表不存在 → 停止并报错）。对预期条件使用 `try: ... except IntegrityError: pass`（如果 DBAPI 支持），并通过异常类型而非通用 `Exception` 重新抛出意外错误。
