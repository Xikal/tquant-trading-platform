## 0. 总纲

### 0.1 项目当前基线

已完成：
- 12 个低吸策略 + 正T/反T 量化引擎
- 优先级榜、回测复盘、持仓监控
- Web 端（React/Vite/TypeScript）+ App 端（Capacitor）
- FastAPI 后端 + SQLAlchemy ORM + SQLite/MySQL
- Agent provider 抽象层（7 个预留 provider，均未实现）
- AiService（LLM 调用，已可用）

关键架构决策（本次开发必须遵守）：
- **不使用任何 agent 框架**（Hermes、LangGraph、CrewAI 等均不接入）
- 模拟盘的交易计划生成为**纯 Python 确定性逻辑**，不走 LLM
- LLM 仅用于收盘后的日报文本生成（复用现有 AiService）
- 模拟盘模块完全独立，不走现有 Mixin 继承链
- 定时执行使用现有 daemon 线程模式，不引入 Celery/Redis

### 0.2 开发阶段概述

```
P0（立即，1 周内）  → 安全修复 + Bug 修正 + 策略重组
P1（P0 后 2-3 周）  → 模拟盘核心（账户、持仓、委托、成交、撮合、T+1）
P2（P1 后 1-2 周）  → 模拟盘绩效统计
P3（P2 后 2-3 周）  → 代码质量提升
```

每个阶段独立验收，前一阶段验收通过后才能开始下一阶段。

### 0.3 关键约束

- 不修改现有策略的核心计算逻辑（仅重组分层，不改变打分公式）
- 不影响现有 Web/App 功能（所有变更向后兼容）
- 所有新 API 必须加鉴权
- 所有数据库操作必须通过 ORM
- 必须撰写单元测试

**当前问题**：`POST /api/agent/provider/invoke`（`api/routes/agent.py:93`）接受任意 `tool_name` 和 `arguments`，调用 `provider.invoke_tool()`，无任何认证检查。

**涉及文件**：

- `backend/app/agent_tools/policy.py`

- `backend/app/core/admin_auth.py`

**要求**：

1. 在 `agent.py` 的 `invoke_tool` 端点添加 `require_admin_auth` 依赖注入
2. 在 `policy.py` 中为每个已注册工具标注风险等级：

### 1.2 [BUG-1] net_win_rate 计算修复

**当前问题**：两个文件中 `net_win_rate` 与 `win_rate` 使用完全相同的计算公式，导致"净胜率"指标无意义。

**涉及文件**：
- `backend/app/services/low_buy/execution_backtest.py`（第 122-123 行）
- `backend/app/services/low_buy/performance.py`（第 352-353 行）

**要求**：

`execution_backtest.py:123` 修改为：
```python
net_win_rate=_rate(len(winners) - len(losers), max(len(filled), 1)),
```

`performance.py:352-353` 修改为：
```python
hit_rate=round(hit_count / max(filled_signals, 1) * 100, 2),
net_win_rate=round((hit_count - miss_count) / max(filled_signals, 1) * 100, 2),
```

注意：`performance.py` 需要先确认该函数中是否存在 `miss_count` 变量。如果不存在，需要先计算出未命中/亏损笔数：
```python
miss_count = filled_signals - hit_count
```

**验收标准**：
- 回测面板中 `net_win_rate` 与 `win_rate` 数值不同（除非胜率 100%）
- 一个胜率 55% 亏损比盈利大的策略，净胜率应显著低于 55%
- 全胜时净胜率等于胜率（边界验证）

### 1.3 [SEC-2] Auth Token 存储方案改进

**当前问题**：`frontend/src/api/base.ts` 将 access_token 和 refresh_token 存于 `localStorage`，任何注入页面的恶意脚本可读取。

**涉及文件**：
- `frontend/src/api/base.ts`
- `backend/app/core/auth.py`
- `backend/app/api/routes/auth.py`

**要求**：

短期方案（本次实施）：

1. 在 `auth.py` 中将 access_token 过期时间缩短为 15 分钟
2. 在 `base.ts` 中，token 仍存于内存变量中用于 API 请求，但不再持久化到 localStorage
3. refresh_token 使用 httpOnly cookie 传递（后端 set-cookie，前端不读取）
4. 登录接口 `/api/auth/login` 的响应中，access_token 仍在 body 返回，refresh_token 通过 Set-Cookie header 返回
5. refresh 接口 `/api/auth/refresh` 从 cookie 读取 refresh_token 而非 body

**验收标准**：
- 页面刷新后需要重新登录（access_token 不持久化）
- refresh 流程正常工作
- XSS 攻击无法通过 `localStorage.getItem('access_token')` 窃取 token

### 1.4 [SEC-3] admin_auth 回路绕过修复

**当前问题**：`core/admin_auth.py:52-53` 允许当 `ADMIN_API_TOKEN` 为空时，任何来自 loopback 的请求直接通过。在反向代理后面可能被伪造 `X-Forwarded-For` header 绕过。

**涉及文件**：
- `backend/app/core/admin_auth.py`

**要求**：

1. 移除 "ADMIN_API_TOKEN 为空 + loopback 请求自动放行" 的逻辑
2. `_is_loopback_host()` 方法只信任 `request.client.host`（socket 级别 IP），不信任任何代理 header
3. 强制要求配置 `ADMIN_API_TOKEN` 才能访问 admin 端点
4. 如果 `ADMIN_API_TOKEN` 未配置，admin 端点直接返回 500 并记录日志（不允许 fallback 到免鉴权）

**验收标准**：
- 不配置 `ADMIN_API_TOKEN` 时，admin 端点不可访问
- 带 `X-Forwarded-For: 127.0.0.1` 的远程请求不能绕过认证
- 本地 `127.0.0.1` 请求不带 token 也不放行

### 1.6 [BUG-3] 回测止损退出价修正

**当前问题**：`execution_simulation.py:109`：
```python
exit_price = min(row.open_price, stop_loss) if row.open_price < stop_loss else stop_loss
```
当开盘价低于止损价时，以止损价退出。但真实市场中以开盘价（或更低）成交，导致回测低估亏损。

**涉及文件**：
- `backend/app/services/low_buy/execution_simulation.py`

**要求**：

修改为：
```python
# 如果开盘跳空跌破止损，以开盘价退出（反映真实亏损）
# 否则以止损价退出
if row.open_price <= stop_loss:
    exit_price = row.open_price  # 跳空跌破，实际在开盘价成交
elif row.low_price <= stop_loss:
    exit_price = stop_loss  # 盘中触发止损
else:
    exit_price = None  # 未触发止损
```

**验收标准**：
- 回测中跳空跌停的股票，退出价等于开盘价而非止损价
- 普通止损（非跳空）仍以止损价退出
- 历史回测结果中，止损退出的平均亏损略大于修改前

滑点逻辑：
- 股票买入滑点：`current_price * (1 + slippage_bps / 10000)`

- ETF 滑点减半

- 行情时间超过 120 秒，买入/卖出均被拒绝

```python
def _update_cost_basis(
    current_cost: Decimal,
    current_qty: int,
    new_cost: Decimal,  # 新买入的成交价（含费用分摊）
    new_qty: int,
) -> Decimal:
    """买入：新成本 = (旧成本*旧数量 + 新成本*新数量) / (旧数量 + 新数量)"""
    return (current_cost * current_qty + new_cost * new_qty) / (current_qty + new_qty)
```

**关键计算逻辑**：

- **净胜率**：使用修复后的公式 `(胜-负)/总成交 × 100`
- **Profit Factor**：`sum(盈利金额) / sum(亏损金额)`，亏损为 0 时返回 None
- **最大回撤**：遍历每日总资产，计算从峰值到谷值的最大跌幅
- **盈亏比**：`avg_win / abs(avg_loss)`，亏损为 0 时返回 None
- **平均持仓天数**：卖出日期 - 买入日期（取中位数和均值两个指标）

**验收标准**：
- 有 10 笔成交（5 盈利 5 亏损），胜率 50%，净胜率 0%
- 有 10 笔成交（8 盈利 2 亏损），胜率 80%，净胜率 60%
- 最大回撤计算正确（验证：峰值 10000→谷底 9000→回撤 10%）
- Profit Factor > 1 表示整体盈利，< 1 表示亏损
