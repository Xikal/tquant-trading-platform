## 二、逐模块详评

### 2.1 数据提供层 (`data_provider.py`, 340 行) — 评分 A-

**完成度**: 90%

已实现：
- `DailyBar` 冻结 dataclass，含 `vwap`、`is_valid`、`is_suspended` 属性
- `DailyBarDataProvider`：从 `DailyBarSnapshot` + `LowBuyResultSnapshot` 读取 PIT 数据
- `dataset_manifest`：数据集清单（hash + 复权方式 `"forward"`）
- `DataQualityReport`：12 个质量字段（缺失率、零价、停牌、数据滞后）
- ST 信号过滤（`_is_st_signal`）

未实现/偏差：
- `DailyBar` 缺少 `adjustment_factor` 字段（每根 bar 的复权因子不可独立追溯，只有 manifest 级别的 `adjustment_method`）
- ST 判断仅做了"名称含 ST 或退"的简单检查，未覆盖 *ST 变种和按交易日的精准判断
- `_bar_from_row` 假设 DB 行有 `instrument_type` 和 `market` 字段，存在 schema 兼容性风险

### 2.2 券商层 (`broker.py`, 148 行) — 评分 B+

**完成度**: 85%

已实现：
- 4 种执行模型（`OPEN_PRICE` / `VWAP` / `CLOSE_PRICE` / `ENTRY_ZONE_TOUCH` / `CONSERVATIVE_SLIPPAGE`）
- 封装 `PaperMatchingEngine` 做撮合
- 涨跌停/停牌拒绝（`_is_limit_up` / `_is_limit_down` / `is_suspended`）
- 费用计算委托给 `calculate_fee`

问题：
- `_is_limit_up` 阈值 `pct_chg >= 9.8` 硬编码，不区分主板/创业板/科创板/北交所不同涨跌幅限制
- `up_limit` / `down_limit` 传入撮合引擎的值与 `selected_price` 相同，不是真实涨跌停价（应为昨日收盘价的 +-10%）。这在 `CONSERVATIVE_SLIPPAGE` 等非开盘价模型中可能导致涨跌停判断逻辑错误

### 2.3 组合层 (`portfolio.py`, 249 行) — 评分 B

**完成度**: 80%

已实现：
- 多 lot 的 FIFO 持仓管理
- T+1 解锁逻辑（股票 T+1，ETF T+0）
- 买入冻结资金、卖出现金结算
- `PortfolioSnapshot` 快照输出

**严重 Bug #1 — `RealizedTrade` 缺少 `holding_days` 字段**：

文件第 47-59 行定义的 `RealizedTrade` 冻结 dataclass 不包含 `holding_days` 字段，但 `persistence.py` 第 115 行访问 `trade.holding_days`。这会直接抛出 `AttributeError`，导致任何回测结果持久化到成交表时崩溃。

修复方案：
```python
# portfolio.py 第 47-59 行，增加 holding_days 字段
@dataclass(frozen=True)
class RealizedTrade:
    ...
    holding_days: int = 0  # 新增
    ...
```

同时在 `_realized_trade()` 函数中计算 `holding_days`（trade_date - entry_date 之间的交易日数）。

### 2.4 引擎层 (`engine.py`, 498 行) — 评分 A-

**完成度**: 88%

已实现：
- 事件驱动主循环（逐日推进，先卖后买）
- 多策略信号去重（同 symbol 取最高分策略）
- Entry delay（信号到执行的延迟天数）
- 费用安全的 quantity 计算（`_cash_safe_quantity` 逐步降量直到费用可负担）
- 止损/止盈/持仓到期退出
- 强平检查（end_date 前持仓全部清仓）
- Cancellation token 支持
- `_dataset_manifest` 版本记录

问题：
- `_dedupe_signals` 使用 `>` 比较符，分数相同时靠 Python dict 插入顺序决定胜者，非确定性（应改用 `>=` 或加 tiebreaker）
- 强平使用 `bar.close_price`，未扣除卖出费用——最后一天的卖出手续费会直接吞噬现金余额
- engine 的结果集 `trades` 列表中，买入和卖出是独立的两笔 trade，缺乏显式的 buy-sell 配对 ID

### 2.5 分析层 (`analyzer.py`, 99 行) — 评分 B-

**完成度**: 55%

### 2.6 持久化层 (`persistence.py`, 165 行) — 评分 C+

**完成度**: 70%

**严重 Bug #2 — fee 计算只含卖出费**：

第 97-98 行：`fee_amount = gross_pnl - net_pnl`。这个公式只捕获了**卖出侧的手续费**（因为 `net_pnl = gross_pnl - exit_fee`）。买入侧的费用已经嵌入 `cost_basis` 中，不在 `gross_pnl` 中体现。造成成交记录中的 `fee_amount` 严重低估（通常少约 50%）。

修复方案：
```python
# 需要分别记录 entry_fee 和 exit_fee
# 或者在 portfolio._cost_basis 中存储 pre-fee cost，并在 sell 时计算 total_fee
```

**严重 Bug #3 — `requested_price` 赋值错误**：

第 85 行：`requested_price=float(order.fill_price or 0.0)`——将**成交价**赋值给**委托价**字段。对于成交订单，这掩盖了真正的委托价；对于拒绝订单（`fill_price=None`），它变成 0.0。应该从信号或配置中获取委托时的目标价。

其他问题：
- `result_json` 作为 `result.to_dict()` 整存到 DB，对含 500+ 交易日的净值曲线会产生数 MB 的 JSON blob，与已存在的 `backtest_daily_snapshots` 表重复
- benchmark 数据（`benchmark_close`、`benchmark_return_pct`、`turnover`）在 equity snapshot 中全是默认值
- 删旧写新不是事务性的，中断可能留下脏数据

### 2.7 任务服务 (`backtest_job_service.py`, 380 行) — 评分 B+

**完成度**: 85%

已实现：
- 异步任务创建（`create_run` 启动后台线程）
- `_RunCancelToken` 线程安全取消
- 分页列表查询、详情、净值、交易明细
- 权限控制（owner or admin）
- 线程安全的 DB session 隔离（每个后台线程独立的 `SessionLocal`）

问题：
- 后台线程是 daemon 线程，服务器关闭时中途持久化可能丢失
- `cancel_run` 访问 `_cancel_tokens` 字典时未持有锁（轻微的 race condition）
- 无重试逻辑，瞬态失败永久标记为 failed
- 无超时检测（卡住的回测线程不会被自动终止）

### 2.8 优化器/验证器 (`optimizer.py` 49 行 + `validator.py` 63 行) — 评分 B

两个模块均为"受控骨架"，标签为 `@controlled skeleton`。网格搜索有 `max_runs=20` 上限。Walk-Forward 有基础的 train/test 切分。代码本身没有 bug，但功能只是 Phase 4-5 的占位符。

### 2.9 报告层 (`reporter.py`, 45 行) — 评分 D

完全未被生产代码调用。`to_payload`、`to_summary`、`to_markdown` 三个方法都是死的。API 响应使用的是 `BacktestJobService._detail` 直接读 `result_json`。

## 八、架构优点

以下设计决策值得肯定，应在后续迭代中保护：

1. **paper 模块复用**。broker 封装 `PaperMatchingEngine` 而非重写撮合逻辑。portfolio 复用 `calculate_fee` 和 `to_money`。这意味着回测中使用的交易成本模型与模拟盘一致——回测结果的可信度得到保证。

2. **冻结 dataclass 的广泛使用**。`DailyBar`、`BacktestSignal`、`ExecutionRequest/Result`、`RealizedTrade`、`PortfolioSnapshot` 全部不可变。回测的确定性由此保障。

3. **取消令牌的优雅设计**。`_RunCancelToken` 使用 `threading.Event`，取消检查散布在 engine loop 的 3 个关键点（`_cancel_requested`、`_process_signals` 入口、退出循环后）。取消后保留部分输出。

4. **DataQualityReport 不阻塞回测**。即使数据质量差（缺失交易日期、零价异常），回测仍然运行，但结果中标注了质量警告。这避免了"数据不完美就不让用"的困境。

5. **前端 SVG 轻量净值图**。没有引入 ECharts 重依赖做首版净值曲线，用纯 SVG 路径渲染，体积小加载快。等回测数据量上来后再引入重图表库是正确的优先级。

## 十、结论

Codex 此次交付的 v2 回测系统是**一次认真、方向正确的实现**。2,547 行后端 + 820 行前端在工程量和质量上超过了"骨架 demo"但尚未达到"生产就绪"。最大的亮点是 paper 模块复用的架构决策——回测和模拟盘共享同一套交易成本模型，长期看这是正确的。

3 个 bug（全部在 `persistence.py` 和 `portfolio.py` 的交接处）必须在 testing 中发现并修复。`analyzer.py` 的分析能力是最大的功能缺口——做了 55% 的分析指标，缺了 45%，导致回测结果页的"基准收益"字段在需求中定义了但实际永远为空。
