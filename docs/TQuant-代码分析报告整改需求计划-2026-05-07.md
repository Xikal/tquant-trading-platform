# TQuant 代码分析报告整改需求计划

来源：`/Users/j/Downloads/TQuant_代码分析报告.html`  
生成日期：2026-05-07  
适用项目：TQuant A 股短线做 T / 低吸选股量化辅助平台  
文档定位：将报告中的问题、优化建议和发展方向整理为可执行需求，不构成交易建议。

## 1. 总体结论

报告对当前项目的总体判断是：架构已经具备生产级基础，策略体系、回测系统、风控机制、Agent Safe API 边界和模拟盘闭环基本成型；当前不适合大规模推倒重构，更适合围绕“参数可配置、数据源统一、性能热点、ML 质量门槛、可维护性”做定向补强。

整改目标不是改变现有交易规则，而是把现有能力从“功能可用”推进到“可配置、可验证、可扩展、可审计”。

## 2. 报告核心发现

### 2.1 已确认优势

- 后端采用 FastAPI、Pydantic v2、SQLAlchemy 2.0，类型约束和服务分层基础较好。
- 前端 React、Vite、TypeScript 架构成熟，已具备懒加载和页面拆分基础。
- 低吸策略已形成 `core / auxiliary / research / factor` 分层，能区分生产策略、辅助策略、研究策略和因子。
- Agent 层通过 Safe API 读取脱敏结构化数据，不直接访问数据库、不执行 shell、不直接下单，权限边界合理。
- 回测引擎支持多策略回放、滑点模型、归因、数据质量、强制清算和持仓约束。
- 风控体系覆盖硬风控、市场状态、动态惩罚预算、模拟盘熔断。
- Provider Router 已覆盖部分行情主路径，具备降级和数据质量标记的设计基础。

### 2.2 主要短板

- 策略阈值仍大量硬编码，运行时参数版本系统未完全接管。
- 部分 AkShare 调用仍绕过 Provider Router，数据质量、超时和降级口径不统一。
- SQLite 写锁、缓存 deepcopy、因子权重缓存线程安全等性能热点仍需修。
- ML 信号模块骨架完整，但生产门槛偏低，缺少 K-fold、样本外稳定性和模型回滚闭环。
- `paper.py`、`candidate_rules.py`、`shared.py` 等文件职责偏重，后续维护成本高。
- 回测执行模型缺少市场冲击成本，对小盘股和大额成交可能偏乐观。
- 自动治理只有降级/暂停闭环，恢复门槛不足，存在状态震荡风险。

## 4. P0 需求

### R-001 策略阈值完整迁移到参数版本系统

#### 当前问题

报告指出 `candidate_rules.py` 中仍存在大量硬编码策略阈值字典，例如：

- `LIMIT_UP_BREAKOUT_PREFILTER`
- `DIVERGENCE_CONSENSUS_PREFILTER`
- `CORE_MIDCAP_RETRACE_PREFILTER`
- 其他策略预过滤与确认阈值

虽然项目已有 `runtime_parameters.py` 和参数版本体系，但迁移不完整，导致策略调参需要同时改代码和参数表，容易产生代码阈值、运行时参数、回测参数三者不一致。

#### 影响范围

- 低吸选股策略筛选
- 策略回测
- 策略参数优化
- 策略审计
- 线上调参和灰度

#### 实现方案

1. 建立统一策略参数 schema。
   - 每个策略定义参数 namespace，例如 `low_buy.first_board`、`low_buy.volume_shrink`。
   - 参数包含 `key`、`type`、`default`、`min`、`max`、`description`、`risk_level`。

2. 将硬编码阈值迁移为参数读取。
   - 保留代码内默认值作为兜底，但所有运行时计算优先读取参数版本。
   - 迁移顺序先覆盖生产策略，再覆盖辅助/研究策略。

3. 回测任务绑定参数版本。
   - Backtest manifest 记录 `parameter_version_id`、`parameter_hash`。
   - 回测报告展示参数版本，避免“结果不可复现”。

4. 管理端支持参数变更审计。
   - 记录操作者、变更前后值、变更原因、生效范围。
   - 参数变更后触发相关策略缓存失效。

5. 建立参数导出和回滚能力。
   - 支持导出当前参数集为 JSON。
   - 支持回滚到历史参数版本。

#### 验收标准

- 所有 core 策略阈值不再直接依赖硬编码字典。
- 修改参数后无需发版即可影响下一轮策略扫描。
- 回测报告能展示所用参数版本。
- 参数变更有审计日志。
- 默认参数缺失时系统能安全回退到代码默认值，并打出告警。

#### 测试要求

- 单元测试：参数读取、默认值回退、参数类型校验。
- 集成测试：修改参数后策略输出变化可追踪。
- 回测测试：同一策略不同参数版本结果可区分。

### R-002 AkShare 直接调用统一迁移到 Provider Router

#### 当前问题

报告指出部分服务仍直接使用 `akshare` 或 `self.ak.xxx`，例如市场情绪、市场状态和板块热力相关服务。这样会绕过 Provider Router，导致：

- 数据源降级不统一。
- 数据质量标签不完整。
- timeout 配置无法统一控制。
- AkShare 故障可能拖慢业务请求。

#### 影响范围

- 市场状态分类
- 热点行业识别
- 情绪数据
- 板块热力
- 低吸策略主线过滤
- Agent 市场分析工具

#### 实现方案

1. 梳理所有 AkShare 直连点。
   - 使用 `rg "akshare|self.ak|ak\\." backend/app` 全量扫描。
   - 分为 quote、batch_quote、sector_heatmap、market_sentiment、limit_up_pool、calendar 等能力。

2. 扩展 `MarketProvider` 协议。
   - 增加 `fetch_market_sentiment`。
   - 增加 `fetch_sector_heatmap`。
   - 增加 `fetch_limit_up_pool`。
   - 增加 `fetch_trade_calendar`。

3. Provider Router 统一调度。
   - 每个 provider 返回 `ProviderResult` 和 `MarketDataQuality`。
   - 失败时切换下一个 provider。
   - 所有返回结构包含 `source`、`quality`、`stale`、`message`。

4. 业务服务只依赖 Router。
   - `market_state`、`emotion`、`hot_industries` 不再直接 import akshare。
   - 短期内无法替换的 AkShare raw 方法集中放到 `AkshareMarketProvider` 内部。

5. 数据源失败兜底。
   - 可用最近一次有效快照。
   - 返回 stale 标记，不把旧数据包装成实时数据。

#### 验收标准

- 业务服务层无直接 AkShare 调用。
- Provider Router 能覆盖行情、板块、情绪、交易日历主路径。
- 数据源失败时 API 仍返回结构化降级结果。
- 前端能看到“数据降级/待补齐/过期”状态。

#### 测试要求

- Provider contract 测试。
- AkShare 故障 monkeypatch 测试。
- Provider Router 降级顺序测试。
- 市场状态 API 数据质量字段测试。

## 5. P1 需求

### R-003 Priority cache 序列化优化

#### 当前问题

`priority_cache.py` 的 get/set 使用 `deepcopy`，对大型 Pydantic 对象有 CPU 开销。报告估计每次命中约 2-5ms，在高 QPS 下会累积。

#### 实现方案

- 对 Pydantic 响应对象使用 `model_dump_json()` 存储。
- 读取时用 `model_validate_json()` 恢复。
- 非 Pydantic 对象保留浅拷贝或显式 immutable 结构。
- 保留现有 TTL 和锁逻辑。

#### 验收标准

- priority board 缓存返回结构与原来一致。
- 缓存命中路径无对象共享副作用。
- 基准测试显示命中耗时下降或不劣化。

### R-004 拆分 `paper.py` 路由

#### 当前问题

`paper.py` 路由文件接近 800 行，职责包括账户、持仓、订单、绩效、自动交易、风控、日报等，维护成本高。

#### 实现方案

拆分为：

- `paper_accounts.py`
- `paper_positions.py`
- `paper_orders.py`
- `paper_performance.py`
- `paper_auto_trading.py`
- `paper_risk.py`
- `paper_reports.py`

保持 `/api/paper/*` 路径不变，通过统一 `APIRouter` 汇总。

#### 验收标准

- 外部 API 路径、请求体和响应体不变。
- 现有前端无需改动。
- 每个子路由职责清晰，单文件控制在合理范围。

### R-005 提升 ML 生产门槛并加入 K-fold CV

#### 当前问题

当前 ML 生产门槛 `accuracy >= 0.55`、`AUC >= 0.55` 偏低，接近随机模型水平。报告指出小样本 AUC 高可能是过拟合。

#### 实现方案

1. 提升默认生产门槛：
   - `accuracy >= 0.60`
   - `auc >= 0.65`
   - `sample_count >= 1000`
   - `kfold_mean_accuracy >= 0.60`
   - `kfold_mean_auc >= 0.65`

2. 训练流程增加 5-fold CV。
   - 输出每折 accuracy、auc、precision、recall。
   - 保存 CV 均值、标准差。

3. promote 时强校验。
   - 未通过门槛只能进入 research 状态。
   - 生产模型必须显式 promote 并记录审计。

4. 前端展示模型质量。
   - 展示样本数、验证集指标、CV 指标、是否满足生产门槛。

#### 验收标准

- 不满足 CV 门槛的模型无法变成 production。
- 已有模型若指标不足，保持可用但标记为 legacy/research，不影响当前生产链路。

### R-006 因子权重缓存线程安全修复

#### 当前问题

`_WEIGHT_CACHE` 是模块级变量，15s TTL 刷新缺少锁，高并发下可能多线程同时刷新。

#### 实现方案

- 引入 `threading.Lock` 保护刷新路径。
- 双重检查 TTL，避免锁内重复读取。
- 保持读路径轻量。

#### 验收标准

- 并发调用因子评分不会抛异常。
- 同一 TTL 窗口最多触发一次 DB 读取。

### R-007 按场景拆分 HTTP timeout 配置

#### 当前问题

`http_timeout = 12s` 被行情、Agent、飞书等不同场景复用。行情 quote 更需要快速失败切换 provider，12s 会拖慢页面。

#### 实现方案

新增配置：

- `market_quote_timeout_seconds = 3`
- `market_batch_timeout_seconds = 8`
- `market_calendar_timeout_seconds = 5`
- `agent_timeout_seconds` 保持独立
- `notification_timeout_seconds = 8`

Provider 调用按类型使用对应 timeout。

#### 验收标准

- quote 单源超时不超过 3s。
- 批量行情和板块数据不使用 quote timeout。
- 配置缺失时安全回退到旧 `http_timeout`。

## 6. P2 需求

### R-008 策略自动治理增加恢复门槛

#### 当前问题

自动治理已有降级和暂停，但恢复门槛不完整，可能出现 active/watch/paused 状态震荡。

#### 实现方案

- paused -> watch：连续 5 个交易日健康分 > 55，且无新止损/熔断事件。
- watch -> active：连续 10 个交易日健康分 > 65，且近 20 笔净胜率为正。
- 恢复动作写入治理日志。
- 默认只自动恢复到 watch，active 需配置开关或管理员确认。

#### 验收标准

- 策略不会因为单日好转立即恢复。
- 前端显示“观察恢复中/还需 N 天”。

### R-009 ML artifact 远端备份与恢复

#### 当前问题

模型 artifact 只存在本地 `data/ml_models/`，容器重建或磁盘故障会导致 DB 状态与文件不一致。

#### 实现方案

- 模型表增加 `remote_artifact_uri`、`artifact_checksum`。
- 支持 OSS/S3/HTTP storage provider。
- 训练完成后异步上传 artifact。
- 启动或推理时本地文件缺失，则尝试从远端恢复。
- 恢复失败时模型降级为 unavailable。

#### 验收标准

- 本地 artifact 删除后可从远端恢复。
- checksum 不一致时拒绝加载。

### R-010 回测增加 Market Impact 执行模型

#### 当前问题

当前回测主要使用保守滑点模型，缺少大单冲击成本。小盘股、低流动性标的可能被高估。

#### 实现方案

新增执行模型 `MARKET_IMPACT`：

- 当订单金额 / 日均成交额 > 5%，叠加滑点。
- 流通市值 < 30 亿时额外加冲击成本。
- 结合成交额、振幅、换手、涨跌停状态调节。

建议初始参数：

- 基础冲击：0.10%
- 中等冲击：0.30%
- 高冲击：0.80%
- 涨跌停附近强制不可成交或极差成交。

#### 验收标准

- 回测报告展示执行模型。
- 同一策略在 `CONSERVATIVE_SLIPPAGE` 和 `MARKET_IMPACT` 下结果可对比。
- 小盘低流动性样本收益显著更保守。

### R-011 热点行业最近有效缓存兜底

#### 当前问题

热点行业数据源失败时可能返回空列表，导致市场状态和主线策略保守降级，出现误判。

#### 实现方案

- 增加最近有效热点行业缓存，TTL 5 分钟。
- 数据源失败时返回最近有效缓存，并标记 `stale=true`。
- 若缓存也不存在，才返回空列表。
- 前端显示“热点数据沿用上一轮”。

#### 验收标准

- 板块源短暂失败时不会直接把主线状态清空。
- 所有使用 hot_industries 的策略能识别 stale 状态。

### R-012 回测前端归因可视化增强

#### 当前问题

回测归因字段完整，但前端展示深度不足，用户难以理解收益来自哪里、亏损来自哪里。

#### 实现方案

- 策略归因表：策略、交易数、胜率、净胜率、均收益、最大回撤、profit factor。
- 市场状态归因表：按 8 类状态拆分。
- 行业归因表：展示热点行业/非热点行业差异。
- 失败原因分布：止损、未成交、追高、冲高回落、板块退潮。
- 支持导出 CSV。

#### 验收标准

- 回测详情页能定位策略、市场、行业三个维度的收益来源。
- 空数据时展示清晰说明，不显示空白。

## 7. Roadmap 需求

### R-013 Mixin 继承迁移到组合模式

#### 当前问题

低吸主服务通过多个 Mixin 串联逻辑。扩展快，但依赖隐式，MRO 认知成本高。

#### 目标架构

- `LowBuyScreenerService` 作为协调者。
- `ScreeningService` 负责筛选。
- `PriorityBoardService` 负责优先榜。
- `QuoteRefreshService` 负责行情刷新。
- `HistoryService` 负责历史复盘。
- `PerformanceService` 负责绩效。

#### 实施原则

- 分阶段迁移，不一次性重构。
- 先抽纯函数和无状态服务。
- 保持现有 API 和响应结构不变。
- 每拆一块跑回归测试。

### R-014 盘中实时信号、ETF 做 T、Level2 扩展

#### 方向

- Level2 大单净流入、撤单、封单、炸板、回封。
- 行业 ETF 做 T，利用 ETF T+0 特性替代部分个股低吸。
- 盘中异常模式检测，识别龙头拉升/退潮节点。

#### 前置条件

- 数据源稳定性验收。
- 手续费、滑点和冲击成本模型。
- ETF 与普通股票交易制度差异明确建模。

### R-015 Agent 委托草稿

#### 原则

Agent 仍不得直接下单。可新增“委托草稿”能力：

- Agent 生成草稿。
- 用户确认。
- 模拟盘执行。
- 全链路审计。

#### 验收标准

- 默认关闭。
- 需要显式权限。
- 草稿不改变资金或持仓。
- 用户确认前不创建真实订单。

### R-016 App 个性化推送与复盘标注

#### 方向

- 用户关注标的触发买点时推送。
- App 端快速记录交易复盘笔记。
- 笔记绑定策略信号，形成 ML 人工标注样本。
- 历史信号与走势对比时间轴。

## 8. 详细实施阶段

### Phase 1：稳定性与生产闭环补强（1-2 周）

目标：修复 P0 和高收益 P1。

任务：

1. R-001 策略阈值迁移第一批：core 策略。
2. R-002 Provider Router 覆盖市场情绪和热点行业。
3. R-006 因子权重缓存锁。
4. R-007 timeout 拆分。
5. R-011 热点行业最近有效缓存。

验收：

## 10. 风险与约束

### 10.1 不应直接做的高风险动作

- 不应一次性重写低吸服务 Mixin 继承链。
- 不应在没有数据质量验收前启用 Level2 或新外部源作为生产信号。
- 不应让 Agent 直接调用下单接口。
- 不应让 ML 模型替代硬规则和风控。
- 不应在未绑定参数版本的情况下比较回测结果。

### 10.2 兼容要求

- 现有 Web/App API 不破坏。
- 现有策略默认输出不因参数迁移发生非预期变化。
- 所有新增配置必须有默认值。
- 生产路径在外部数据源不可用时应返回降级状态，而不是 500。

## 13. 下一步建议

建议按以下顺序启动开发：

1. 先做 R-006、R-007、R-011：风险低、收益高、改动小。
2. 再做 R-002：统一数据源入口，降低后续策略误判。

该顺序可以在不改变现有策略行为的前提下，优先降低线上风险和维护成本。
