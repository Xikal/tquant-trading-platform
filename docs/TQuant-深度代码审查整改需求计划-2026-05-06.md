# TQuant 深度代码审查整改需求计划

生成日期：2026-05-06  
来源文档：`/Users/j/Downloads/TQuant-深度代码审查报告.html`  
适用范围：TQuant A 股短线做 T / 低吸选股平台

## 1. 总体结论

当前系统工程成熟度约为 `B+`，可以继续用于模拟盘、策略研究和内部验证。

在以下问题修复前，不建议扩大普通用户使用范围：

- 通知未配置时返回假成功。
- 全系统时间口径不统一。
- Android Release 存在明文 HTTP 风险。
- 低吸物化快照存在事务边界问题。
- 策略元数据仍存在多处真源。
- 模拟盘 API 错误语义不一致。

本计划按优先级分为：

- `P0/P1 阻断修复`
- `P1 工程一致性修复`
- `P2 可维护性与架构债务`
- `产品与 UX 改进`
- `测试验收与上线门槛`

## 2. P0/P1 阻断需求

| 编号 | 需求 | 实现方法 | 验收标准 |
|---|---|---|---|
| R0-1 | 通知未配置不能返回假成功 | 修改 `backend/app/services/agent_notification_service.py`。无飞书 webhook 且 Hermes 不可用时，`send_test()` 返回 `ok=false` 和 `NOTIFICATION_NOT_CONFIGURED`；`send_signal()` 只有真实发送成功才更新 `last_notified_at`、`notification_count` 和冷却时间。 | 未配置通知时不会进入 4 小时冷却；飞书/Hermes 失败能被前端、审计和日志明确识别。 |
| R0-2 | 全系统时间口径统一 | 新增或复用时间工具，明确 `beijing_now()`、`beijing_today()`、`utc_now()`；业务归档、日报、低吸快照使用北京时间；JWT 过期使用 aware UTC。 | 部署在 UTC 服务器时，归档、日报、登录过期不偏移。 |
| R0-3 | Android Release 禁止明文 HTTP | 检查 Android `main/release/debug` manifest；`usesCleartextTraffic=true` 只允许 debug；release 使用 `cleartextTrafficPermitted=false`。 | Release 包无法访问 HTTP 明文接口；发布检查脚本失败时阻断。 |
| R0-4 | 低吸物化重建不能提交外部事务 | 修改 `backend/app/services/low_buy/screening.py`，`_rebuild_materialized_snapshot(db)` 不再内部 `commit()`，由调用方控制事务。 | 单元测试中外层 rollback 可回滚重建结果。 |
| R0-5 | 策略元数据单一真源 | 后端 `/api/strategies/meta` 作为唯一真源；前端 fallback 由后端 seed 生成，不再手写；Playbook、App、回测预设全部使用同一套 metadata。 | 新增、隐藏、降级策略后，Web/App/回测入口一致。 |
| R0-6 | 模拟盘 API 错误语义统一 | 服务层区分 `LookupError -> 404`、`ValueError -> 400`、未知异常 -> 500；取消、查询、成交、撤单保持一致。 | 订单不存在时所有相关接口均返回 404；业务校验失败返回 400。 |
| R0-7 | 登录 token 过期时间修正 | `backend/app/services/auth_service.py` 中 JWT `iat/exp` 全部使用 UTC aware datetime；业务展示再转北京时间。 | 刷新页面和跨时区部署不提前掉登录。 |

## 3. P1 工程一致性需求

| 编号 | 需求 | 实现方法 | 验收标准 |
|---|---|---|---|
| R1-1 | 策略展示权限统一 | `/api/strategies/meta` 明确普通用户、研究权限、优化权限、admin 返回差异；hidden 策略普通用户永不可见，admin 仅 `include_hidden=true` 可见。 | 选股宝典、App、优先榜、预设不展示 hidden。 |
| R1-2 | 策略提升/降级校验 | `promote/demote` 必须从 seed + DB 合并后的 metadata 校验 `probe_status`、`visibility`、`enabled`，拒绝未知策略。 | `backtest_only`、`pending` 策略不能被绕过提升。 |
| R1-3 | Feature flag 热路径优化 | `list_feature_flags()` 不再每 60 秒全表扫描审计日志；审计信息移到设置页专用接口，或按 key 限定查询最新记录。 | 普通策略请求不触发审计表全量排序。 |
| R1-4 | 回测预设动态生成 | 快速体检、年度回顾、完整检验根据实时 metadata 动态生成，只包含 `core/auxiliary + visibility=full + enabled=true`。 | 禁用或降级策略不会继续进入默认预设。 |
| R1-5 | 前端策略标签一致 | Playbook 当前策略名称从当前 tabs/API metadata 获取，不再从硬编码列表读取。 | 后端改名后按钮和详情文案一致。 |

## 4. P2 可维护性与架构债务

| 编号 | 需求 | 实现方法 | 验收标准 |
|---|---|---|---|
| R2-1 | 量化评分魔法数治理 | 将 `backend/app/services/quant_engine_scoring.py` 中阈值提取为常量；中期做版本化配置并记录 `engine_version`。 | 每次信号结果可追溯使用的评分版本。 |
| R2-2 | Alembic 替代 schema_compat | 新增字段、索引、回填全部走 Alembic；`schema_compat.py` 仅保留启动兼容检查，逐步删除写表逻辑。 | 新环境只跑 Alembic 即可初始化。 |
| R2-3 | 后台任务拆出 Web 进程 | 低吸扫描、归档、Hermes/飞书日报、回测任务迁出 FastAPI lifespan，改为独立 worker/leader。 | Web worker 不再执行全量扫描或归档。 |
| R2-4 | 指标算法对齐主流口径 | EMA/MACD 增加同花顺/Wind 风格基准测试；明确初始化方式和误差容忍。 | 指标测试覆盖 RSI、MACD、MA、ATR、VWAP。 |
| R2-5 | 全局单例改为依赖注入 | AuthService、rate limiter、provider client 逐步改为 FastAPI Depends/factory。 | 测试可替换 mock，不依赖全局状态。 |
| R2-6 | 多 worker 限流准确性 | 短期使用 Nginx `limit_req`；中期引入 Redis/SQLite 限流后端，避免进程内 deque。 | Gunicorn 4 worker 下限流仍准确。 |

## 5. 产品与 UX 改进需求

| 编号 | 需求 | 实现方法 | 验收标准 |
|---|---|---|---|
| U1 | 实时监控操作更直观 | 自选/持仓卡片突出“现在怎么做、为什么、错了怎么办”；按钮只保留高频动作。 | 非专业用户 10 秒内能理解操作建议。 |
| U2 | 优先榜显示数据状态 | 显示快照日期、是否 stale、数据质量、候选池覆盖数；不要把样本不足显示成 0%。 | 数据不足和策略失败能区分。 |
| U3 | 策略卡片补样本信息 | 每个策略展示近 24 月样本数、真实成交数、1/2/3/4/5 日胜率和收益。 | 用户能判断策略可信度。 |
| U4 | 飞书卡片结构化 | 日报、优先榜、风险提醒使用卡片模板，包含信号、风险、下一步动作。 | 飞书内容短、可读、无敏感信息。 |
| U5 | 移动端刷新与离线态 | App 下拉刷新、空状态、错误态、离线缓存提示统一。 | 断网或 401/500 不白屏。 |

## 6. 测试计划

| 测试编号 | 覆盖需求 | 测试方法 |
|---|---|---|
| T-1 | 通知真实失败 | mock 飞书/Hermes 未配置、失败、成功三种路径。 |
| T-2 | 时间口径 | 固定 UTC/北京时间，验证日报、归档、JWT 过期。 |
| T-3 | Android Release 安全 | 脚本检查 manifest merge 结果不允许 cleartext。 |
| T-4 | 事务边界 | 外部事务 rollback 后物化快照不可见。 |
| T-5 | 策略元数据真源 | 后端改 seed 后生成前端 fallback，CI diff 校验。 |
| T-6 | 模拟盘错误码 | 订单不存在、资金不足、T+1 不足、非法价格。 |
| T-7 | 回归测试 | 执行 `make qa`、`make ui-smoke`、`make prod-preflight`。 |
| T-8 | 云端验收 | 验证 `/healthz`、`/readyz`、前端首屏、Hermes/飞书只读链路。 |

## 7. 实施顺序

1. 第一批：完成 R0-1 到 R0-7，全部属于上线阻断或高风险一致性问题。
2. 第二批：完成 R1-1 到 R1-5，保证策略入口、权限、预设、前端展示不漂移。
3. 第三批：完成 U1 到 U5，提升普通用户可用性和飞书可读性。
4. 第四批：推进 R2-1 到 R2-6，作为架构债务专项，不建议和 P0 修复混在一个发布里。
5. 第五批：完整回归、云端预检、生成变更报告后再部署。

## 8. 上线门槛

必须满足以下条件：

- P0/P1 全部修复并有自动化测试。
- 通知未配置不会假成功。
- 北京时间与 JWT UTC 口径明确。
- Release APK 不允许明文 HTTP。
- 策略元数据前后端一致。
- 模拟盘错误语义稳定。
- `make qa`、前端构建、核心 API 冒烟通过。
- 云端 `/healthz`、`/readyz`、前端首屏、登录刷新恢复正常。

## 9. 暂不纳入本轮的长期项

以下方向合理，但不应阻塞本轮整改：

- 机器学习模型接入。
- 真实券商交易。
- 多数据源高可用。
- Prometheus/Grafana 全量监控。
- 完整 Agent 质量评分体系。
- 全量参数版本化配置平台。

## 10. 执行建议

建议先创建 `p0-hardening` 分支，只做 R0/R1。

原因：

- P0/P1 是上线风险，修复范围明确。
- R2 架构重构影响面大，适合单独排期。
- 产品 UX 可以在安全和一致性修复稳定后并行推进。
