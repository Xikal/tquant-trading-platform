# 盘中节奏增强与基础设施演进需求文档（2026-05-25）

本文档将当前审查结论中“值得强化的功能”与“日后发展方向”细化为可执行需求。
目标不是改写现有系统，而是在不破坏原有策略结果、交易语义和页面结构的前提下，把盘中反馈、复盘、实时读取、计算内核和运维基础设施补齐。

## 1. 文档目标

1. 把盘中监控从“分散指标展示”升级为“一条可执行的盘中 pulse”。
2. 把午盘/收盘复盘从后台任务升级为实时监控界面的盘中决策信息，作为下午与次日动作约束的主入口。
3. 把实时行情读取从单条缓存读升级为批量读 + 数据质量聚合。
4. 把 Rust 计算内核从可选增强升级为可验证、可发布、可回退、可默认进入生产主路径的计算内核。
5. 把数据库迁移和运行时配置持久化从“能用”升级为“原子、可审计、可修复”。

## 2. 适用范围

- 前端：`monitor`、`market emotion`、`paper trading`、`settings`
- 后端：`market`、`paper`、`settings`、`db admin`
- Go：`bff-gateway`、`market-read-service`、`scan-worker`
- Rust：`tquant-rs`
- 运维：CI、Docker、发布镜像、运行手册

## 3. 非目标

1. 不改动核心策略语义。
2. 不改变低吸、风控、回测、模拟盘账本的结果口径。
3. 不让 Go/Rust 绕过验收直接进入生产；但验收完成后，Go/Rust 必须接入正式生产主路径，而不是长期停留在 shadow 或可选增强。
4. 不新增无依据的预测因子或交易建议。

## 4. 需求总览

| 需求 | 优先级 | 目标 |
|---|---|---|
| 盘中 pulse 聚合 | P1 | 把市场宽度、龙头强度、情绪温度、小时快照合成一条可执行摘要 |
| 实时监控复盘展示 | P1 | 把午盘/收盘复盘直接带进实时监控主界面 |
| Go 服务生产化 | P1 | BFF 聚合、行情批量读、扫描任务都进入生产主路径，并保留可观测回退 |
| Rust 内核生产化 | P1/P2 | 补齐核心指标、形成可发布 wheel，并接入生产计算主路径 |
| 迁移与设置原子化 | P1/P2 | 数据迁移和 runtime 持久化可回滚、可审计、可修复 |

## 5. 需求一：盘中 pulse 聚合

### 5.1 目标

把 `hourly_all_market_snapshot`、市场宽度、龙头强度、情绪温度合成一条盘中 pulse，作为实时监控页和市场情绪页的第一层决策入口。

### 5.2 业务场景

- 交易时段内，每隔一个小时需要快速判断“市场是强、弱、分歧还是退潮”。
- 用户不希望先读多个卡片再自行拼结论。
- 当数据缺失时，页面要给出可理解的降级状态，而不是空白或误导性鲜亮结果。

### 5.3 功能要求

1. 盘中 pulse 必须包含以下字段：
   - 更新时间
   - 数据质量状态
   - 市场宽度摘要
   - 龙头强度摘要
   - 情绪温度摘要
   - 小时快照摘要
   - 归纳后的 pulse 等级或文本结论
2. pulse 必须支持手动刷新。
3. pulse 必须支持只读展示，不得触发交易、下单或策略写入。
4. pulse 在部分源数据缺失时必须返回 partial 结果，而不是整页失败。
5. pulse 应保持与现有监控页、情绪页的视觉层级一致，优先展示在页面上方。

### 5.4 数据与接口要求

- 后端要把小时快照、市场宽度、板块/龙头排行、情绪指标统一包装成一个可消费对象。
- 前端类型需要显式包含小时快照字段，不能只靠隐式字段透传。
- 数据质量至少分为：`fresh`、`stale`、`partial`、`unavailable`。
- 若小时快照超时或缺失，必须保留最近一次成功结果，并标注 stale。

### 5.5 页面要求

- 监控页首屏应出现 pulse 条。
- 市场情绪页应能从 pulse 中看到“情绪温度 + 龙头强度 + 数据质量”。
- 小屏下 pulse 需要自动换行，不得遮挡其他卡片。

### 5.6 验收标准

- 每个交易日固定窗口都能生成 pulse。
- pulse 缺一个来源时，页面仍能打开且能提示缺失来源。
- 页面上能直接看到“当前市场状态 + 是否可继续推进下午动作”。

### 5.7 建议测试

- 后端：小时快照到期测试、交易日/非交易日测试、部分源缺失测试。
- 前端：监控页和情绪页渲染测试、窄屏布局测试、stale badge 测试。

## 6. 需求二：实时监控复盘展示

### 6.1 目标

把全市场 `review_reports` 直接显示进实时监控页，让午盘复盘和收盘复盘成为下午与次日决策依据，而不是后台沉默生成的报表。复盘对象是整个 A 股市场，不是某个模拟盘账户；模拟盘可以继续提供账本、委托、成交、绩效明细和历史辅助入口，但复盘内容的主承载界面必须是实时监控。

### 6.2 业务场景

- 午盘后，用户在实时监控页需要马上知道下午是否应该降频、降仓、只延续已验证方向。
- 收盘后，用户在实时监控页需要看到归因、风险提示和次日计划。
- 实时监控页是盘中决策的第一入口，复盘结果不应藏在模拟盘、报表接口或后台任务里。
- 复盘内容必须围绕市场宽度、小时全市场快照、龙头强度、情绪温度和 data_quality，不得按模拟盘账户盈亏生成主结论。

### 6.3 功能要求

1. 实时监控页必须展示：
   - 今日复盘摘要
   - 午盘复盘
   - 收盘复盘
   - 风险提示
   - 建议动作
2. 复盘内容必须支持按 `midday` / `close` 分组展示。
3. 同一天存在两类复盘时，必须能同时看到，不得互相覆盖。
4. 午盘复盘的建议必须以“约束下午执行”为主，不得包装成放宽仓位的许可。
5. 收盘复盘的建议必须以“记录、归因、次日计划”为主，不得误导为盘中继续交易依据。

### 6.4 数据与接口要求

- `MarketReviewReport` / 监控 BFF 需要稳定返回 `review_reports`。
- 实时监控 BFF 或监控接口需要接入这些市场级报告，前端不能只在模拟盘详情里读取。
- `PaperPerformanceDashboard` / `PaperTradingPage` 只能保留复盘历史入口或跳转入口；如返回 `review_reports`，也必须是市场级历史，不得按模拟盘账户生成主复盘。
- 复盘报告至少包含：
  - `report_slot`
  - `overall_summary`
  - `strategy_highlights`
  - `risk_alerts`
  - `suggestion`
  - `generated_at`

### 6.5 页面要求

- 实时监控页首屏或 pulse 附近应给出“今日复盘状态”。
- 实时监控页应有独立复盘卡、折叠区或与 pulse 合并的复盘摘要。
- 模拟盘可提供历史入口或明细跳转，但主流程不能依赖用户进入模拟盘才能看到复盘。
- 若当天没有复盘，应显示空状态和下一次触发时间，而不是空白。

### 6.6 验收标准

- 午盘后实时监控页能看到午盘复盘。
- 收盘后实时监控页能看到收盘复盘。
- 同一天双 slot 结果可同时存在。

### 6.7 建议测试

- 后端：午盘与收盘共存测试、dashboard 返回稳定 shape 测试。
- 前端：实时监控页复盘展示测试、午盘/收盘文案测试、窄屏换行测试；模拟盘只验证历史入口或跳转入口。

## 7. 需求三：Go 服务生产化

### 7.1 目标

把 Go 从“旁路增强”升级为生产主路径能力：

- `bff-gateway` 承担 workspace/monitor 只读聚合主路径。
- `market-read-service` 承担实时行情、板块强弱、关键价位和快照读取主路径。
- `scan-worker` 承担定时扫描、候选排序、结果对比和 snapshot 写入主路径。

三个 Go 服务都必须通过性能、兼容、安全和回退验收后进入生产，而不是长期停留在 shadow、影子扫描或可选增强状态。

### 7.2 业务场景

- 监控页、自选扫描、板块排行和关键价位告警会同时请求大量标的。
- 单条循环读取会放大连接、缓存和数据库压力。
- 用户看到的实时数据必须区分 fresh/stale/partial/unavailable。
- workspace 聚合和扫描任务需要稳定的超时、partial response、内部鉴权和回退口径。

### 7.3 功能要求

1. `market-read-service` 提供批量读取接口，至少覆盖：
   - quote batch
   - sector relative strength
   - key levels snapshot
   - intraday latest batch
2. `bff-gateway` 需要覆盖 workspace/monitor 聚合读取，支持超时、缓存、partial response、字段兼容和内部 token。
3. `scan-worker` 需要覆盖生产扫描任务，输出候选排序、差异对比、snapshot 写入和启用/回退状态。
4. 批量接口必须返回数据质量聚合结果。
5. 顶层质量不能只看“有没有值”，必须能反映 stale 与 partial。
6. 失败时必须返回可消费的 partial response，不得因为个别标的失败拖垮整批请求。
7. 读取路径不得在 symbol 循环中反复创建连接或重复拉取相同缓存。
8. 验收完成后，实时监控页、市场情绪页、选股相关读路径、workspace 聚合和扫描任务必须优先走 Go 服务；Python 保留 fallback 和业务真源，不再把 Go 长期停在 shadow 状态。

### 7.4 性能要求

- 批量读取要按 symbol 数量做性能基线。
- BFF 聚合要按 workspace payload 和并发请求做性能基线。
- scan-worker 要按全市场扫描规模、候选数量和写入耗时做性能基线。
- 需要建立真实批量 benchmark，而不是只测小规模缓存命中。
- 500、1000 symbol 是最低验证规模。

### 7.5 接口兼容要求

- 现有调用方不能因为接口升级而断裂。
- 如需改变字段结构，必须提供兼容层或版本化接口。

### 7.6 验收标准

- Go `bff-gateway` 能稳定支撑 workspace/monitor 聚合主路径。
- Go `market-read-service` 能稳定支撑监控页与排行页读取主路径。
- Go `scan-worker` 能稳定支撑全市场扫描和 snapshot 写入主路径。
- 数据质量字段能正确反映 stale / partial。
- benchmark 结果进入 CI 或发布门禁。
- 生产环境配置 Go 服务后，监控/情绪/选股/workspace/扫描请求默认进入 Go 主路径；关闭 Go 开关后能完整回退 Python。

### 7.7 建议测试

- 批量 symbol 测试。
- Redis 缓存命中 / MySQL fallback 测试。
- 全 stale / 部分 stale / 全 fresh 三种质量聚合测试。
- 连接复用与调用次数测试。
- BFF partial response、超时和字段兼容测试。
- scan-worker 排序一致性、snapshot 写入和回退测试。

## 8. 需求四：Rust 内核生产化

### 8.1 目标

把 Rust 从“可选加速”推进到“可发布、可默认接入生产计算主路径的计算内核”，并补齐核心指标：`RSI`、`VWAP`、`RankIC`，同时保留 `ATR`、`rolling`、`max drawdown`。

### 8.2 业务场景

- 回测、因子实验室、性能评估、风险归因都依赖高频计算。
- Rust 的价值不是替代 Python 业务语义，而是稳定承担计算热点。

### 8.3 功能要求

1. Rust 需要实现并暴露：
   - `ATR`
   - `RSI`
   - `VWAP`
   - rolling window
   - max drawdown
   - RankIC
2. Python wrapper 需要明确处理 warmup `None`，不得因为包装层把可用数据回退成不可用。
3. fallback 逻辑必须保留，Rust 不可用时必须继续运行 Python 实现。
4. wheel 必须作为镜像产物或发布产物的一部分，不得依赖运行时现编译。
5. 验收完成后，回测、因子实验室、性能评估和风险归因中的对应计算热点必须优先调用 Rust 内核；Python 保留 fallback，但不能作为已迁移指标的默认主路径。

### 8.4 发布要求

- `cargo test`、wheel import、Python parity benchmark 必须进入发布门禁。
- `rust_finance_math_enabled` 在验收前作为受控开关；验收完成并进入发布镜像后，应在生产配置中默认启用，同时保留一键关闭回退 Python 的能力。

### 8.5 验收标准

- 指标结果与 Python reference 在阈值内一致。
- wheel 在目标镜像中可直接导入。
- release benchmark 达到预设速度门槛。
- 生产环境启用后，对应指标默认走 Rust，日志和 metrics 能证明实际命中 Rust 主路径。

### 8.6 建议测试

- 单元测试：边界输入、空输入、warmup 区间、长序列输入。
- parity 测试：Rust 与 Python 输出误差阈值。
- 集成测试：容器内导入、镜像内发布、fallback 可用性。

## 9. 需求五：数据库迁移与 settings 持久化原子化

### 9.1 目标

把数据库迁移和运行时配置持久化从“能写”升级为“可回滚、可审计、可修复”。

### 9.2 数据库迁移要求

1. 迁移接口必须明确 scope：
   - 要么是全量迁移
   - 要么是明确命名的局部物化数据迁移
2. 不得把“部分表迁移”包装成“全库迁移”。
3. 中途失败时必须可回滚，不能留下半成品目标库。
4. `overwrite` 行为必须可审计，必须明确清空了哪些表、跳过了哪些表。

### 9.3 settings 持久化要求

1. 数据库提交和 runtime 文件写入必须形成一致性语义。
2. 文件写入失败时，不能留下数据库已更新而运行时文件未更新的分叉状态。
3. `runtime.env` 的写入必须支持原子替换或补偿恢复。
4. 敏感字段不能在持久化时被错误回显或混写。

### 9.4 验收标准

- 迁移失败时，目标库状态可预期。
- settings 保存失败时，数据库和 runtime 文件状态一致。
- 运维能从日志里看出失败点和恢复路径。

### 9.5 建议测试

- 迁移中途失败回滚测试。
- overwrite 清空范围测试。
- settings 文件写失败测试。
- runtime 文件与 DB 一致性测试。

## 10. 中长期发展方向

### 10.1 产品方向：交易日节奏闭环

目标：把实时监控作为交易日主入口，把情绪、选股、模拟盘、复盘串成一个连续工作流。

建议顺序：
1. 先把午盘/收盘反馈放到实时监控界面。
2. 再把策略医生、AI 结论和回放串进策略工作台。
3. 最后把研究、模拟、复盘收束到以实时监控为入口的统一日内节奏。

依赖：
- pulse 数据稳定。
- 复盘报告可见。
- 页面路由和移动端入口完整。

风险：
- 如果没有统一的节奏入口，用户会继续在多个页面之间手工拼结论。

### 10.2 数据方向：历史表与回放能力

目标：小时快照和复盘报告不能只保留 latest，需要可回放、可归因、可对比。

建议补充：
- 小时快照历史表
- 午盘/收盘复盘历史表
- 数据质量历史表
- 重要 pulse 事件表

价值：
- 能做盘中回放。
- 能支持策略医生和复盘对比。
- 能把“今天为什么强/弱”做成可查询证据。

### 10.3 架构方向：Go/Rust 验收进入 CI

目标：Go/Rust 的验收脚本和性能门禁必须在 CI 中自洽运行，不能依赖外部 `.venv` 或人工机器状态；通过验收后必须进入生产主路径。

建议补充：
- Go 三服务测试
- market benchmark
- Rust parity benchmark
- wheel import smoke
- 失败阈值门禁

价值：
- 避免 Go/Rust 长期停留在“看起来能用，实际上没接生产”的状态。
- 让 Go 承担 BFF 聚合、实时读和扫描任务主路径，让 Rust 承担计算热点主路径，同时保留可观测回滚。

### 10.4 性能方向：bundle 与样式收敛

目标：继续拆 `antd` / `echarts` 大 chunk，同时把页面级 style 收敛到共享组件和 tokens。

建议补充：
- 路由级懒加载继续细化
- 共享 `WorkspaceComponents` 扩展
- 旧页面级 CSS 逐步替换
- 窄屏截图回归测试纳入发布前检查

价值：
- 降低首屏体积。
- 降低样式漂移。
- 让桌面与移动端更一致。

### 10.5 运维方向：失败报告可观测化

目标：把迁移、settings、部分响应降级的失败报告做成结构化可观测输出。

建议补充：
- request_id
- source/module
- partial_errors
- fallback_reason
- recovery_hint

价值：
- 运维能快速分辨“真失败”还是“部分降级”。
- 减少看起来成功、实际半状态的事故。

## 11. 推荐推进顺序

1. 盘中 pulse 聚合
2. 实时监控复盘展示
3. Go 三服务生产化：BFF 聚合、行情批量读、扫描任务都接生产主路径
4. 数据库迁移与 settings 原子化
5. Rust 核心指标补齐、wheel 发布并接生产计算主路径
6. 历史表、CI 门禁、bundle / style 收敛

## 12. 最终验收口径

当且仅当以下条件都满足时，才可把这些增强项视为进入正式演进阶段：

1. 盘中 pulse 能稳定输出且前端可见。
2. 午盘/收盘复盘能在实时监控页直接被使用。
