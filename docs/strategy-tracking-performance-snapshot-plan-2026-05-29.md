# 策略跟踪性能优化开发文档

## 1. 背景

当前策略跟踪页面存在首屏加载慢、冷启动慢、接口耗时波动大的问题。已有短缓存可以改善重复访问，但不能从根本上解决冷路径实时计算慢的问题。

本次最终方案采用：

```text
后台预计算快照 + 首页读取单一快照接口 + 详情懒加载
```

本次不做大重构，不新增复杂读服务，不改变策略逻辑。

## 2. 目标

| 指标 | 当前问题 | 目标 |
| --- | --- | --- |
| 首页冷请求 | 秒级，极端情况下更慢 | 300-500ms |
| 首页 P95 | 波动较大 | <800ms |
| 首页热请求 | 已较快但依赖进程缓存 | 100-200ms |
| 冷启动已有快照 | 仍可能触发重算 | <1s |
| 首屏请求数 | 多接口并发 | 1 个主接口 |

核心目标不是追求单次热缓存更快，而是让页面从“偶尔很慢”变成“稳定可控”。

## 3. 开发边界

### 3.1 本次要做

1. 新增策略跟踪快照表。
2. 新增策略跟踪快照生成任务。
3. 策略跟踪首页接口改为读取快照。
4. 前端首页只请求一个主接口。
5. 股票详情、持有分析、走势图改为懒加载。
6. 增加数据更新时间、刷新中、快照过期状态。
7. 保留防未来函数字段和异常收益审计。

### 3.2 本次不做

1. 不新增复杂 Go 读服务。
2. 不把策略计算搬到前端。
3. 不修改策略买卖逻辑。
4. 不降低风控、审计和防未来函数要求。
5. 不依赖无限延长缓存 TTL 来掩盖性能问题。

## 4. 总体流程

```text
策略任务完成
  -> 后台生成策略跟踪快照
  -> 写入 strategy_tracking_snapshots
  -> 首页读取快照接口
  -> 用户打开股票详情后再加载明细数据
```

## 5. 数据表设计

新增表：

```text
strategy_tracking_snapshots
```

建议字段：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| id | bigserial / uuid | 主键 |
| snapshot_key | text | 快照唯一键 |
| as_of_date | date | 快照交易日 |
| range_days | integer | 统计周期 |
| strategy_key | text nullable | 策略标识，空值表示全部策略 |
| market_scope | text | 市场范围，例如 all / exclude_chinext_star |
| filter_hash | text | 筛选条件哈希 |
| data_version | text | 数据版本，用于缓存失效 |
| status | text | fresh / stale / building / failed |
| generated_at | timestamptz | 快照生成时间 |
| source_data_cutoff | timestamptz | 计算使用的数据截止时间 |
| payload_json | jsonb | 首页直接返回的数据 |
| metrics_json | jsonb | 生成耗时、样本数、异常数量等 |
| error_message | text nullable | 最近一次生成失败原因 |
| created_at | timestamptz | 创建时间 |
| updated_at | timestamptz | 更新时间 |

唯一约束建议：

```text
(snapshot_key)
```

索引建议：

```text
(as_of_date, range_days)
(strategy_key)
(market_scope)
(data_version)
(status)
```

## 6. 快照内容

`payload_json` 建议结构：

```json
{
  "summary": {},
  "items": [],
  "performance": {},
  "market_segments": [],
  "holding_summary": {},
  "shadow_observations": {},
  "audit": {}
}
```

每条 `items` 至少包含：

| 字段 | 说明 |
| --- | --- |
| symbol | 股票代码 |
| name | 股票名称 |
| sectors | 所属板块列表 |
| strategy_keys | 命中的策略列表 |
| recommend_date | 推荐日期 |
| signal_type | 信号类型 |
| signal_time | 信号生成时间 |
| data_cutoff_time | 信号使用的数据截止时间 |
| return_start_time | 后验收益计算起点 |
| support_price | 支撑位 |
| planned_buy_price | 计划买点 |
| stop_loss_price | 止损位 |
| target_price | 目标位 |
| max_gain_pct | 推荐后最高涨幅 |
| max_drawdown_pct | 推荐后最大回撤 |
| profit_type | 盈利类型，例如冲高止盈 / 趋势延续 / 未盈利 |
| failure_reason | 失败归因 |
| abnormal_return_flag | 是否异常收益 |

## 7. 后端改造

### 7.1 新增快照生成服务

建议新增服务：

```text
StrategyTrackingSnapshotBuilder
```

职责：

1. 调用现有策略跟踪计算逻辑。
2. 生成首页所需完整快照。
3. 写入 `strategy_tracking_snapshots`。
4. 记录生成耗时、样本数、异常收益数量。
5. 校验防未来函数字段。
6. 生成失败时保留旧快照。

### 7.2 新增快照读取接口

新增接口：

```http
GET /strategy-tracking/snapshot
```

请求参数建议：

| 参数 | 说明 |
| --- | --- |
| range_days | 统计周期，默认 30 |
| strategy_key | 策略筛选，可选 |
| exclude_chinext | 是否排除创业板 |
| exclude_star | 是否排除科创板 |
| limit | 首页返回数量 |

响应结构：

```json
{
  "status": "fresh",
  "stale": false,
  "generated_at": "2026-05-29T10:00:00+08:00",
  "source_data_cutoff": "2026-05-29T09:30:00+08:00",
  "data_version": "2026-05-29-default",
  "payload": {}
}
```

### 7.3 保留手动重建接口

仅管理员或内部调试使用：

```http
POST /strategy-tracking/snapshot/rebuild
```

用途：

1. 手动刷新快照。
2. 部署后预热默认快照。
3. 排查快照和实时计算差异。

## 8. 前端改造

策略跟踪首页改造：

1. 首屏只请求 `/strategy-tracking/snapshot`。
2. 首页直接展示快照中的 `summary`、`items`、`performance`、`market_segments`、`shadow_observations`。
3. 页面顶部展示 `generated_at` 和 `source_data_cutoff`。
4. 如果 `stale=true`，展示“数据刷新中”，但继续展示旧快照。
5. 股票详情抽屉打开后，再请求详情接口。
6. 持有时长分析、走势图、逐日表现全部懒加载。

详情懒加载内容：

1. 推荐日。
2. 支撑位。
3. 计划买点。
4. 止损位。
5. 目标位。
6. 实际最高点。
7. 实际最低点。
8. 最大涨幅。
9. 最大回撤。
10. 是否冲高回落。
11. 信号失效时间。

## 9. 快照刷新策略

触发快照生成的时机：

1. 每日策略任务完成后自动生成。
2. 行情数据刷新后自动生成。
3. 策略配置发生变化后自动生成。
4. 管理员手动刷新。
5. 服务启动后异步预热默认快照。

降级规则：

| 场景 | 处理方式 |
| --- | --- |
| 有新快照 | 返回新快照 |
| 新快照生成中 | 返回旧快照，标记 stale |
| 快照生成失败 | 返回旧快照，记录错误 |
| 没有任何快照 | 返回 empty/building 状态 |

## 10. 防未来函数要求

快照生成必须校验：

1. `data_cutoff_time <= signal_time`。
2. `return_start_time > signal_time`。
3. 推荐日前的数据只能用于生成信号。
4. 推荐日后的数据只能用于后验收益统计。
5. 最大涨幅、最大回撤、止损、冲高回落只能使用信号后的行情。
6. 异常高收益必须保留 `abnormal_return_flag`。

如果校验失败：

1. 不允许写入 `fresh` 快照。
2. 快照状态标记为 `failed`。
3. 页面继续使用上一版可用快照。
4. 后端记录审计日志。

## 11. 验收标准

### 11.1 功能验收

1. 首页只发起一个主接口请求。
2. 首页能展示推荐列表、策略统计、市场状态分层、Shadow 样本。
3. 股票详情点开后才加载明细。
4. 快照过期时页面仍可打开。
5. 快照生成失败不影响旧结果展示。
6. 异常收益仍会被标记。

### 11.2 性能验收

| 指标 | 验收目标 |
| --- | --- |
| 首页首屏 | 300-500ms |
| 首页 P95 | <800ms |
| 热请求 | 100-200ms |
| 冷启动已有快照 | <1s |
| 首屏主请求数 | 1 |

### 11.3 一致性验收

快照结果需要和原实时计算结果对齐：

1. 样本数一致。
2. 策略统计一致。
3. 最大涨幅一致。
4. 最大回撤一致。
5. 买点触达状态一致。
6. 止损状态一致。
7. 冲高回落标签一致。
8. 异常收益标记一致。

## 15. 最终结论

本次采用策略跟踪快照化方案。该方案改造范围可控，不改变策略逻辑，不降低风控要求，可以直接解决策略跟踪首页实时计算慢的问题。

预期收益：

1. 首页首屏提升约 6-15 倍。
2. P95 耗时下降约 70%-85%。
3. 数据库和 Python 实时计算压力下降约 70%-90%。
4. 用户感知从“卡顿等待”变成“基本秒开”。
