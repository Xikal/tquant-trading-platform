## 一、总体判断

### 1.1 当前项目整体成熟度

**综合评分: B+（约 78% 成熟度）**

TQuant 已从一个原型进化为一个具备真实交易辅助能力的中型系统。基础设施扎实（FastAPI + React + Capacitor + Docker），策略体系完整（12 策略 4 级治理），模拟盘闭环可用，Agent/Hermes 已接入且权限设计合理，部署链路（CI/CD + Docker + Nginx + Let's Encrypt）完整。

正确和做得好的部分远多于错误和遗漏。

### 1.2 是否已具备正式使用基础

**是，但带有以下前提条件**：

- 核心策略（首板回调、量能低吸）经过回测验证，通过 PBO 过拟合测试
- 模拟盘可以完成完整的下单→撮合→持仓→绩效闭环
- 用户鉴权体系完整（PBKDF2-SHA256 + JWT + httpOnly refresh cookie）
- Agent 权限分层清晰（read/write/notify/dangerous），审计记录完整
- HTTPS + HSTS + CSP + X-Frame-Options 安全头完整

**建议在以下 P0 项解决后再用于实盘**：

- 通知服务在未配置时的"假成功"bug（导致信号静默抑制）
- WebSocket 断线恢复和保活机制
- 时区处理统一化和硬编码修复
- mobile auth 的冗余刷新请求优化

### 1.3 最大的 5 个风险

| 序号 | 风险 | 严重性 | 影响 |
|------|------|--------|------|
| 1 | **通知未配置时返回 ok=True** — `agent_notification_service.py:74-75`，导致信号通知被误标记为"已发送"而遭受冷却期抑制 | High | 飞书/推送通知全部静默失败，用户收不到信号提醒 |

## 二、分模块分析

### 2.1 实时监控（Monitor）

**当前状态**: 功能闭环基本完整。市场全景（涨跌停家数、成交量比）、优先榜 Top 12（含信号等级和风险标记）、持仓做 T 信号扫描、自选股 CRUD 均已实现。使用 10 秒轮询刷新。

**主要问题**:

1. **Monitor 页 4 个操作按钮未简化** — Phase 3 方案要求简化为 2 个（同步数据 + 切换视图），当前仍为 4 个（同步行情、全量扫描、自选扫描、切换视图）。Risk: Low
2. **`useMonitorData` hook 中 `change_pct` 阈值硬编码** — 涨跌幅颜色带阈值 `>2%` 红、`<-2%` 绿、`>0` 浅红、`<0` 浅绿写在组件内。Risk: Low
3. **优先榜在市场数据量极少时（≤5 条）无降级提示** — 用户可能误以为"今天没有机会"，实际上是数据未加载完成。Risk: Low

**建议优化方案**:
- 合并 4 按钮为 2 按钮（同步数据 + 视图切换），其他操作放到二级菜单
- 优先榜增加数据源就绪状态提示："实时数据就绪（167 条信号）"或"仅展示缓存数据"
- 相关文件: `frontend/src/features/trading-workspace/MonitorPage.tsx`, `useMonitorData.ts`

**验收标准**:
- 普通用户看到 2 个主按钮而非 4 个
- 市场数据延迟超过 5 分钟时显示黄色提示条
- 优先榜上方显示数据就绪状态（XX 条策略信号已更新 / XX 秒前）

### 2.3 持仓管理（Holdings / Paper Trading）

**当前状态**: 模拟盘有完整的账户→持仓→委托→成交→绩效→风控→自动交易体系。持仓多批次管理（lots）、T+1 可用日期追踪、VWAP 确认、日内确认条均已实现。像素交易员（PixelTrader）动画增加趣味性。

**主要问题**:

1. **`paper/order.py:126` 硬编码 100 股为一手** — 科创板 200 股、不同板块手数不同，未做区分。Risk: Medium
2. **`cancel_order` 取消部分成交单时不更新 `filled_quantity`** — `paper/order.py:116-123`，取消 partial 状态委托后，已成交部分保留但委托表中的 filled_quantity 不体现。Risk: Low
3. **`get_order` 抛出 `LookupError` 而非 `HTTPException(404)`** — `paper/order.py:113`，导致前端收到 500 错误而非 404。Risk: Medium
4. **并发下单时的风控竞态** — `paper/order.py:144-150`，两个并发创建订单请求可能同时通过风控检查。Risk: Medium
5. **`_paper_archive_due` 使用 `datetime.now()` 比较北京时间 15:05** — `main.py:284-287`，UTC 服务器上永远不会触发。Risk: High
6. **纸笔归档的 `global` 变量无锁保护** — `main.py:58,197-206`，虽然是单线程循环，但代码结构不够防御性。Risk: Low

**建议优化方案**:
- 从 `InstrumentRule` 表读取每只股票的实际手数（已有该表结构）
- `cancel_order` 增加 `filled_quantity` 更新逻辑
- 统一异常处理 → HTTPException
- 风控检查时增加 `SELECT ... FOR UPDATE` 行锁或使用 SERIALIZABLE 隔离级别
- 所有时间比较改用 `beijing_now()`
- 相关文件: `backend/app/services/paper/order.py`, `backend/app/main.py:273-290`

**验收标准**:
- 科创板股票下单时手数默认 200
- cancel partial 订单后，`filled_quantity` 正确体现已成交股数
- 不存在 500 错误 → 都是明确的 HTTP 状态码
- Paper 归档在北京时间 15:05+ (UTC 7:05+) 正确触发

### 2.4 持仓做 T 信号

**当前状态**: 信号通过 `WatchlistSignalService` 合成（整合自选股 + 低吸信号 + 日内确认），自选信号快照 45 秒刷新一次。T+1 可用日期由 `watchlist_t1.py` 追踪。

**主要问题**:

1. **做 T 信号未区分正 T 和反 T** — `watchlist_signal_service.py` 目前只提供单一的 signal summary（信号等级 + 建议操作），但 A 股做 T 需要明确是"先买后卖"（正 T）还是"先卖后买"（反 T）。Risk: Medium

- 信号增加 `direction: "正T" | "反T" | "观望"` 字段
- 持仓面板增加止损价/止盈价的 inline 展示
- 自选刷新传入与 screener 相同的 db session
- 相关文件: `backend/app/services/watchlist_signal_service.py`, `frontend/src/features/trading-workspace/MonitorPage.tsx`

**验收标准**:
- 每一条做 T 信号明确标注正 T 或反 T
- 持仓做 T 面板展示"止损 ¥XX.XX / 止盈 ¥XX.XX"

### 2.6 Agent/Hermes 接入

**当前状态**: Agent 系统架构是项目中最成熟的部分之一。支持 8 种 provider 后端（MCP、LangGraph、OpenAI Agents、CrewAI、Pydantic AI、OpenClaw、Hermes、Custom HTTP），21 个工具注册，4 级权限控制（read/write/notify/dangerous），审计日志完整。Hermes 工作流编排（5 agents × 3 phases）已定义，通过 CLI 或 HTTP 两种方式执行。

**主要问题**:

1. **`agent_notification_service.py:74-75` 通知未配置时返回 ok=True** — 这是最高优先级的 bug。未配置 webhook 或 Hermes CLI 时，`send_test` 返回成功，导致 `send_signal` 增加通知计数和更新时间戳，信号被冷却期抑制。Risk: Critical
2. **Hermes CLI 每次通知都启动子进程** — `subprocess.run()` 启动开销 10-50ms，高频信号场景下性能不足。Risk: Medium
3. **`agent_providers/base.py:127` 审计日志记录完整参数** — 如果参数包含敏感数据（PII、具体持仓金额），会被直接写入审计表。Risk: Low
4. **`config.py:131-150` agent_token JSON 解析失败静默返回 `{}`** — 管理员不知道 token 配置无效。Risk: Low

**建议优化方案**:
- 修复通知"假成功" → 未配置时返回 `ok=False, message="未配置通知通道"`
- Hermes 改为 HTTP 长连接或至少进程池（`concurrent.futures.ProcessPoolExecutor`）
- 审计日志增加参数脱敏开关（`agent_audit_sanitize: bool = True`）
- Token 解析失败时记录 warning 日志
- 相关文件: `backend/app/services/agent_notification_service.py:59-78`, `backend/app/agent_providers/base.py:127-146`

**验收标准**:
- 未配置 webhook 时，`send_test` 返回 `ok=False`
- `send_signal` 在未配置时不增加通知计数
- 发送信号后，通知计数仅在真正发送成功后递增

### 2.8 App 更新机制

**当前状态**: Android APK 更新链完整 — 服务端从 JSON 读取版本信息 + 提供 APK 下载，客户端检查版本号 → 弹出更新卡片（区分强制/可选）→ Capacitor Browser 打开下载。iOS 暂无更新提示。

**主要问题**:

1. **`VITE_NATIVE_VERSION_CODE` 与 Android `versionCode` 无自动同步** — 构建时可能不一致，导致更新检查永远/永不触发。Risk: Medium
2. **启动时双重检查** — `useAppUpdate` 自身 useEffect 和 `useNativeRuntime` 回调都调用 `checkForUpdate()`。非有害但浪费。Risk: Low
3. **`usesCleartextTraffic="true"` 过于宽松** — AndroidManifest 允许所有 HTTP 明文流量。Risk: Low
4. **iOS 无更新提示路径** — 缺失 App Store 更新引导。Risk: Low
5. **APK manifest 文件路径硬编码** — `update_manifest.py` 使用 `BACKEND_DIR / "data" / "app_updates"` 固定路径，无法从 S3/云端拉取。Risk: Low

**建议优化方案**:
- `version_sync.py` 扩展为也同步 Android versionCode
- 合并重复的 checkForUpdate 调用
- 添加 `network_security_config.xml` 限定明文流量域
- iOS 增加 `appApi.checkIosUpdate()` 调用 App Store API（可选，P2）
- APK 路径支持环境变量覆盖 `APP_UPDATE_PATH`
- 相关文件: `frontend/src/mobile/useAppUpdate.ts`, `backend/app/services/app_mobile/update_manifest.py`, `frontend/android/app/src/main/AndroidManifest.xml`

**验收标准**:
- `version_sync.py --check` 验证 Android versionCode 一致性
- 应用启动时仅一次 update check 请求
- APK 更新清单路径可通过 `APP_UPDATE_PATH` 环境变量覆盖

### 2.9 后端架构与接口

**当前状态**: FastAPI 单体应用，mixin-based 服务层，SQLAlchemy ORM，Pydantic 序列化。路由分层清晰（api/routes/ → services/ → models/），Web/App 复用同一套后端接口。

**主要问题**:

1. **`_getattr__` 代理模式破坏 IDE 自动完成和子类覆盖语义** — `low_buy/service.py:72-73`，`LowBuyScreenerService` 是一个 façade，将所有方法调用代理到 `_LowBuyRuntime`。IDE 无法列出可用方法，子类覆盖的方法不会被 mixin 内部调用识别。Risk: Medium
2. **12-mixin 继承菱形** — `_LowBuyRuntime` 继承 12 个 mixin，MRO 依赖 C3 线性化正确但极易发生方法名冲突。Risk: Medium
3. **全局单例服务** — `MarketDataService()`、`AgentContextService()` 等作为模块级变量创建，无生命周期管理、无注入。Risk: Low
4. **`SessionLocal()` 在 WebSocket 和后台任务中绕过 FastAPI DI** — `strategy_stream.py:69`、`main.py:154` 中手动创建 session，与请求路径的 `get_db()` DI 不一致。Risk: Low
5. **后台任务的 leader election 使用 `fcntl.flock` 文件锁** — `main.py:368-385`，不可移植（Unix-only），`/tmp` 清理可能丢失锁。Risk: Low

**建议优化方案**:
- 低吸 façade 改用显式方法映射或 mypy 插件生成 stub
- mixin 继承树加文档注释 + 方法名前缀约定（如 `_screen_` → ScreeningMixin）
- 引入服务容器（简单 `dict` 或 `dependency-injector` 库）
- background tasks 统一通过 FastAPI 的 `BackgroundTasks` 或独立的 worker 进程
- leader election 改用数据库锁（`SELECT ... FOR UPDATE` 或 Redis `SETNX`）
- 相关文件: `backend/app/services/low_buy/service.py:29-73`, `backend/app/main.py:368-385`

**验收标准**:
- `LowBuyScreenerService` 实例在 IDE 中能看到所有公开方法
- mixin 继承树有文档说明各 mixin 的方法名前缀约定
- leader election 在 macOS 和 Linux 上均正常工作（数据库锁方案）

### 2.10 Web/App 接口一致性

**当前状态**: Web 和 App 共用同一套后端 API（FastAPI 路由），但 App 有专用的 `/api/app/*` 端点提供移动端优化的返回格式（精简字段、离线友好的缓存策略）。

**主要问题**:

1. **Bootstrap 端点与前端实际显示不一致** — `bootstrap.py` 返回 2 个 tabs，但移动端实际显示 4 个 tabs。Risk: Low
2. **App 端和 Web 端低吸详情格式不同但内容一致** — `app_mobile/low_buy.py` 为移动端做了精简（去掉部分分析字段），但 Web 端的 `screeners.py` 返回更完整的字段。这本身是合理的，但缺少文档说明哪些字段在两端通用。Risk: Low
3. **App 端持仓搜索使用 `findLatestPrice` 线性扫描** — `MobileApp.tsx:129-137`，每次搜索 O(N+M)。在持仓量较大（>200 条）时可能感知到延迟。Risk: Low

**建议优化方案**:
- Bootstrap 端点返回实际使用的 tabs 或从 features 常量动态生成
- 为移动端和 Web 端低吸接口差异编写文档
- 移动端价格查找预构建 `Map<symbol, price>`
- 相关文件: `backend/app/services/app_mobile/bootstrap.py`, `frontend/src/mobile/MobileApp.tsx:129-137`

**验收标准**:
- Bootstrap 返回的 tab 列表与前端实际渲染一致
- 持仓 >200 条时搜索延迟 <50ms

### 6.4 模拟盘如何验证胜率和收益

3. **模拟盘 vs 回测对比** — 同策略在模拟盘的实际收益与回测收益的偏差应 < 20%

5. **风险调整收益** — 不仅看总收益，还要看夏普比率和最大回撤。`paper/performance.py` 已有的 metrics 继续维护

### 6.5 策略自动化治理完善建议

当前自动治理（`strategy_governance.py`）已实现：
- 健康评分 < 35 → auto-pause ✅
- 健康评分 < 55 → auto-watch ✅
- PBO 过拟合测试 ✅
- 60 日滚动窗口绩效 ✅

建议增加：
- **最大连续亏损次数阈值** — 连续 5 笔亏损 → 自动暂停
- **最大浮动回撤** — 浮动回撤 > 15% → 自动降级
- **样本量下限严格化** — 研究策略在 60 日内 <20 个信号 → 不能升级到生产（当前阈值 20 已在代码中，持续执行）
- **数据质量门** — 如果标的的 daily bar 数据有 >10% 的缺失率，该策略对该标的的推荐自动降级

### 7.4 哪些能力必须由后端确定性逻辑完成

| 能力 | 为什么不能交 Agent |
|------|-------------------|
| **实际下单/撤单** | 资金安全 — 任何写操作必须通过后端风控 + 权限校验 |
| **策略信号计算** | 确定性 — 信号必须可复现、可验证、可回测 |
| **风控断路器** | 资金安全 — 硬止损/日亏损上限/连续亏损暂停，不容延误或遗漏 |
| **绩效计算** | 确定性和公平性 — 绩效必须是数学计算，不能由 LLM "估计" |
| **自动治理策略升级/降级** | 合规 — 策略上线/下架必须基于定量指标，不能依靠 Agent 判断 |
| **用户认证和权限** | 安全 — 绝对不能交给外部 Agent |
| **交易数据持久化** | 可靠性 — 数据不能由 Agent 处理后再存储 |

### 7.5 如何设计可替换 Agent 架构

当前架构已支持可替换性（8 种 provider），但还有改进空间：

1. **工具注册表的版本化和契约测试** — 每个 provider 切换时，自动运行 `agent_os_acceptance.py` 验证所有工具可用
2. **Provider fallback 链** — 主 provider (Hermes) 不可用时，自动降级到本地规则引擎（`agent_report_service.py` 已有规则版日报生成）
3. **结果质量评分** — 对 Agent 返回结果做结构化校验（必需字段存在、数值在合理范围、中文文本无乱码），不合格则拒绝
4. **Provider 性能基准** — 每个 provider 的 P95 响应时间记录（当前 timing.py 只记录 HTTP 请求，不记录 Agent 调用）

### 7.6 如何控制权限、审计、限流和安全边界

**当前已有的（做得好）**:

**建议增加**:
