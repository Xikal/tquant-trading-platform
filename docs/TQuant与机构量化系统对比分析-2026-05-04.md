# TQuant 与机构量化系统对比分析

**日期**: 2026-05-04
**分析对象**: TQuant（维斯量化），A 股短线低吸量化辅助平台
**对比基准**: 国内中型量化私募/自营交易台的典型系统
**分析依据**: 本项目 3 轮代码审查（Claude 82 项初查 → Codex 复核 → 最终裁定 27 项确认问题）+ 10 个 GitHub 开源量化项目对比

---

## 一、相同点

### 1.1 策略研究管线结构一致

TQuant 的策略管线（screening → candidate → metrics → prefilter → scoring → setup → signal）与机构系统的标准研究管线结构相同。机构通常也是"数据 → 因子计算 → 组合筛选 → 信号生成 → 风控过滤 → 执行"的流程。TQuant 的 12 策略、市场状态 8 分类、逐策略 override、动态仓位乘数的设计思路，与机构的多策略多状态框架在方法论上没有本质区别。

差异在于规模：机构通常有 50-500+ 个因子、20-100+ 个子策略，TQuant 目前 12 个策略、约 30 个因子（来自 candidate_metrics），规模大约是机构研究环境的 1/5 到 1/10。

### 1.2 模拟盘与回测闭环

TQuant 的模拟盘实现了完整的订单生命周期（create → pending → filled/rejected → settled）、T+1 规则、滑点模型、手续费计算、绩效归档，这与机构的 paper trading / simulation 环境功能对齐。机构在策略上线前也必须通过模拟盘验证，TQuant 的这一闭环设计方向正确。

### 1.3 多 Agent 架构方向

TQuant 采用的 Hermes + Agent Safe API + 10 个标准化工具 + 三级权限（read/write/notify）的架构，与 QuantDinger 的 Agent Gateway 设计高度一致，也符合 TradingAgents（65,000+ stars）的多角色分析→验证→决策范式。机构目前也在探索 LLM Agent 辅助研究，TQuant 在这一方向上甚至比部分传统机构走得更快。

### 1.4 数据源策略

TQuant 以 AkShare 为主、东方财富/Tushare 为辅的数据源策略，与中小型机构使用 Wind/Polygon/Bloomberg 的多源策略思路一致——核心是"主数据源 + 降级备用"。差异在于数据质量层级：机构使用付费商业数据（Wind 年费六位数起），TQuant 使用开源免费数据。

## 二、不同点（关键差距）

### 2.1 回测体系缺失

这是最大的差距。TQuant 当前没有独立的标准化回测框架。performance.py 中的绩效计算是基于历史快照的复盘统计（"信号发出后 N 日收益"），不是真正的事件驱动回测。机构系统的回测至少包括：

- 事件驱动回测引擎：模拟真实订单撮合，逐笔/逐分钟/逐日推进
- 前视偏差防护：Point-in-Time 数据（qlib 的 PIT 数据库正是为此设计）
- 交易成本模型：冲击成本、买卖价差、涨跌停不可交易
- 样本外验证：滚动窗口训练、时间序列交叉验证
- 绩效归因：Brinson 归因、因子归因、行业归因

TQuant 目前缺少以上全部。performance.py 的复盘统计可以给出"这个信号历史上看对不对"的粗略结论，但无法回答"如果真实执行这个策略，扣掉冲击成本和滑点后是否仍然盈利"。

### 2.2 因子体系单薄

机构系统的核心是因子库（Alpha Factory）。一个中型量化私募通常维护 200-500 个因子，分为：

- 价量因子（动量、反转、波动率、成交量、换手率）
- 基本面因子（估值、盈利、成长、质量）
- 另类因子（舆情、资金流、龙虎榜、分析师预期）
- 通过 IC/IR/Rank IC 评估因子有效性
- 因子正交化、去冗余、组合优化

TQuant 目前的因子计算集中在 candidate_metrics.py，约 30 个指标（均线距离、量比、回踩天数、分布风险分、突破距离等），且全部是围绕"低吸"场景设计的。没有基本面因子、没有标准化 IC 评估、没有因子组合优化。这限制了信号质量的天花板。

### 2.3 组合优化与执行算法缺失

机构系统从"信号"到"交易"之间有一段关键的优化层：

- 组合优化：均值-方差优化、风险平价、最大分散度、约束优化（行业上限、个股权重上限、换手率约束）
- 执行算法：TWAP/VWAP/POV 算法拆单、暗池路由、冰山订单
- 交易前风控：订单金额上限、单票仓位上限、日内亏损熔断

TQuant 目前是"信号→模拟盘订单"的直接映射。风控层（portfolio_guard.py）是建议性的而非执行性的——它输出警告但不阻止订单。仓位建议是静态百分比（15%-65%），而非基于当前持仓和风险预算的动态计算。

### 2.4 数据质量与可靠性

机构系统对数据质量有严格要求：

- 数据完整性校验（交易日历、复权因子、停牌处理）
- 数据延迟监控（实时行情延迟 < 100ms）
- 多源交叉验证（Wind vs Bloomberg vs 交易所原始数据）
- 历史数据版本管理（数据修正后可追溯）

TQuant 依赖 AkShare（开源社区维护），数据质量取决于上游。pool.py 中的 Stage 6 数据完整性检查（stock_count >= 4500）是好的实践，但缺少系统性的数据质量监控。分钟线通过 subprocess 构建 Python 脚本执行——这不只是安全问题，更可能在网络不稳时静默失败。

### 2.5 运维与监控体系

机构生产环境通常包括：

- 实时监控仪表盘（订单状态、持仓风险、系统延迟）
- 告警体系（PagerDuty/飞书/短信分级告警）
- 灾备与回滚（主备切换、快速回滚、数据恢复演练）
- 合规审计（每笔交易可追溯、监管报告自动生成）

TQuant 当前 Dockerfile 单 worker uvicorn 启动、无 /metrics 端点、无 Prometheus、无告警规则、无回滚机制。这是从"Pilot-ready"到"Production-ready"的核心差距。

### 2.6 测试与质量保证

机构对策略上线有严格的测试流程：

- 单元测试覆盖率 > 80%（核心模块 > 95%）
- 回归测试套件（每次策略修改重新运行全部历史回测）
- 压力测试（极端行情、流动性枯竭、数据断连）
- 演练环境（staging 环境完全复制生产）

TQuant 后端 34 个测试文件、前端 7 个测试文件（共 348 行），无覆盖率度量。模拟盘核心逻辑、量化引擎执行逻辑缺少单元测试。这是可立即改善的差距。

## 三、客观评价

### 3.1 项目整体完成度：65%-70%

已完成且质量较好的部分（70%-85%）：

- 策略管线架构（12 策略 × 4 层级 × 市场状态 × 风控）
- 模拟盘生命周期（订单、成交、持仓、T+1、绩效）
- Agent 接入体系（10 tools、三级权限、审计、Hermes 适配器）
- 数据库模型设计（强类型 ORM、参数化查询）
- 前端类型覆盖（TypeScript 全量类型定义）
- API 路由组织（RESTful、service/repository 分层）
- 文档体系（39 份 markdown、约 23,000 行）

部分完成的部分（40%-60%）：

- 回测体系（仅有复盘统计，无事件驱动回测）
- 因子体系（约 30 个低吸相关指标，无标准化评估）
- 安全加固（Feishu 空 token 绕过、Docker root、subprocess 注入、单 token）
- 部署运维（单 worker、无监控、无回滚）
- 移动端 App（功能完整但代码单体化严重）

基本缺失的部分（<20%）：

- 组合优化与执行算法
- 数据质量监控体系
- 生产级告警与灾备
- 机构级回测框架
- 绩效归因体系

### 3.2 与机构的定位差异

TQuant 与机构量化系统有一个本质差异：TQuant 是"决策辅助工具"，机构系统是"自动交易系统"。

这个差异不是缺陷，而是定位不同。TQuant 的目标是帮助个人交易者做出更好的决策：选股、做 T、仓位建议、模拟验证。机构的系统是无人值守的自动交易：策略产生信号 → 自动执行 → 自动风控 → 自动结算。

基于这个定位，TQuant 的完成度评估应调整为 75%-80%（如果目标是"个人量化决策辅助"），而不是按"机构自动交易系统"标准评估。

### 3.3 代码质量评级：B+

在开源量化项目中处于中上水平。FastAPI 强类型、SQLAlchemy 参数化查询、四层分离（service/repository/schema/model）、Agent 安全模型完备。扣分项：超 800 行的单体文件有 6 个、部分函数过深嵌套、重复逻辑未提取。

### 3.4 架构评级：B+

策略管线分层清晰、Agent Gateway 设计合理、数据源多路降级方向正确。扣分项：回测与生产环境未分离、无独立研究环境、测试基础设施薄弱。

## 四、专业建议

### 4.1 短期（1-2 个月）：补齐安全与运维底线

按照最终裁定中的 P0-P1 执行：安全 5 项修复、gunicorn 多 worker、Prometheus 监控、CI 覆盖率门禁。这些是"个人量化系统可以容忍，但真正用于资金管理不能没有"的底线。

### 4.2 中期（3-6 个月）：建立研究闭环

参考 qlib（41,000+ stars，微软）的设计，建立独立的离线研究环境。核心是：在修改策略参数之前，必须在独立回测环境中验证。当前"改代码 → 看快照统计"的迭代方式太粗糙。具体路径：

1. 搭建 qlib 离线环境，从 TQuant DB 同步数据
2. 对 3 个 AUXILIARY 策略执行标准化事件驱动回测（IC/IR/Sharpe/MaxDD/胜率/盈亏比）
3. 建立"策略修改 → 样本外验证 → 绩效归因 → 决策"的标准流程
4. 只有通过验证的策略参数变更才能推到生产环境

### 4.3 长期（6-12 个月）：因子体系扩容

当前 30 个指标集中在"低吸场景"。建议从三个方向扩展：

- 基本面因子：通过 OpenBB adapter 或直接接入东方财富基本面数据，增加 PE/PB/ROE/营收增速/利润增速等因子
- 资金流因子：主力净流入、大单中单单分布、北向资金持仓变化
- 情绪因子：涨停家数变化率、炸板率趋势、连板高度分布、板块轮动速度

评估方法：对新增因子做 IC 分析（月度 IC 均值、IC_IR），只有 IC > 0.02 且显著的因子才进入策略。

### 4.4 关于机构化的诚实判断

以目前的状态，TQuant 距离"接外部资金管理"还有相当距离。主要差距不是代码量（47K 行 Python 已经足够），而是：

1. 没有独立的回测验证闭环（这是最重要的一个）
2. 没有实盘交易接口（目前仅模拟盘）
3. 没有合规审计体系（资金管理的法律底线）
4. 没有灾备和业务连续性方案

但如果定位是"个人量化交易决策辅助系统"，TQuant 已经非常出色——12 策略多层级信号体系、模拟盘验证、Agent 接入、移动端 App，这些组合起来在开源中文量化项目中属于第一梯队。

### 4.5 最值得骄傲的三个设计

1. **策略管线中的 progressive filtering**：common_prefilter → strategy_prefilter → scoring → execution_ready → signal_resolution，五层逐步收紧，既保证了候选质量又避免了过度过滤。这是优秀的量化工程实践。

2. **Agent Safe API 的安全模型**：read/write/notify 三级权限 + 默认禁用 write + paper-only + 审计日志。在 2026 年 Agent 安全普遍被忽视的环境下，这个设计超前于大多数开源项目。

3. **市场状态的逐策略 override**：8 类市场状态 × 12 策略 = 96 种策略-状态组合，每种都有独立的仓位乘数、评分调整、信号约束。这种细粒度控制在机构系统中也是先进的。

这三个设计如果将来扩展到更多策略和更多市场，将成为 TQuant 的核心技术壁垒。

**最终建议**：坚持"个人量化决策辅助"的定位，不要为了"机构化"而偏离方向。先把回测闭环补齐（P1），再把因子体系扩展（P2），让 12 个策略的每一个都有经过标准化回测验证的绩效数据。一个策略信号扎实、回测透明、Agent 友好的个人量化平台，比一个"看起来像机构但策略未经验证"的系统有价值得多。
