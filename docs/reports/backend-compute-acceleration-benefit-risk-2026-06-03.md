# 第二个后端加速计划收益与风险整理

状态：决策参考
适用范围：`docs/superpowers/plans/2026-06-03-backend-compute-acceleration-final.md`
参考审查：`docs/reports/backend-compute-acceleration-landable-scope-2026-06-03.md`
最后核验日期：2026-06-03
结论：这份计划的核心价值不是“重写后端”，而是把已有 Rust、Go、DuckDB、Redis、RuntimeTask 能力接到热路径。确定可做的部分收益明确、风险可控；并行化部分潜在收益最大，但也是最容易破坏策略口径的部分，必须先做小样本 parity spike。

## 总体判断

| 模块 | 预期收益 | 主要风险 | 建议 |
|---|---|---|---|
| M0 基线测量 | 给后续优化提供真实对比，避免凭感觉优化 | 数据采集不完整，导致收益无法归因 | 必须先做 |
| K1 Rust 复用 | 降低指标计算耗时，尤其全市场扫描、回测、因子计算 | Rust/Python 浮点差异、fallback 行为不一致 | 第一优先级，逐文件接入 |
| K2 I/O 与缓存治理 | 降低接口 p95、减少 MySQL 回退、减少外部源阻塞 | 缓存口径漏标的、陈旧数据误用、Go fallback 字段不一致 | 第一优先级，配合守卫 |
| K3 全市场扫描并行化 | 潜在最大墙钟收益，适合 5000 标的 × 多策略 | 排序、合并、partial、取消恢复破坏结果一致性 | 先 spike，不直接生产化 |
| K4 派生指标缓存 | 重复请求和重复计算明显降耗 | 缓存 key 不稳、版本失效遗漏、内存膨胀 | 局部试点 |
| K5 观测与预算门 | 防止优化回退，定位 fallback 和尾延迟 | CI 过度阻塞、云端指标波动误报 | 先烟测，稳定后强阻塞 |

## 1. M0 基线测量与口径冻结

### 收益

- 建立优化前的真实基线，后续能量化 Rust 命中率、Redis 命中率、BFF timeout、接口 p95、扫描墙钟、24M 回测墙钟。
- 固化 PF、平均单笔、max5、max10、最大回撤等策略关键口径，避免“跑快了但结果变了”。
- 让后续每批改动都有回滚判断依据。

### 风险

- 如果基线缺少云端真实数据，后续收益可能只能做局部证明。
- `/metrics` 和性能脚本可能反映的是当前部署状态，不一定代表本地代码改动后的效果。

### 风险控制

- 报告中明确区分“本地基线”“云端基线”“无法测量项”。
- 每批改动前后使用同一套命令、同一数据范围、同一时间窗口对比。

### 建议

必须先做。没有基线就不要进入 Rust 替换或并行化。

## 2. K1 Rust 复用接入

### 收益

- 已有 Rust 11 个函数可复用，不需要新语言或新框架。
- 对全市场扫描、24M 回测、指标计算、因子 IC、最大回撤这类重复计算路径收益最高。
- 通过统一 `finance/rust_math.py` API，可避免散点调用，后续维护和回退更简单。
- `rust_finance_math_enabled=False` 可作为应急回退，生产风险低于直接替换算法。

### 风险

- Rust 与 Python fallback 对 NaN、None、短窗口、样本标准差、Wilder 平滑等边界处理可能不完全一致。
- 浮点误差可能影响阈值边界附近的信号或排序。
- 一次性替换多个文件，出错后很难定位。
- Rust 模块在镜像或部署环境中加载失败，会导致实际仍走 Python fallback。

### 风险控制

- 先补统一 API 和 parity 测试，再替换业务调用。
- 每个热路径文件替换前保存旧输出 golden，替换后断言一致。
- 按 `atr_metrics`、`candidate_metrics`、`factor_functions`、`backtest/analyzer`、`analytics/report_queries` 等逐文件推进。
- `/metrics` 监控 `rust_math_hits/fallbacks/errors/disabled`，fallback 异常突增要告警。

### 建议

第一优先级实施。收益明确，风险可以通过 parity 和 golden 控住。

## 3. K2 I/O 与缓存治理

### 收益

- mysqlclient 优先可降低 MySQL driver 层开销，已具备 PyMySQL fallback。
- 行情缓存覆盖扩大后，可减少外部行情源调用和 MySQL 回退，改善 `market_pulse`、优先榜、监控页体感。
- BFF / Go market-read fallback 补齐后，接口慢源不会直接拖垮主链路。
- N+1 查询上界测试能防止热接口随着功能增加逐步劣化。

### 风险

- 缓存预热集合不准，会造成热页面仍 miss，或者预热过大浪费 provider 调用。
- 陈旧行情如果没有明确 `stale` 标记，可能被前端或策略误读。
- Go 返回字段与 Python fallback 不完全一致，会造成 BFF schema mismatch 或 UI 降级。
- 连接池参数盲目调大可能把 MySQL 压垮。

### 风险控制

- 缓存目标集合只加真实热需求：自选、优先榜、纸面持仓、监控板块成员、策略追踪需要的标的。
- 所有 fallback 数据保留 `data_quality`、`source_quality`、`is_stale`。
- Go/BFF adapter 增加成功、失败、schema mismatch、部分缺 symbol 测试。
- 连接池参数按 worker 角色复核，不用“越大越好”。

### 建议

第一优先级实施。当前已有代码基础，主要是补覆盖、补测试、补观测。

## 4. K3 全市场扫描并行化

### 收益

- 潜在墙钟收益最大，尤其适合全市场 5000 标的、多策略、多日期扫描。
- 可以把重计算从 Web 请求线程移到 RuntimeTask worker，避免前端等待和请求阻塞。
- 任务分片后具备取消、重试、恢复、进度上报能力。

### 风险

- 并行合并顺序不稳定，可能改变优先榜排序。
- 分片后跨标的、跨策略、跨日期的约束可能被破坏。
- partial 分片失败如果处理不严，可能产生“看似完整但实际缺数据”的结果。
- 进程池和 worker 并发如果不受控，可能抢占 Web CPU 或压垮 DB。
- 这个模块涉及生产候选、物化结果和策略口径，风险高于 Rust 单函数替换。

### 风险控制

- 先做 spike：单策略、固定小 symbol 集，串行 vs 并行结果完全一致。
- 合并逻辑必须稳定排序，所有缺片显式 `partial/no_data/blocked`。
- 不在并行路径中重写策略规则，只并行安全的数据准备或独立计算片段。
- worker 并发由配置控制，不与 Web 共享 CPU。

### 建议

暂不直接生产落地。先做专项 spike，通过后再纳入开发计划。

## 5. 24M 回测并行化

### 收益

- 如果做对，24M 报告耗时可能明显下降。
- 可以把历史数据准备、分策略前置计算、归因聚合卸载到 worker 或 DuckDB。

### 风险

- `portfolio_backtest_metrics` 是组合唯一事实源，max5/max10、同票冷却、同板块、弱市、退潮等约束是跨时间连续规则。
- 按月份或日期分片后再聚合，容易破坏组合状态和冷却逻辑。
- 回测结果一旦漂移，会直接影响策略判断和生产准入信任。

### 风险控制

- 不并行实现 `portfolio_backtest_metrics`。
- 只允许并行前置数据准备，最终组合指标仍走唯一事实源。
- 对成交数、PF、平均单笔、max5、max10、最大回撤做 golden。

### 建议

后置。收益大，但风险也大，不能和 K1/K2 混在一个批次。

## 6. K4 派生指标缓存

### 收益

- 对均线、ATR、滚动分位、板块强度、相对强度这类重复计算有直接收益。
- 二次请求、同日重复扫描、策略追踪刷新都能减少重复计算。
- 缓存命中率可以通过 `/metrics` 可视化。

### 风险

- 缓存 key 如果不包含参数和版本，会读到错误结果。
- 算法变更后不失效，会造成历史口径与当前口径混用。
- 对实时或时间敏感对象缓存，可能造成陈旧信号。
- 缓存过大可能增加内存压力。

### 风险控制

- key 固定为 `indicator|symbol|trade_date|params_hash|version`。
- 版本变更必须 miss。
- 只缓存只读、纯函数、可复现派生指标。
- 设置 maxsize/TTL，并暴露 hits/misses/size。

### 建议

作为 P1 局部试点，不要全仓铺开。

## 7. K5 观测与守卫

### 收益

- 能持续监控 Rust fallback、缓存命中、N+1、worker 耗时、接口 p95。
- 防止未来改动把优化成果回退。
- 让性能问题从“用户感觉慢”变成可定位指标。

### 风险

- 如果把不稳定云端 p95 直接做 CI 强阻塞，容易误报。
- metrics 过多但没有阈值和解释，会降低可读性。
- 性能脚本如果依赖外部服务，CI 稳定性会下降。

### 风险控制

- 初期做 smoke/report，不直接强阻塞。
- 只对稳定、本地可复现的预算做 CI 强门。
- 云端 p95 用巡检报告或告警，不作为普通 PR 的唯一阻断。

### 建议

必须做，但分阶段：先观测，再预算，再 CI 强阻塞。

## 推荐执行顺序

1. M0 基线测量与口径冻结。
2. Rust 统一 API 与 parity 测试。
3. Rust 热路径逐文件接入。
4. mysqlclient / PyMySQL fallback / 部署模板复核。
5. 行情缓存覆盖治理。
6. priority board 与 strategy tracking 查询上界守卫。
7. Go market-read / BFF fallback parity 冒烟。
8. `/metrics` 观测补强。
9. 派生指标缓存局部试点。
10. 性能预算烟测。
11. 全市场扫描并行化 spike。
12. 24M 回测并行化专项。

## 优先级建议

### 立即做

- M0 基线测量。
- Rust 统一 API。
- Rust parity/golden 测试。
- 已有 Rust 热路径补齐。
- 缓存覆盖对账。
- N+1 查询上界测试。

### 第二批做

- 派生指标缓存局部试点。
- Go/BFF fallback parity 补齐。
- `/metrics` 补 worker/cache/fallback 比例。
- 性能预算烟测脚本。

### 先不直接做

- 全市场扫描生产级并行化。
- 24M 回测并行化。
- 全量 async SQLAlchemy。
- Go/Rust 重写业务。
- 新增 Celery/Kafka/Temporal/K8s。

## 最大收益点

1. Rust 复用接入：收益最高且已有基础，适合先做。
2. 行情缓存覆盖 + mysqlclient：接口 p95 和尾延迟收益明确。
3. N+1 上界守卫：收益可能不如 Rust 立竿见影，但防止后续持续劣化。
4. 派生指标缓存：对重复请求和重复扫描收益稳定。
5. 并行化：理论收益最大，但必须后置。

## 最大风险点

1. 并行化破坏排序、冷却、组合约束。
2. Rust/Python 边界处理不一致导致信号漂移。
3. 缓存陈旧导致错误数据被当成新数据。
4. Go/BFF fallback 字段不一致导致前端或 BFF schema mismatch。
5. 性能预算门过早强阻塞导致 CI 不稳定。

## 一句话结论

这份计划可以拆成“确定收益、低风险”的接线治理批次和“高收益、高风险”的并行化专项。前者应立即做，后者必须先 spike。最稳妥的路线是：先用 Rust parity、缓存覆盖、N+1 守卫和 metrics 把现有加速栈接稳，再讨论全市场扫描和 24M 回测并行化。
