## 二、跨阶段设计决策（含 10 个澄清问题回答）

### 2.1 权限模型

**当前状态**：`User.roles` 逗号分隔字符串。`backtests.py:386-402` 有 `_require_optimizer_access` 和 `_require_research_access`。`/api/strategies/meta` handler 不接收 `current_user`。

**目标状态**：

| 角色 | roles 值 | 权限 |
|------|---------|------|
| 管理员 | `admin` / `administrator` | 全部（含 factor 策略查看、feature flag 修改、promote/demote） |
| 研究员·优化 | `backtest_optimizer` | 参数优化 + 样本外验证 + 查看 factor |
| 研究员·验证 | `backtest_research` | 样本外验证 + 查看 factor |
| 普通用户 | 无上述角色 | 查看 core/auxiliary/research（不含 factor） |

**Q: 普通用户能否运行 factor 策略回测？**
A: 回测 API 不做 role 阻断。但普通用户无法从 `/api/strategies/meta` 发现 factor 策略 key，因此前端策略选择器不会展示 factor，用户无法主动触发。若用户通过直接 curl 传入 factor key，回测正常执行（不留后门黑名单）。此决定是为了：回测 API 不因新增策略类型而需要改权限逻辑。

**Factor 权限过滤**：**后端过滤**。Handler 改为接收 `current_user`：

```python
# 当前（不可做权限过滤）：
def list_strategy_meta(db: Session = Depends(get_db)) -> StrategyMetaResponse:

# 目标：
def list_strategy_meta(
    current_user = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> StrategyMetaResponse:
    items = [...]
    if not _has_role(current_user, {"backtest_optimizer", "backtest_research", "admin", "administrator"}):
        items = [item for item in items if item.category_key != "factor"]
    return StrategyMetaResponse(strategies=items)
```

路由级 `dependencies=[Depends(get_current_user)]` 保留不动，仅 handler 签名加 `current_user` 参数。

### 2.3 Resolver 边界

**当前状态**：`strategy_tier_resolver.py` 不存在。governance/priority 调用纯函数 `get_strategy_tier()` / `participates_in_priority_board()`。

**Q: Resolver 缓存 TTL 300s，跨请求如何持有 DB session？**

### 2.4 策略元数据 4 字段（4 处落点）

### 2.6 Governance 调用链

**Q: `strategy_tier_overrides` 多次 promote/demote 时，主表是 UPDATE 还是 INSERT？**
A: **UPDATE**。主表 `UNIQUE(strategy_key)` 保证每个策略最多一行 active override。规则：
- 首次 promote → INSERT 新行
- 再次 promote（不同 tier） → UPDATE `override_tier/reason/evidence_summary/promoted_at`，`reverted_at` 设为 NULL
- demote → UPDATE `reverted_at = now()`（行保留，不删除）
- 历史全量记录在 `strategy_tier_override_log` 表（每次操作 INSERT 一条）

### 2.10 弹性评分

**Q: 计算公式、数据来源、回测是否使用同一公式？**
A: 数据源：`MinuteBarSnapshot` 近 20 日分钟线。公式：盘中跌 >1.5% 后当日或次日反弹超跌幅 60% 的次数。≥3 次 → 评分 60+；1-2 次 → 25-74；0 次 → 10（最低基础分）。回测使用同一公式，但若分钟数据不可用则标记为 `"backtest_estimated"`（daily 代理估计）或 `"unavailable"`（无分钟数据）。

### 2.11 result_quality

**Q: coverage_pct 由哪个 service 计算，缺失日线和停牌日如何排除？**
A: 由回测 runner 在 `BacktestRunDetail` 构建时计算。公式：`实际有日线数据的交易日数 / 区间内总交易日数 × 100`。排除周六日和 A 股已知节假日（通过交易日历）。停牌日（标的无数据但其他标的有数据）计入分子缺失。连续停牌超 5 日的区间从分母剔除。

### 2.12 做T信号质量增强（在不改 trade_levels() 前提下）

**问题**：当前做T引擎信号产出少且时机不够精准。`trade_levels()` 5 元组不能改（不破规则第 1 条），但可以在引擎外围补三层预判来提升信号质量和用户决策效率。

**三层增强策略**（全部在 `trade_levels()` 外围实现，不改引擎核心）：

**第一层：盘前标的初筛 — 弹性排名**

每个交易日 9:00 预热弹性缓存后，对用户持仓按弹性评分降序排列。在 API 响应中新增 `elasticity_ranking` 字段：排名前 25% 标"★★★★★ 今日做T首选"，25%-50% 标"★★★★ 可关注"，50%-75% 标"★★★ 一般"，后 25% 标"★★ 弹性偏低，建议观望"。用户一眼知道哪些标的适合做T，减少盲目操作。

实现位置：`quant_engine_decision.py` 在调用 `trade_levels()` 前，从 `trading_elasticity_cache` 读取弹性评分，在 `TradeCostEstimate` 中附带 `elasticity_tier: str` 字段。

**第二层：盘中量价预判 — 流动性检查**

在 `attach_trade_costs()` 中新增流动性门槛检查（不改变 `trade_levels()` 的输出，仅在费用估算阶段附加）：

```python
# 流动性预判（不修改原始信号，仅附加在 cost estimate 中）
def _liquidity_gate(*, spread_pct: float, depth_bps: float, position_value: float) -> str:
    """返回 '' = 通过, 非空 = 警告文本"""
    if spread_pct > 0.30:
        return f"当前买卖价差 {spread_pct:.2f}% 偏大，做T滑点成本高"
    if depth_bps < 5.0:
        return f"盘口深度不足（五档仅 {depth_bps:.1f}bp），大单可能无法成交"
    if position_value < 5000:
        return f"持仓市值仅 {position_value:.0f} 元，做T费用占比过高，建议至少 10,000 元市值"
    return ""
```

此检查不影响 `is_actionable`（不做硬阻断），仅在 `fee_warning` 中追加提示。用户在信号卡片上看到警告后可以自行判断。

**第三层：时段建议 — 日内时间窗口**

A 股做 T 有明显的时段效应：开盘 30 分钟波动大但方向不稳，14:30 后往往趋势明确。在 `TradeCostEstimate` 中新增 `suggested_timing: str` 字段：

```python
def _suggested_timing(hour: int, minute: int) -> str:
    if hour == 9 and minute < 45:
        return "开盘波动较大，建议观察 15-30 分钟后再操作"
    if hour == 10 or hour == 11:
        return "上午盘中，适合执行做T"
    if hour == 13 and minute < 30:
        return "午后开盘，注意方向确认"
    if hour >= 14 and minute >= 30:
        return "尾盘趋势较明确，适合执行"
    return "盘中适合作T操作"
```

前端在信号卡片底部用灰色小字展示时段建议，不阻断操作。

**对信号数量的实际影响**：这三层增强不会增加 `trade_levels()` 产出的原始信号数（引擎核心不改），但通过弹性排名让用户聚焦高胜率标的 + 流动性警告避免无效操作 + 时段建议提升执行质量，间接提高**实际盈利信号占比**（胜率）。

**新增字段汇总**（全部在 `TradeCostEstimate` 或 `StrategySuggestion` 中，全 Optional）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `elasticity_tier` | `str` | `"★★★★★"` / `"★★★★"` / `"★★★"` / `"★★"` |
| `liquidity_warning` | `str` | 空=正常，非空=流动性警告文本 |
| `suggested_timing` | `str` | 时段建议文本 |
| `min_position_value` | `float` | 建议最低持仓市值（低于此值费用不划算） |

### 6.3 策略一：均线通道波段 (`ma_channel_band`)

### 6.4 策略二：龙头回踩波段 (`leader_pullback_band`)

**定位**：3-10 天波段策略，捕捉热点板块龙头的第二波机会。依赖涨停事件数据。

**投资逻辑**：A 股短线生态中，每个热点板块有 1-3 只龙头股。龙头股经历"涨停启动 → 高位回踩均线支撑 → 再度拉升"的循环。当前 `first_board` 捕捉首板+首阴，但龙头确认后的第 2-4 次回踩同样安全——此时龙头身份已确认、市场记忆仍在、获利盘已消化。

**龙头识别**（板块内排序，满足 2/3）：

| # | 条件 | 数据来源 |
|---|------|---------|
| 1 | 近 20 日涨停次数 ≥ 2 | `limit_up_pool` 事件聚合 |
| 2 | 近 20 日日均成交额在行业中排前 3 | `DailyBarSnapshot` 行业聚合 |
| 3 | 近 20 日涨幅在行业中排前 5 | `DailyBarSnapshot` 行业聚合 |

**入场条件**（全部满足）：

| # | 条件 | 说明 |
|---|------|------|
| 1 | 龙头确认（满足上述 2/3） | 板块地位确认 |
| 2 | 从近 20 日高点回撤 ≥ 6% | 获利盘消化 |
| 3 | 近 3 日均量 < MA(VOL, 20) × 0.75 | 缩量确认（抛压减轻） |
| 4 | 当前价在 MA10-MA20 之间 | 均线支撑区域 |
| 5 | 当日非跌停（`latest_change_pct > -9.7`） | 排除流动性枯竭 |
| 6 | 排除 ST/退市/利空公告 | 风险规避 |

**出场条件**（满足任一）：

| # | 条件 | 类型 |
|---|------|------|
| 1 | 反弹至回撤幅度的 50% | 半仓止盈 |
| 2 | 反弹至回撤幅度的 80% | 全部止盈 |
| 3 | 跌破 MA60 | 趋势破坏止损 |
| 4 | 持仓 > 12 交易日 | 时间止损 |

- 仅主板标的（688/300 开头排除）
- 单只最大仓位：总资金 20%
- 板块热度降温（板块内涨停家数 < 2）→ 策略暂停该板块
