### 1.3 核心优势

1. **策略引擎深度扎实**：12 个策略分 4 层级（CORE/AUXILIARY/RESEARCH/FACTOR），21 个因子注册表，4 阶段信号评分管线，优先级榜单跨策略去重，PBO 回测过拟合检验——这些在个人量化项目中属于罕见的系统化程度。
2. **模拟盘体系完整**：撮合引擎、T+1 约束、四档风控硬限制、熔断机制、savepoint 回滚、四维绩效追踪（整体/策略/市场状态/标签），已具备生产级模拟盘的骨架。
3. **Agent 架构设计超前**：9 种 Provider 的可插拔抽象层、审计追踪、敏感数据脱敏、通知去重账本、飞书自然语言命令桥——这些设计为未来多 Agent 协作和 LLM 集成预留了干净接口。
4. **数据获取多源降级**：腾讯 → 东方财富 → 新浪 → akshare → 子进程 → 过期缓存，6 层降级链确保报价可用性。
5. **前端代码分割到位**：7 个页面 lazy load，ECharts 独立 chunk，离线缓存 + 请求去重 + 指数退避重试。

### 1.4 核心风险

1. **无版本控制**（P0）：35,000+ 行生产代码无 Git 管理。这是最高优先级风险。
2. **auth_secret_key 空默认值**（P0）：默认 `""` → 降级链到 `database_url` 作为 HMAC 签名密钥。任何读到 `config.py` 的人可伪造 Token。
3. **4 个路由模块零鉴权**（P0）：analysis、research、instruments、screeners 路由无任何 auth 依赖，settings 的 GET 端点暴露 LLM API Key。
4. **SQLite 单写者瓶颈**：WAL 缓解了读写并发，但写-写竞争靠 `busy_timeout=30000` 硬扛。多后台任务同时写入快照时可能阻塞 30 秒。
5. **前端 856 行单体编排器**：`TradingWorkspace.tsx` 集中了全部 25+ 个状态变量和所有业务逻辑，props 层层传递至 15-24 个参数。

## 二、各模块深度分析

### 2.1 后端架构

#### 当前状态

- **路由注册**：17 个路由模块通过 `app/api/router.py` 统一注册
- **鉴权覆盖**：8 个模块有鉴权（通过 `get_current_user` 依赖），4 个模块零鉴权（analysis/research/instruments/screeners），2 个模块部分鉴权（settings GET 无鉴权、agent 通过双 Token 模式）
- **服务层组织**：126 个 `.py` 文件按功能域分散在 `services/` 下，无统一的模块边界划分
- **配置管理**：45+ 个 Pydantic Settings 字段，分属 `AppSettings` 和 `RuntimeSettings`
- **数据库**：SQLite + SQLAlchemy 2.0 ORM，37 张表，25+ 个通过 `schema_compat.py` 自动创建的索引
- **后台任务**：`TaskManager` 线程调度器管理 5 个定时任务 + 自动交易线程
- **限流**：独立 SQLite 数据库的滑动窗口限流器，4 个限流维度

#### 优势

- RESTful 路由组织清晰，每个文件职责单一
- 双 Token 鉴权模式（用户 JWT + Agent API Token）设计灵活
- `schema_compat.py` 启动时自动修复缺失列和索引，降低运维成本
- 后台任务注册接口简洁（`register_loop`），支持运行时调节

#### 问题与缺口

| 严重度 | 问题 | 影响 |
|--------|------|------|
| P0 | 4 路由模块零鉴权 | 任意访问者可调用 analysis/research/instruments/screeners |
| P0 | settings GET 端点暴露 LLM API Key | 配置信息泄露 |
| P0 | `auth_secret_key` 空默认值 | Token 可被任意伪造 |
| P1 | 后台任务在 SQLite 上默认关闭 | SQLite 用户无缓存刷新/信号扫描/绩效归档 |
| P1 | `_upsert_frame` N+1 写入 | 数千行逐行 SELECT + INSERT |
| P2 | 无 SQLAlchemy 连接池（NullPool） | 每个请求创建/销毁 SQLite 连接 |
| P2 | 快照表 JSON 列无法索引查询 | TEXT 存 JSON 牺牲了查询能力 |
| P2 | 无 API 版本控制 | 前后端耦合升级困难 |

#### 演进方向

- **短期**：补全鉴权（所有路由模块加 `get_current_user`），修复 `auth_secret_key` 默认值，将 settings GET 端点拆分为公开/鉴权两个版本
- **中期**：启用后台任务在 SQLite 上的运行（读写分离 + 延迟写入队列），增加 API 版本前缀（`/api/v1/`），引入 `INSERT ... ON CONFLICT ...` 批量 upsert
- **长期**：MySQL 作为主库 + SQLite 作为本地缓存层，引入 Redis 作为分布式缓存和限流后端，gunicorn + 多 worker 部署

#### 优化建议

1. **立即**：所有路由模块统一注入 `get_current_user` 依赖
2. **立即**：`auth_secret_key` 改为必填字段，启动时检查非空
3. **本周**：`settings GET` 端点分离：`/api/settings/public`（公开）和 `/api/settings/private`（鉴权）
4. **本周**：为 `MarketDataService` 添加 SQLite 连接池（`pool_size=5, max_overflow=10`）

### 2.2 前端架构

#### 当前状态

- **入口**：`TradingWorkspace.tsx`（856 行）作为单页编排器，承载全部状态（25+ `useState`）、全部数据获取逻辑、全部事件处理、路由管理、SSE 连接和定时轮询
- **组件树**：7 个页面 lazy load，12+ 个共享组件集中在 `WorkspaceComponents.tsx`（455 行）
- **状态管理**：无全局 Store，无 Context，无 `useReducer`。数据流为纯 props 下传 + callback 上抛
- **API 层**：两个客户端（`api` + `appApi`），共享同一个 `request()` 传输层，有内存缓存 + localStorage 离线缓存 + 请求去重 + 指数退避重试
- **CSS**：单文件 3,280 行 `index.css`，CSS Grid 布局，命名 BEM-like 但无作用域隔离
- **构建**：Vite 5.4 + React 18.3 + TypeScript 5.6，ECharts 独立 chunk

#### 优势

- API 层设计精良：缓存、去重、重试、离线支持四层保护
- 代码分割合理：7 个页面 lazy load + ECharts 独立 chunk
- CSS Grid 布局语义化（`grid-template-areas`），响应式 5 级断点
- 无重量级依赖（仅 echarts 较大），bundle 可控

#### 问题与缺口

| 严重度 | 问题 | 影响 |
|--------|------|------|
| P0 | TradingWorkspace 856 行单体组件 | 任何修改需理解全部业务逻辑，不可单独测试页面 |
| P1 | 25+ useState 无结构化管理 | 状态依赖隐式，难以追踪数据流 |
| P1 | Props 逐层传递 15-24 个参数 | 新增功能需穿透整个链条 |
| P1 | 无 `useCallback` | 所有 handler 每次 render 重建 |
| P1 | `loading` 为单个字符串 | 多加载器冲突，拼写错误无编译检查 |
| P2 | 单文件 3,280 行 CSS | 样式冲突风险，难以维护 |
| P2 | 鉴权错误检测靠字符串匹配 | "401"/"登录"等硬编码匹配，脆弱 |
| P2 | 无 Error Boundary | lazy 页面崩溃时无恢复机制 |
| P2 | 手动 history 管理 | 无 URL search params、无滚动恢复、无深层链接 |

#### 演进方向

- **短期**：将 7 个页面的数据获取逻辑分别提取为自定义 Hook（参考已有的 `usePaperTrading`），将 TradingWorkspace 缩减为路由调度器
- **中期**：引入轻量状态管理（Zustand 或 React Context + useReducer），将全局状态（用户、loading、notice、error）提升为 Context
- **长期**：迁移至 React Router v6（支持嵌套路由、search params、loader），拆分为独立页面 + 共享 Layout；引入 CSS Modules 或 Tailwind CSS 替代单文件 CSS

#### 优化建议

1. **本周**：提取 `useMonitor`、`usePlaybook`、`useAnalysis`、`useResearch` 四个 Hook，将数据获取和状态从 TradingWorkspace 移出
2. **本周**：`loading` 改为 `Record<string, boolean>` 或使用 `useReducer`
3. **本周**：给所有 handler 加 `useCallback`
4. **本月**：引入 React Context 管理 user / auth / notification 三层全局状态
5. **本月**：将 `index.css` 按页面拆分为 7 个 CSS 文件，通过页面 lazy load 按需加载

### 2.3 策略与因子引擎

#### 当前状态

- **策略体系**：12 个策略分 4 层级（CORE 2 个 / AUXILIARY 3 个 / RESEARCH 5 个 / FACTOR 2 个），通过 `strategy_policy.py` 管理层级和权重
- **策略家族**：9 个家族（首板回调 / 回调缩量 / 午后强势支撑 / 中盘均线 / 主分背离等），用于跨策略去重
- **因子注册表**：21 个因子，按类别分为量价（8）、板块（3）、资金流（2）、基本面（3）、盘口（3）、融资（2）
- **评分管线**：Pool 构建 → 预过滤 → 70+ 指标计算 → 4 阶段信号评分（启动质量 24% + 回调健康度 30% + 确认质量 26% + 失败风险 20%）→ 21 因子加权 → 市场状态调整 → 6 态信号解析
- **回测系统**：执行层面回测（开仓/止损/止盈/时间退出），16bps 成本，PBO 过拟合检验，流动性危机压力测试
- **实现方式**：13 个 Mixin 类通过 Python MRO 组合成 `_LowBuyRuntime` 服务类，无 Strategy 接口或 ABC

#### 优势

- 策略层级设计合理：CORE 生产 / AUXILIARY 辅助 / RESEARCH 研究 / FACTOR 因子，权重递减
- 因子注册表设计优雅：`FactorSpec` 数据类 + `list_factor_specs()` 注册函数，新增因子只需加一项
- 信号管线完整：从数据 → 指标 → 评分 → 信号 → 优先级榜单，每个环节可独立测试
- PBO 回测检验：在个人量化项目中属于罕见的严谨做法

#### 问题与缺口

| 严重度 | 问题 | 影响 |
|--------|------|------|
| P0 | 70-90+ 硬编码魔法数字 | 散落在信号评分、阈值判断中，无文档、不可配置 |
| P1 | 7/21 个因子为存根（永久返回 0） | 注册但不生效，混淆性大 |
| P1 | 13-mixin 钻石继承 | 隐式 MRO，调用链难以追踪，IDE 跳转困难 |
| P1 | 无 Strategy 抽象接口 | 添加全新策略类型需修改核心管线 |
| P2 | `_has_distribution_hard_block` / `_soft_block` 70% 重复 | 维护两份相同逻辑 |
| P2 | 评分管线同步阻塞 | `_screen_sync()` 处理 480 候选时阻塞 API 响应 |
| P2 | akshare 依赖脆弱 | per-symbol 调用，单次失败影响全扫描 |

#### 演进方向

- **短期**：将 70+ 魔法数字提取到 `LowBuyThresholds` 数据类（已有框架，扩展即可），7 个存根因子加 `status="stub"` 标记并在文档中说明
- **中期**：提取 `BaseStrategy` 抽象类（含 `prefilter` / `score` / `entry_zone` / `exit_rules` 方法），将策略特定代码从 `signals.py`/`candidate.py` 中解耦到策略类中
- **长期**：评分管线异步化（后台渐进式扫描 + 结果推送），引入 ML 因子模型（使用已有因子作为特征，训练排序模型替代手写评分），实现真正的多日持仓管理

#### 优化建议

1. **本周**：魔法数字提取到 `LowBuyThresholds` 数据类，加中文注释说明每项含义
2. **本周**：合并 `_has_distribution_hard_block` 和 `_soft_block` 为一个参数化方法
3. **本月**：为 `_screen_sync` 添加进度回调，支持分页扫描和取消
4. **本月**：移除或实现 7 个存根因子，至少为 `north_flow_factor` 接入北向资金数据

### 2.4 Agent 系统

#### 当前状态

- **工具注册表**：10 个工具（7 read + 1 write + 3 notify），均有 Pydantic 入参 schema
- **Provider 抽象层**：9 种 Provider 实现，`AgentProvider` 抽象基类统一了鉴权、审计、追踪
- **鉴权三层**：用户 JWT / Agent API Token（静态共享）/ Admin Token
- **审计追踪**：工具调用全程记录（trace_id、参数脱敏、耗时、状态），可选 DB 持久化
- **通知系统**：飞书 Webhook + HMAC 签名 + 去重账本（17 级信号优先级）+ 冷却计时 + 信号升级检测
- **飞书桥**：7 个自然语言命令映射（持仓/成交/绩效/风控/策略/自选/日报）
- **当前可用 Provider**：仅 `none`（本地直接调用）和 `mcp`（HTTP 代理到本服务）。其余 7 个 LLM Provider 为骨架存根

#### 优势

- Provider 抽象层设计超前：统一的 `invoke_tool` 入口 + Policy 鉴权 + Audit 审计，新增 Provider 只需继承基类
- 通知去重账本设计精良：`(scope_key, channel, event_type, symbol, strategy_key)` 复合唯一约束 + 信号升级检测
- 敏感数据脱敏：12 种敏感 key 递归扫描脱敏，覆盖 token/api_key/password/secret 等
- 飞书自然语言桥模式优雅：命令 → `AgentContextService` → 返回结果，易于扩展新命令

#### 问题与缺口

| 严重度 | 问题 | 影响 |
|--------|------|------|
| P1 | 7/9 Provider 为骨架存根 | LLM 集成实际不可用 |
| P1 | 通知仅支持飞书 | 其他 channel 返回 "not supported" |
| P1 | 无工具级速率限制 | Agent 可无限调用工具 |
| P2 | `recommend_orders` 仅 dry_run | 从建议到执行还需手动步骤 |
| P2 | 无多 Agent 编排 | 无路由/委派/并行执行能力 |
| P2 | 无流式响应 | 所有调用为请求-响应模式 |
| P2 | 服务层测试覆盖率低 | AgentContextService/AgentReportService 等无测试 |

#### 演进方向

- **短期**：实现至少一个 LLM Provider（建议从 `openai_agents` 开始，对接 OpenAI API），启用 `agent_enable_notify_tools` 让飞书通知生效
- **中期**：添加工具级速率限制（每个工具独立限流器），实现飞书交互式卡片（按钮/下拉），扩展飞书命令到 12+ 个
- **长期**：多 Agent 协作（策略 Agent + 风控 Agent + 执行 Agent），Agent 间通过共享上下文通信，Agent 自主交易（需 `dangerous` 权限级别 + 人工确认流程）

#### 优化建议

1. **本周**：为 `agent_enable_notify_tools` 添加启动时检查，如开启但飞书 Webhook 未配置则警告
2. **本月**：实现 `openai_agents` Provider 的 LLM 调用逻辑（OpenAI function calling 协议对接工具注册表）
3. **本月**：添加工具级速率限制（`AgentToolRateLimiter`，每个工具独立窗口）
4. **本月**：补全 `AgentContextService` 和 `AgentReportService` 的单元测试

### 2.5 模拟盘系统

#### 当前状态

- **撮合引擎**：fill-or-kill 模式，买入按卖一价 + 5bps 滑点（ETF 2bps），卖出按买一价 - 5bps。无部分成交，无订单簿模拟
- **订单管理**：市价/限价两种类型，6 种状态（pending/filled/partial/rejected/cancelled/expired），限价单需满足 `限价 >= 撮合价` 才成交
- **风控系统**：4 档硬限制（单票 30%/单日 40%/连续亏损 60%/同时持仓 20 只）+ 熔断机制（回撤 >12% 或连续 3 笔亏损自动暂停账户）+ T+1 买入锁定
- **费率计算**：A 股标准费率（印花税 0.05% 卖出 / 佣金 0.025% 最低 5 元 / 过户费 0.001%），使用 Python Decimal + ROUND_HALF_UP
- **自动交易**：线程内运行，信号准入 → 头寸规模 → 退出计划（止损 -3% / 止盈 +5%）→ savepoint 批量执行
- **绩效追踪**：四维（整体/策略/市场状态/标签），日报支持 LLM 或规则生成
- **标签系统**：每笔成交可加多个标签，支持绩效按标签聚合

#### 优势

- 风控制度严谨：4 档硬限制 + 熔断机制，覆盖了个人量化模拟盘的核心风险场景
- Savepoint 回滚：批量执行中的部分失败可回滚到 savepoint，保证数据一致性
- 四维绩效追踪：超越简单的收益统计，支持策略/市场状态/标签的多维归因
- Decimal 精度处理：费率计算使用 Decimal + ROUND_HALF_UP，准确度有保障

#### 问题与缺口

| 严重度 | 问题 | 影响 |
|--------|------|------|
| P1 | Float/Decimal 混用 | 退出逻辑中部分计算使用 float，与订单模块的 Decimal 不一致 |
| P1 | 并发余额检查无行锁 | 多请求并发时余额检查存在竞态条件 |
| P1 | 5 元最低佣金对小额订单负担重 | 100 股 × 10 元的订单佣金率达到 0.5% |
| P2 | `max_drawdown` 循环引用 | PaperAccount 和 PaperPerformanceSnapshot 互相引用，导致序列化问题 |
| P2 | 无部分成交 | fill-or-kill 可能导致流动性差时无法成交 |
| P2 | 退出逻辑中 max_drawdown 未实时更新 | 使用建仓时的估值作为基准，不随价格波动更新 |
| P2 | 缺少 ETF/T+0 检测 | ETF 不受 T+1 限制但系统未做区分 |

#### 演进方向

- **短期**：统一 Decimal 精度（全链路 Decimal），修复 `max_drawdown` 循环引用（改为单向引用），添加行级锁（SELECT ... FOR UPDATE）
- **中期**：支持部分成交（订单拆分 + 剩余撤单），增加 ETF/T+0 检测逻辑，实现冰山订单和 TWAP/VWAP 算法订单
- **长期**：真实行情回放撮合（逐笔成交驱动），多账户支持，组合层面优化（均值-方差 / 风险平价）

#### 优化建议

1. **本周**：修复 `max_drawdown` 循环引用，改为从 `PaperPerformanceSnapshot` 单向查询
2. **本月**：统一 float → Decimal 转换，添加类型检查（mypy strict decimal）
3. **本月**：添加 `SELECT ... FOR UPDATE` 行锁保护余额检查
4. **本月**：增加小额订单警告（佣金占比 > 1% 时前端提示）

### 2.6 数据与性能

#### 当前状态

- **数据源架构**：6 层降级链（腾讯 → 东方财富 → 新浪 → akshare → 子进程 → 过期缓存），按报价/K线/快照分类路由
- **缓存体系**：进程内存缓存（报价 10s TTL / K线 20s / 市场宽度 45s / 情绪 120s / 交易日期 600s）+ 物化 DB 快照，带容量限制和 LRU 修剪
- **限流**：独立 SQLite 数据库的滑动窗口限流器，全局 30 req/s，AI 决策 30/60s，登录 30/60s，注册 30/3600s
- **数据库**：SQLite WAL 模式，37 表，25+ 复合索引，`Numeric` 在 SQLite 上降级为 FLOAT
- **后台任务**：5 个定时线程（全量深筛 3600s / 自选信号 45s / 绩效归档 300s / 策略验证 24h / 通知扫描），SQLite 下默认关闭

#### 优势

- 数据降级链健壮：6 层 fallback 确保报价不中断
- 缓存设计成熟：多级 TTL + 容量修剪 + 请求去重
- 索引覆盖全面：25+ 个针对热查询路径的复合覆盖索引
- WAL 模式缓解了读写并发冲突

#### 问题与缺口

| 严重度 | 问题 | 影响 |
|--------|------|------|
| P1 | SQLite 写者瓶颈 | 多后台任务同时写入时 `busy_timeout` 最长阻塞 30s |
| P1 | SQLite 无连接池（NullPool） | 每个请求创建/销毁连接 |
| P1 | 后台任务 SQLite 下默认关闭 | SQLite 用户无缓存刷新/信号扫描/归档 |
| P1 | 限流器自身成为瓶颈 | 每请求 DELETE+SELECT+INSERT 事务 |
| P2 | 多进程部署缓存膨胀 | 每个 worker 独立进程缓存，2-4x 内存 |
| P2 | `Numeric` → FLOAT 精度损失 | 金额计算存在舍入误差风险 |
| P2 | 无分布式缓存 | 无法跨 worker 共享报价缓存 |

#### 演进方向

- **短期**：SQLite 添加连接池（`pool_size=5, max_overflow=10`），启用后台任务（读写分离 + 写入队列），限流器迁移至内存实现
- **中期**：引入 Redis（分布式缓存 + 限流 + 消息队列），MySQL 作为主库保留 SQLite 为本地缓存
- **长期**：微服务化数据源（独立报价服务），时序数据库存储 K 线（InfluxDB/TimescaleDB），CDC 同步到分析库

#### 优化建议

1. **本周**：`database.py` 中为 SQLite 添加 `pool_size=5, max_overflow=10` 的 `StaticPool`
2. **本周**：限流器从 SQLite 改为内存实现（`collections.deque` 滑动窗口），解决 `database is locked` 问题
3. **本周**：添加 `healthz` 端点暴露 p50/p95/p99 延迟指标
4. **本月**：实现 `_upsert_frame` 的批量 `INSERT ... ON CONFLICT` 替代逐行 upsert

### 3.2 密钥管理

- `auth_secret_key: str = ""` — 默认空字符串，降级链到 `database_url`
- `admin_api_token: str = ""` — 默认空，导致 admin 端点返回 500
- `agent_api_token: str = ""` — 默认空，Agent Token 鉴权不可用
- LLM API Key 可通过 settings GET 端点明文获取

### 3.3 推荐立即修复

1. `auth_secret_key` 改为必填，空值时启动报错退出
2. 所有路由模块统一注入 `get_current_user` 依赖
3. `settings GET` 端点拆分公开/鉴权版本
4. LLM API Key 存储加密（至少 base64，理想情况用环境变量或密钥管理服务）
