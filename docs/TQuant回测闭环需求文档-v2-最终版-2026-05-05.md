## 裁定总纲

v1 需求文档方向正确，接受为中长期架构目标。但 v1 存在三方面偏差需要修正：

1. **数据层过度设计**：不应新建 `backtest_data_snapshots` 表重复存储全量日线，应优先复用 `daily_bar_snapshots` 事实表，通过 manifest/version/quality 元数据确保可复现性
2. **部分细节不准确**：API 路径、T+1 规则、买入执行模型、核心模块复用方式需要修正
3. **优先级失序**：参数优化、贝叶斯搜索、PBO、蒙特卡洛、HTML 报告、Fama-French 归因等不应出现在首版，应严格按 6 阶段递进

以下为逐条裁定后的最终需求文档。

## 一、核心目标

建立一个**可复现、异步、投资组合级、真实执行口径**的日线回测闭环：

1. 按 A 股交易日历逐日推进，模拟多信号并发时的资金竞争、复利效应、组合持仓
2. 复用现有模拟盘的撮合引擎（`paper/matching.py`）、费用模型（`paper/fees.py`）、T+1 规则（`paper/position.py`）
3. 每次回测结果可复现（相同参数 + 相同数据版本 = 相同结果）
4. 回测、参数优化、样本外验证均为异步任务，不阻塞 HTTP 请求
5. 逐策略、市场状态、行业维度做绩效归因，为当前 12 策略体系的持续优化提供数据支撑

### 2.2 数据层：复用现有表 + 元数据清单

**裁定**：不新建 `backtest_data_snapshots` 表重复存储全量日线 JSON。数据集本身（OHLCV）已存在 `daily_bar_snapshots` 中，缺的是"这次回测用了哪个版本的数据"的可追溯性。

方案：新增轻量级元数据表。

```sql
-- 数据集清单：记录每次回测使用的数据版本
CREATE TABLE backtest_dataset_manifest (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id INTEGER NOT NULL REFERENCES backtest_runs(id),
    data_type TEXT NOT NULL,              -- daily_bar / limit_up_pool / market_state / sector
    source_table TEXT NOT NULL,           -- daily_bar_snapshots / 等
    source_hash TEXT NOT NULL,            -- 数据集的 hash（如 COUNT(*) + MAX(updated_at) 的 hash）
    record_count INTEGER NOT NULL,        -- 记录数
    date_range_start TEXT,
    date_range_end TEXT,
    quality_tag TEXT NOT NULL DEFAULT 'ok',  -- ok / incomplete / stale
    quality_notes TEXT,                   -- 如 "含 12 个交易日零价异常"
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 数据质量快照（每次回测启动时自动采集）
CREATE TABLE backtest_data_quality (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id INTEGER NOT NULL REFERENCES backtest_runs(id),
    check_type TEXT NOT NULL,             -- missing_dates / zero_price / stale_data / suspension / st_list
    detail_json TEXT NOT NULL DEFAULT '{}',
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

## 三、核心模块详细要求

### 3.1 交易日历

**裁定**：必须使用 A 股真实交易日历，不能仅跳周末。

直接复用项目已有的 `backend/app/services/market/trading_calendar.py`：

```python

# 回测引擎中
trade_dates = [
    d for d in date_range
    if is_a_share_trading_day(d)
]
```

需补充：定期从 akshare `tool_trade_date_hist_sina` 同步并更新 `_KNOWN_CN_MARKET_HOLIDAYS`。

### 3.2 数据质量标签（必须）

每次回测启动前，自动采集并在结果中记录以下质量指标：

| 检查项 | 方法 | 标签示例 |
|--------|------|---------|
| 缺失交易日 | `date_range` 内应有交易日 vs 实际有数据的交易日 | `missing_dates: 3 (2025-09-15, ...)` |
| 零价异常 | `open_price <= 0 or close_price <= 0` 的记录 | `zero_price_count: 12` |
| 停牌 | 连续多日无成交 / 价格不变 | `suspension_days: 47` |
| 过期数据 | `MAX(trade_date)` 与回测 end_date 的差距 | `data_lag: "2026-04-28 vs end 2026-05-04"` |
| 样本量 | 回测区间内实际有日线的标的总数 | `symbol_count: 4823` |
| 复权状态 | 记录当前使用的复权口径 | `adjustment: "forward" (前复权)` |

**裁定**：数据质量问题不阻塞回测运行，但必须在结果中明确标注。质量标签写入 `backtest_data_quality` 表。

### 3.3 复权口径（必须明确）

**裁定**：必须明确复权方式，否则长期收益不可信。

TQuant 当前 `daily_bar_snapshots` 存储的是 akshare 前复权数据。回测引擎应：

1. 在 `data_version_hash` 中记录复权方式标识
2. 在回测结果摘要中显示 `adjustment_method: "forward"`（前复权）
3. 如果未来支持后复权或混合复权，作为参数可配置

### 3.4 ST/退市历史口径（必须）

**裁定**：不能在回测中使用"当前是否 ST"来筛选历史标的。必须按回测当日的 ST 状态判断。

```python
def is_st_on_date(symbol: str, trade_date: str) -> bool:
    """按历史日期判断 ST 状态，避免幸存者偏差。"""
    # 查询 symbol 在 trade_date 时的名称是否包含 "ST" 或 "*ST"
    # 方案1：akshare stock_info_a_code_name() 历史快照
    # 方案2：daily_bar_snapshots 中 name 字段的历史值
```

- 回测入场时排除当日为 ST 的标的
- 持仓期间若标的变更为 ST，标记为特殊退出（`exit_reason: "st_flagged"`）

### 3.5 涨跌停与停牌（必须进入撮合模型）

**裁定**：涨跌停和停牌必须进入 broker 撮合逻辑。一字板买不到/卖不出是 A 股交易的核心约束。

```python
class BacktestBroker:
    """封装 paper 撮合引擎 + 涨跌停/停牌判断。"""

    def __init__(self):
        self._engine = PaperMatchingEngine()  # 复用现有撮合

    def match_buy(self, symbol, quantity, price, trade_date, bar):
        # 1. 涨停检查：如果开盘价 == 涨停价（一字板），reject
        if bar.open_price >= bar.up_limit:
            return MatchResponse(result=MatchResult.REJECTED, reject_reason="一字涨停无法买入")

        # 2. 停牌检查：如果当日无成交（volume == 0 或 high == low == open），reject
        if bar.volume <= 0:
            return MatchResponse(result=MatchResult.REJECTED, reject_reason="停牌")

        # 3. 委托现有撮合引擎
        return self._engine.match(
            symbol=symbol, side=OrderSide.BUY, quantity=quantity,
            current_price=price, ...
        )
```

### 3.6 买入执行模型（支持多种）

**裁定**：不能仅支持开盘价买入。至少支持以下模型，用户可选：

| 模型 | 撮合价 | 适用场景 |
|------|--------|---------|
| `open_price` | 当日开盘价 | 默认模型，最悲观/保守 |
| `vwap` | 当日成交额 / 成交量 | 中等保守，假设能拿到均价 |
| `close_price` | 当日收盘价 | 用于快速验证（偏乐观） |
| `entry_zone_touch` | 如果当日最低价 ≤ entry_zone_high，以 entry_zone_high 成交 | 最贴近低吸策略的实际操作 |
| `conservative_slippage` | 开盘价 × (1 + slippage) | 保守滑点模型 |

默认使用 `open_price`。回测结果中必须标注使用的执行模型。

### 3.7 T+1 规则（修正）

**裁定**：v1 文档的 T+1 描述不准确。修正为：

- A 股股票：**股份 T+1 可卖**（今日买入的股票，下一交易日才能卖出）。卖出资金当日可继续买入其他股票，但不可取（T+1 可取）
- 回测引擎中：买入当日 `available_quantity = 0`，下一交易日自动解锁
- ETF：部分 ETF 支持 T+0（如债券 ETF、黄金 ETF、跨境 ETF），需按品种分类处理。当前 `paper/symbols.py` 的 `is_etf()` 已有此分类

```python
def unlock_position(position, trade_date):
    # 股票：买入日 + 1 交易日解锁
    # ETF（T+0 品种）：买入日当日可卖
    if is_etf_t0(position.symbol):
        position.available_quantity = position.quantity
    else:
        if trade_date > position.entry_date:  # 严格大于
            position.available_quantity = position.quantity
```

## 四、绩效分析

### 4.1 核心指标（首版必须）

| 类别 | 指标 |
|------|------|
| 收益 | 总收益率、年化收益率、日均收益率 |
| 风险 | 年化波动率、最大回撤（金额 + 百分比 + 恢复天数）、VaR(95%) |
| 风险调整 | Sharpe Ratio、Sortino Ratio、Calmar Ratio |
| 交易 | 总交易次数、胜率、平均盈利/平均亏损、利润因子（Profit Factor）、平均持仓天数 |
| 基准对比 | 超额收益、跟踪误差、信息比率（IR） |

### 4.2 归因分析（首版必须）

| 维度 | 输出 |
|------|------|
| 逐策略拆解 | 每个策略的独立绩效（收益/Sharpe/胜率/交易数/贡献度） |
| 市场状态归因 | 按 8 类市场状态分组的胜率、平均收益 |
| 行业归因 | 按申万一级行业分组的盈亏贡献。首版使用当前分类，但报告必须标注"行业分类可能存在历史偏差" |
| 数据质量分桶归因 | 按缺失率/样本量将回测区间分桶，标注各桶的绩效可信度 |

### 4.3 首版不做

- Fama-French 风格因子归因（A 股短线低吸平台价值不高，且数据要求高）
- HTML 完整报告（JSON + 前端图表优先）

## 七、参数优化（Phase 4，严格约束）

**裁定**：参数优化可以做，但必须满足以下硬性约束：

1. **需要管理员权限或白名单**
2. **必须强制样本外验证**：最优参数必须在预留的样本外窗口独立验证
3. **默认使用网格搜索**（Grid Search），仅在参数空间超过 500 组合时才允许随机搜索
4. **贝叶斯优化暂不支持**（首版容易过拟合，且 scikit-optimize 引入新依赖，暂缓）
5. **只允许优化以下参数**：
   - `min_score`、`max_position_pct`、`max_holding_days`、`stop_loss_multiplier`
   - 不允许修改策略核心逻辑参数（如 `board_count`、`volume_burst_ratio`）
6. **优化结果不自动应用**到生产环境，需人工审核后手动修改配置

---

## 八、Walk-Forward 与 PBO（Phase 5）

**裁定**：接受为 Phase 5，不阻塞首版回测上线。

- Walk-Forward 窗口数默认 4（训练 18 月 / 测试 6 月）
- PBO（Probability of Backtest Overfitting）作为研究增强功能，为每个策略输出过拟合风险评级
- 样本外 Sharpe < 0 的策略，标记为 `downgrade_review_required`

---

## 九、版本记录（每次回测必须）

每次回测运行必须记录以下版本信息，写入 `backtest_runs` 表：

| 字段 | 来源 | 示例 |
|------|------|------|
| `code_version` | `git rev-parse HEAD` | `a1b2c3d` |
| `strategy_version` | `LOW_BUY_RESULT_VERSION` 常量 | `8` |
| `fee_model_version` | `fees.py` 的固定标识或 hash | `v1` |
| `data_version_hash` | `daily_bar_snapshots` 的 `COUNT(*) + MAX(updated_at)` 的 MD5 | `e4f5a6b7...` |

回测结果摘要中必须显示以上版本信息，确保任何结果的复现路径清晰。

## 十、不做的清单

以下功能在 Codex 裁定中明确暂缓或拒绝，不在任何阶段实现：

1. **分钟级全市场回测**：成本过高。先做日线级，未来可对重点标的做分钟级验证
2. **12 策略联合参数优化**：工程上可行但方法论上过早，容易变成调参挖矿
3. **贝叶斯优化**（首版）：先用网格/随机搜索，外加强制样本外验证
4. **Fama-French 因子归因**：数据要求高，对 A 股短线低吸平台价值有限
5. **新建 `backtest_data_snapshots` 全量日线副本**：浪费存储，已有 `daily_bar_snapshots`

## 十二、验收标准

1. 对 first_board 单策略做 2025-01-02 至 2026-04-30 回测，3 分钟内完成

4. 回测结果中包含完整的数据质量标签和版本记录

### Phase 3 验收

1. 前端可提交回测、查看运行状态、查看净值曲线和交易明细
2. 12 策略均可独立跑通回测
3. 多策略联合回测正确处理资金竞争和同 symbol 去重

### Phase 4 验收

1. 参数优化功能可用，且强制要求样本外验证
2. 优化结果中标注样本内/样本外绩效差距

### Phase 5 验收

1. Walk-Forward 验证产出样本外绩效汇总
2. PBO 测试为每个策略给出过拟合风险评级

## 裁定结语

本 v2 文档为 TQuant 回测闭环的最终需求规格。核心原则：

1. **复用优先**：不重写已有的撮合、费用、交易日历、策略管线
2. **可复现优先**：每次回测必须有完整的数据版本 + 代码版本 + 策略版本记录
3. **数据质量透明**：不阻塞回测，但必须在结果中标注所有数据质量问题
4. **严格分阶段**：不跳过 Phase 1-2 直接做优化和 PBO
5. **过拟合防护**：参数优化必须强制样本外验证，结果不自动应用

Phase 1-3 完成后，TQuant 将首次具备完整的"信号产出 → 回测验证 → 绩效分析 → 策略优化"闭环。这是从"决策辅助工具"到"可验证的量化研究平台"的关键一步。
