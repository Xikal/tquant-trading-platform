### 2.2 当前系统状态判断

当前 TQuant 已经进入“可运行、可用、可继续治理”的阶段，但仍存在三类遗留问题：

1. **研究命名与真实实现不一致**

   - 真正 Markowitz/协方差优化；

   - 更安全的离线缓存与 PWA 能力。

## 4. 需要继续整改的真实问题

## 4.1 PKG-01 研究命名与实现一致性整改

### 4.1.1 `regime_aware_walk_forward` 不是 regime-aware

#### 当前核验

文件：`/Users/j/Documents/gupiao/backend/app/services/backtest/validator.py`

当前 `regime_aware_walk_forward()` 只是直接调用 `walk_forward()`，没有：

- 对训练窗口做市场状态标注；
- 对测试窗口按 `market_state` 分桶；
- 输出不同市场状态下的最佳参数与表现；
- 比较不同 regime 下的稳定性漂移。

#### 需求

将其改造成真正的**市场状态感知 Walk-forward 验证**：

1. 对每个 window 标注训练期主市场状态；
2. 对测试期按 `market_state` 聚合：
   - 胜率
   - 平均收益
   - Sharpe
   - 最大回撤
   - 参数漂移度
3. 输出：
   - `overall`
   - `by_market_state`
   - `best_params_by_state`
   - `state_window_details`

#### 实现方式

- 新增独立模块：
  - `backend/app/services/backtest/regime_walkforward.py`
- 保留旧接口签名不变；
- `validator.py` 中仅负责编排调用；
- 结果结构保持向后兼容，新增字段而不是替换字段。

#### 验收

- 至少 1 组样本数据下，`regime_aware_walk_forward()` 输出 `by_market_state` 非空；
- 前端/接口文案不再把普通 walk-forward 冒充 regime-aware。

#### 当前核验

- 基于历史分组统计；
- 基于结果查表；
- 不是 PPO/SAC/Q-learning 的完整训练与评估链路。

#### 需求

两种路线二选一，但必须统一：

1. **短期路线，优先推荐**

   - 所有 API / 页面 / 文档禁止再使用“强化学习”“RL 优化”字样。

2. **长期路线**
   - 另立真正 RL 模块；
   - 与当前统计研究严格区分。

#### 实现方式

- 先完成短期重命名；
- 保留数据模型兼容字段，但 UI 展示只用新名称；
- 新增说明文字：`基于历史统计归纳，非强化学习训练结果`。

#### 验收

- 代码、API、前端文案中不再出现误导性 RL 表述；
- 若保留旧字段，则仅用于兼容，不对用户显示。

### 4.1.3 “Mean-Variance optimizer” 名称误导

#### 当前核验

当前策略权重优化更接近：

- Sharpe 比例分配；
- 启发式风险预算；
- 不是基于协方差矩阵和有效前沿求解的 Markowitz 模型。

#### 需求

短期必须做的：

1. 将现有实现重命名为：
   - `heuristic_portfolio_optimizer`
   - `sharpe_weight_allocator`
   - 或 `risk_adjusted_weight_allocator`
2. 页面、接口、报告中不再写“Mean-Variance”。

中期可选：

1. 新增真正 Markowitz / Mean-Variance 优化器；
2. 单独提供 `covariance_matrix`、`frontier_points`、`constraints`。

#### 实现方式

- 新建：
  - `backend/app/services/portfolio/heuristic_optimizer.py`
  - `backend/app/services/portfolio/markowitz_optimizer.py`（预留）
- 旧服务保留兼容导出，但外部统一走新命名。

#### 验收

- 生产页面和 API 中不再把启发式分配称作 Mean-Variance；
- 若提供 Markowitz，则必须有协方差矩阵计算和约束求解结果。

## 4.2 PKG-02 Provider / 缓存 / 本地化整改

### 4.2.1 Redis 客户端失败永久缓存 `None`

#### 当前核验

文件：`/Users/j/Documents/gupiao/backend/app/services/shared/distributed_cache.py`

当前 `_redis_client()` 使用 `@lru_cache(maxsize=1)`，初始化失败后会返回 `None`，且失败态可能长期滞留。

#### 需求

改为：

1. 失败态短 TTL 缓存，例如 10-30 秒；
2. 成功态长 TTL 或进程级复用；
3. 明确区分：
   - unavailable
   - reconnecting
   - healthy

#### 实现方式

- 移除纯 `lru_cache` 方案；
- 新建 `RedisClientHolder`：
  - 成功连接缓存客户端对象；
  - 失败只缓存时间戳和错误摘要；
  - 到期后自动重试。

#### 验收

- Redis 短暂故障恢复后，无需重启进程即可重新连通；
- 健康接口可看到 redis 状态变化。

### 4.2.2 Redis Sliding Window 仍每次发送完整 Lua 脚本

#### 当前核验

文件：`/Users/j/Documents/gupiao/backend/app/core/redis_rate_limit.py`

每次请求都走 `eval()`，存在重复发送脚本文本的性能浪费。

#### 需求

改为：

1. 启动时注册脚本；
2. 运行时优先 `EVALSHA`；
3. SHA 失效时回退重注册。

#### 实现方式

- 在 `RedisSlidingWindowRateLimiter` 中维护脚本句柄；
- 封装 `_run_script()`。

#### 验收

- 正常路径不再发送完整 Lua 文本；
- Redis 重启后仍能自动恢复脚本执行。

### 4.2.3 LocalMarketProvider 对新股 `<60` 日过严

#### 当前核验

文件：`/Users/j/Documents/gupiao/backend/app/services/market/providers/local_provider.py`

当前逻辑在历史长度 `<60` 或 `latest_local_date < end_date` 时直接返回 `UNAVAILABLE`，会导致新股、本地短历史数据标的长期不可用。

#### 需求

改为分级可用：

1. `>=60` 日：正常可用；
2. `20-59` 日：`estimated` / `limited_history`；
3. `<20` 日：可返回最小可用历史并标注 `insufficient_history`；
4. 不得把“数据不足”直接等同于“不可用”。

#### 实现方式

- 新增数据质量标签：
  - `limited_history`
  - `partial_local_history`
  - `stale_local_history`
- 让调用链在策略端决定是否接受，而不是 provider 一刀切拒绝。

#### 验收

- 新股不会因为 `<60` 日历史被永久拦截；
- 前端能看到明确的数据质量提示。

### 4.2.4 LocalMarketProvider 仅覆盖日线/交易日历，实时行情仍依赖外部

#### 当前核验

这是实情，不是误报。

#### 需求

推进“本地数据优先模式”第二阶段：

1. 建立本地实时 quote 缓存层；
2. 由后台采集任务定期刷新主流标的报价；
3. API 读本地缓存，外部 provider 只做补齐/回源；
4. 明确 `fresh / stale / estimated / unavailable` 四级质量状态。

#### 实现方式

- 新增本地 quote 表或 Redis hash；
- 新建采集任务：
  - `market_quote_collector`
- Web/API 默认优先读本地；
- Provider Router 只在本地缺失或过期时回源。

#### 验收

- 常用行情接口在外部源短时失败时仍能返回最近可用报价；
- 返回结构中包含本地/外部来源与质量标签。

## 4.3 PKG-03 前端离线与安全边界整改

### 4.3.1 离线缓存仍为明文 `localStorage`

#### 当前核验

文件：`/Users/j/Documents/gupiao/frontend/src/api/base.ts`

当前离线缓存只是：

- TTL 缩短；
- logout 清理；
- 但仍是明文 JSON 写 `localStorage`。

#### 需求

短期：

1. 严格限制缓存内容：
   - 不缓存任何 token；
   - 不缓存敏感配置；
   - 不缓存用户隐私字段；

   - 优先榜摘要；

2. 实现版本化清理与离线回退页。

#### 实现方式

- 先增加缓存白名单；
- 再逐步引入 `service-worker.ts` 和离线缓存策略。

#### 验收

- `localStorage` 中不再出现高敏数据；
- 离线缓存命中场景与失效场景可区分；

## 4.4 PKG-04 回测并发与研究能力整改

### 4.4.1 回测并发“完全无限制”表述过重，但仍需补强

#### 当前核验

当前代码中已经存在：

- `max_concurrent_backtests`；
- 运行中任务计数限制；
- MySQL claim lock 防重复领取。

因此“完全没有并发限制”这一说法已不准确。

#### 真实问题

仍需补的不是“有没有限制”，而是：

1. Python 进程级并发令牌是否明确；
2. CPU 密集计算是否会冲垮 API；
3. 多类回测任务是否有分级调度；
4. 队列等待时间与并发数是否对外可观测。

#### 需求

1. 明确回测并发闸门实现与配置项；
2. 输出运行中数量、排队数量、估算等待时间；
3. 区分轻量验证 / 完整回测 / walk-forward 的资源级别。

#### 实现方式

- 强化：
  - `backtest_worker.py`
  - `backtest_queue_metrics.py`
- 加可观测字段：
  - `current_running`
  - `queue_depth`
  - `estimated_wait_seconds`

#### 验收

- 同时提交多任务时不会拖垮 API；
- UI 能看到任务排队与资源状态。

## 9. 最终判断

对 Claude v5 报告的最终判断如下：

1. **总体方向合理**，尤其是对命名一致性、Provider 稳定性、缓存安全和本地数据能力的判断是对的。
2. **存在部分表述过重**，例如“回测并发仍无限制”在当前代码下已经不够准确，应该改成“已有基础限制，但仍需显式化与验收”。
3. **有些内容属于发展方向，不是现存 bug**，例如真正 Markowitz、真正 RL、PWA，不应混写成当前阻塞项。
4. **最值得优先做的不是再堆新功能，而是把研究命名、provider 退化路径、缓存安全和本地行情能力补齐**。

因此，后续开发应以本文档为准，而不是直接照抄 v5 报告原文。
