## 2. 当前代码基线

### 2.1 已确认问题

#### S1：生产策略分层与 24M 证据脱节

当前 `backend/app/services/low_buy/strategy_policy.py` 仍将两个 N 字策略放在 CORE：

- `CORE_STRATEGIES` 包含 `n_pattern_long_wash`、`n_pattern_short_wash`
- `PRODUCTION_PRIORITY_STRATEGIES = CORE_STRATEGIES | AUXILIARY_STRATEGIES`
- `participates_in_priority_board()` 只看静态 tier

而 `docs/reports/strategy_24m_duckdb_report.md` 显示：

- `n_pattern_long_wash`：成交 1585，最大回撤 -51.15%，建议 `default_off`
- `n_pattern_short_wash`：成交 1571，最大回撤 -88.63%，PF 0.72，建议 `delete_candidate`

结论：**S1 可接受为 P0，必须修。**

#### D2：DuckDB 24M 报告口径误导

当前 `backend/app/services/analytics/report_queries.py` 在 Markdown 表头中输出：

```text
| 策略 | 样本 | 成交 | 总收益 | 最大回撤 | PF | 平均单笔 | 建议 |
```

但权威 Python 报告已把收益拆成：

- 每日信号等权复利收益

## 4. 目标状态

整改完成后，平台应满足：

1. 生产策略集合只包含 24M 门禁通过的策略。
2. N 字策略不再作为 CORE/AUXILIARY 进入生产榜和模拟盘自动交易。
3. DuckDB 24M 报告明确区分“每日信号等权复利收益”和“真实组合 max5/max10 收益”。
4. Analytics worker 在 compose 中可启动，可消费 `strategy_24m_duckdb_report` 等任务。
5. CI 每次 PR 都运行 OpenAPI 契约检查，后端字段漂移会让 CI 失败。
6. Web 主进程默认不跑重型研究 loop，研究任务必须通过 Worker 或显式 flag 启用。
7. 新产生的大体量 JSON 报告默认进入 `backend/data/analytics/reports/` 或外部 artifact，不继续污染 `docs/reports`。
8. 前端扫描型大表默认走虚拟滚动，自定义卡片/列表走 `VirtualCardList`，不再用非业务性 `.slice(0,N)` 控制 DOM。
9. 前端渲染性能护栏进入 lint/check 或 PR 检查，防止大列表回退到 raw `<Table>`、分页兜底或人为截断。

### 7.1 目标

让 24M 数据检查、Parquet 导出、DuckDB 报告在部署环境中可运行、可观测、可重试，而不是只在本地脚本存在。

- `PRODUCTION_RUNBOOK.md`

### 7.3 实施要求

1. `Dockerfile` 新增：

```dockerfile
ARG INSTALL_ANALYTICS=0
COPY backend/requirements-analytics.txt /tmp/backend-requirements-analytics.txt
RUN if [ "$INSTALL_ANALYTICS" = "1" ]; then \
      pip install --retries 8 -r /tmp/backend-requirements-analytics.txt; \
    fi
```

2. `docker-compose.mysql.yml` 新增 `analytics-worker`：

```yaml
analytics-worker:
  build:
    context: .
    dockerfile: Dockerfile
    args:
      INSTALL_ANALYTICS: "1"
  image: tquant-analytics:mysql
  restart: unless-stopped
  depends_on:
    mysql:
      condition: service_healthy
    redis:
      condition: service_healthy
    migration:
      condition: service_completed_successfully
  command: ["python", "backend/scripts/analytics_worker.py", "--poll-interval-seconds", "2"]
  environment:
    TQUANT_ANALYTICS_ENABLED: "true"
    TQUANT_ANALYTICS_ROOT: /app/backend/data/analytics
    TQUANT_DUCKDB_THREADS: ${TQUANT_DUCKDB_THREADS:-2}
  volumes:
    - app_runtime_data:/app/backend/data
```

实际命令路径需按容器 `WORKDIR=/app/backend` 调整，可以使用 `python /app/backend/scripts/analytics_worker.py` 或 `python -m app...`，以实测为准。

3. `analytics/__init__.py` 增加依赖探测函数，例如：

```python
def analytics_dependencies_ready() -> tuple[bool, str]:
    try:
        import duckdb  # noqa
        import pyarrow  # noqa
    except Exception as exc:
        return False, str(exc)
    return True, "ok"
```

4. `/readyz` 增加 analytics 状态：
   - 未启用时：`disabled`
   - 启用且依赖存在：`ok`
   - 启用但依赖缺失：`degraded` 或 `failed`
5. RuntimeTask API 提交 `strategy_24m_duckdb_report` 后，必须能被 `analytics-worker` 消费。
6. `data_backfill_24m` 如果失败，任务必须明确失败，不允许永久 queued/running。

### 7.4 验收

本地/服务器均需通过：

```bash
docker compose -f docker-compose.mysql.yml build analytics-worker
docker compose -f docker-compose.mysql.yml up -d analytics-worker
docker compose -f docker-compose.mysql.yml exec analytics-worker python -c "import duckdb, pyarrow; print('ok')"
```

提交任务：

```bash
curl -X POST "$BASE_URL/api/runtime-tasks" \
  -H "Authorization: Bearer $ADMIN_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"task_type":"strategy_24m_duckdb_report","payload":{"months":24,"manifest":"latest"}}'
```

```ts
type DataTableProps<RecordType extends object> = TableProps<RecordType> & {
  paginated?: boolean;
  virtualized?: boolean;
  defaultScrollY?: number;
};
```

2. 默认行为：

- `expandable`
- `rowSpan` / `colSpan`
