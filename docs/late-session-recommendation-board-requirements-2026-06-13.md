# 尾盘推荐榜需求文档（2026-06-13）

> 目标：新增独立的“尾盘推荐榜 / late session recommendation board”，在不改变现有生产优先榜、`production_score`、策略准入和排序语义的前提下，基于已物化生产候选做 14:50-14:57 的尾盘轻确认，并在 14:55/14:57 固化尾盘快照。
>
> 本文档是需求与验收口径，不授权直接部署、不授权切流、不授权修改生产策略语义。

## 1. 背景

当前平台已有低吸优先榜 `priority_board`，用于盘中观察、监控页展示、行情缓存、策略追踪、物化热读和回测对齐。线上性能核验显示：

| 项目 | 当前表现 | 结论 |
| --- | --- | --- |
| priority board 热读 | 约 11ms | 足够支撑尾盘轻量读取 |
| 实时价格 overlay | 约 7ms | 足够支撑尾盘确认 |
| 常规低吸物化 | 多数 7-26s | 可在尾盘前完成 |
| 偶发慢物化 | 约 186-221s | 不适合 14:50 后才全量重算 |
| 线上资源 | load 约 0.7，available memory 约 1.1GiB，swap 仍有使用 | 可以做轻确认，不宜在尾盘窗口叠加重任务 |

因此尾盘推荐不能设计为“14:50 后全市场重新扫描”。正确形态是：

1. 14:30-14:45 提前完成低吸候选和 priority board 主物化。
2. 14:50-14:57 只读取已物化候选，叠加实时价格、VWAP、分钟线、尾盘承接和市场状态做轻量确认。
3. 14:55 固化第一版尾盘快照，14:57 固化最终确认快照。
4. 数据不足或外部源异常时降级为“尾盘观察”，不生成正式推荐。

## 2. 问题陈述

用户希望把当前策略推荐从“全天观察/盘中推荐”进一步转成更接近实盘执行的“尾盘推荐”。尾盘推荐的核心价值是减少盘中波动干扰，在收盘前根据承接、VWAP、价格位置和市场状态确认是否具备次日预期。

如果直接替换现有 `priority_board`，会带来以下风险：

1. 改变现有生产优先榜排序和历史可比性。
2. 影响 monitor、strategy-tracking、行情缓存、物化和回测链路。
3. 把尚未独立验证的尾盘过滤条件混入生产策略语义。
4. 在 14:50 后触发全量重任务，可能错过 14:55/14:57 固化窗口。

所以本需求采用新增独立尾盘榜，而不是改写当前默认榜。

## 3. 目标

1. 新增独立“尾盘推荐榜”，用于 14:50-14:57 的尾盘轻确认和展示。
2. 尾盘推荐只从当前生产 priority board 候选中二次筛选，不从全市场重新扫描。
3. 固化 14:55 第一版快照和 14:57 最终快照。
4. 保留现有 `priority_board` 作为全天观察和盘中监控主榜。
5. 尾盘推荐明确区分“正式尾盘推荐”“尾盘观察”“数据不足/降级”。
6. 支持回测/复盘对比：原优先榜 vs 尾盘确认榜。
7. 不影响核心任务：监控、行情缓存、低吸榜、priority board、策略追踪继续运行。

## 4. 非目标

1. 不直接修改 `backend/app/services/low_buy/strategy_policy.py`。
2. 不改变 `production_score`、priority board 默认排序、生产策略准入和生产风控语义。
3. 不把 research/factor 策略直接纳入尾盘正式推荐。
4. 不做自动下单。
5. 不在 Web 请求中触发全量低吸扫描、24M 回测、DuckDB 报告或重分析任务。
6. 不承诺尾盘推荐一定提高收益，只交付可验证、可降级、可回测的尾盘确认链路。

## 5. 硬边界

1. 现有 `priority_board` 默认 API、排序、字段含义保持兼容。
2. 尾盘榜必须是新增契约或新增参数，不能覆盖默认 `priority_board`。
3. 前端不得重算生产策略口径；尾盘推荐状态以后端返回为准。
4. 数据不足必须显式返回 `partial_data`、`minute_data_missing`、`quote_unavailable` 或等价状态。
5. 分钟线、VWAP、实时行情任一关键输入不可用时，不得输出“正式推荐”，只能输出“观察/降级”。
6. 14:50 后不得启动全市场重算；只允许轻确认和快照固化。
7. 任何后续生产升权或策略准入变化必须另走 24M、walk-forward、OOS、守卫测试和用户授权。

## 6. 策略来源

尾盘推荐只从现有生产优先榜候选中筛选，策略范围如下：

| 策略 key | 层级 | 是否进入尾盘正式推荐候选 | 说明 |
| --- | --- | --- | --- |
| `first_board` | core | 是 | 首板/强势股回调类，需尾盘不转弱、不过度追高 |
| `volume_shrink` | core | 是 | 量能低吸类，需确认缩量回踩后尾盘承接仍成立 |
| `late_session_strong_support` | auxiliary | 是，但低样本限权 | 本身适配尾盘承接，但样本较低，权重和推荐等级需受限 |

以下策略只能作为研究或观察标签，不进入尾盘正式推荐：

| 策略集合 | 处理方式 |
| --- | --- |
| `classic_retrace`、`ma_support`、`breakout_support` 等 research 策略 | 可展示“研究共振”，不参与正式尾盘推荐 |
| `deep_pullback`、`trend_rebound` 等 factor 策略 | 只做观察/研究标签 |
| `sector_mainline_first_divergence_low_buy`、`mainline_limitup_shrink_retrace_reclaim` 等主线研究策略 | 需另走样本验证，不能直接入生产尾盘榜 |

## 7. 核心用户故事

1. 作为交易用户，我想在 14:50 后看到一份尾盘候选列表，以便判断哪些票接近收盘仍保持承接。
2. 作为交易用户，我想区分“正式尾盘推荐”和“仅观察”，以便避免把数据不足或承接不足的票误当成买点。
3. 作为交易用户，我想看到每只票通过或失败的尾盘确认原因，以便知道是 VWAP、支撑位、价格位置还是市场状态导致过滤。
4. 作为交易用户，我想看到 14:55 和 14:57 两个快照，以便判断尾盘最后几分钟是否转弱。
5. 作为交易用户，我想保留原 priority board，以便继续做全天观察和策略追踪。
6. 作为策略研究者，我想对比原优先榜和尾盘确认榜的次日表现，以便验证尾盘过滤是否真正改善收益质量。
7. 作为运维者，我想尾盘确认任务轻量、可降级、可监控，以便不影响主服务和其他核心任务。

## 8. 业务流程

### 8.1 标准交易日流程

| 时间 | 动作 | 类型 | 超时建议 | 失败处理 |
| --- | --- | --- | ---: | --- |
| 14:30-14:45 | 确认低吸候选和 priority board 主物化已完成 | 后台任务 | 3 分钟 | 未完成则标记尾盘榜 `blocked_by_materialization` |
| 14:50 | 生成尾盘预警榜 | 轻任务 | 20 秒 | 降级为观察榜 |
| 14:55 | 固化第一版尾盘快照 | 轻任务 + 写快照 | 20 秒 | 保留 14:50 预警并标记 `snapshot_failed` |
| 14:57 | 固化最终尾盘快照 | 轻任务 + 写快照 | 20 秒 | 保留 14:55 快照并标记 `final_snapshot_failed` |
| 15:00 后 | 只读展示和复盘，不再改写尾盘推荐结果 | 只读 | - | - |

### 8.2 非交易日或非尾盘时段

1. 非交易日返回最近一个交易日尾盘快照，并标记 `historical_snapshot`。
2. 14:50 前允许展示“今日尾盘榜待生成”，可提供上一交易日回看。
3. 14:57 后展示最终快照，不再触发实时重算。
4. 数据源异常时展示降级状态，不返回空白页。

## 9. 尾盘筛选规则

尾盘推荐筛选链路：

```text
priority_board 生产候选
  -> 策略白名单过滤
  -> 价格位置过滤
  -> VWAP/支撑/分钟线确认
  -> 市场状态与板块状态过滤
  -> 风险过滤
  -> 尾盘推荐分层
  -> 14:55/14:57 快照固化
```

### 9.1 基础候选过滤

必须满足：

1. 来自当前交易日 `priority_board`。
2. `strategy_key` 属于 `first_board`、`volume_shrink`、`late_session_strong_support`。
3. 不处于明显风险标签，例如跌停、停牌、严重事件风险、放量破位。
4. 价格仍在低吸区、接近低吸区或不超过策略允许的追高距离。
5. priority board 原始状态不能是明确 `avoid`，除非后端已有明确的可观察恢复状态。

### 9.2 VWAP 与分钟线确认

必须计算：

1. 当日 VWAP。
2. 最新价是否站上或接近 VWAP。
3. 14:30 后是否持续弱于 VWAP。
4. 最近若干分钟低点是否抬高。
5. 尾盘是否存在放量砸盘或直线拉升。

推荐通过条件：

| 条件 | 正式推荐要求 |
| --- | --- |
| 最新价相对 VWAP | 不低于 VWAP 附近，建议 `>= VWAP * 0.998` |
| 尾盘低点 | 不持续下移 |
| 尾盘强度 | 收盘位置不在日内振幅下半区 |
| 尾盘拉升 | 不允许 14:50 后无回踩直线拉升过大 |
| 成交量 | 不能出现明显放量砸盘 |

### 9.3 市场和板块过滤

必须考虑：

1. 市场状态是否 `allow`、`reduce` 或 `block`。
2. 上涨家数、跌停家数、炸板率等情绪指标是否异常。
3. 个股所属板块是否尾盘同步走弱。
4. 主线板块是否存在回流。

处理规则：

| 市场状态 | 尾盘榜处理 |
| --- | --- |
| `allow` | 可输出正式尾盘推荐 |
| `reduce` | 只允许低仓位/观察优先，推荐数量收缩 |
| `block` | 不输出正式推荐，只输出观察或空榜 |
| 数据缺失 | 标记 `market_context_missing`，不输出正式推荐 |

### 9.4 推荐分层

尾盘榜输出分层：

| 层级 | 含义 | 展示建议 |
| --- | --- | --- |
| `late_confirmed` | 尾盘确认通过，可进入正式尾盘推荐 | 强调“小仓观察/按计划执行”，避免承诺收益 |
| `late_watch` | 结构还可以，但尾盘确认不足 | 只观察，不作为正式推荐 |
| `late_rejected` | 尾盘转弱、追高、破 VWAP、市场阻断等 | 展示过滤原因 |
| `late_unavailable` | 数据不足或任务失败 | 展示降级原因 |

## 10. 数据需求

### 10.1 输入数据

| 数据 | 必需性 | 用途 |
| --- | --- | --- |
| 当前交易日 priority board read model | 必需 | 候选池来源 |
| 实时行情 / quote cache | 必需 | 最新价、涨跌幅、时间戳 |
| 分钟线 | 必需 | VWAP、尾盘低点、尾盘强度 |
| 市场状态 | 必需 | allow/reduce/block |
| 行业/板块上下文 | 强建议 | 板块同步和主线判断 |
| 用户行业排除设置 | 必需 | 与现有 priority board 用户过滤一致 |

### 10.2 输出数据

尾盘榜响应需要包含：

1. `trade_date`
2. `snapshot_slot`：`preview_1450`、`snapshot_1455`、`final_1457`
3. `generated_at`
4. `source_priority_board_epoch`
5. `status`：`ok`、`partial_data`、`blocked`、`unavailable`
6. `items`
7. `data_quality`
8. `data_quality_tags`
9. `degradation_reason`
10. `next_refresh_at`

每个 item 至少包含：

1. 现有 priority board 基础字段：`symbol`、`name`、`strategy_key`、`priority_score`、`production_score`、`buy_signal_state`
2. 尾盘字段：`late_session_state`、`late_session_score`、`late_session_reason`
3. 确认字段：`vwap`、`latest_price`、`above_vwap`、`late_session_strength`、`low_rising`
4. 风险字段：`risk_tags`、`reject_reasons`
5. 快照字段：`quote_timestamp`、`snapshot_slot`

## 11. API 需求

建议新增独立接口，而不是扩展默认 `priority-board` 语义：

```text
GET /api/screeners/low-buy/late-session-board
```

查询参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `limit` | `12` | 返回数量，建议 3-30 |
| `slot` | `latest` | `preview_1450`、`snapshot_1455`、`final_1457`、`latest` |
| `refresh` | `cache` | `cache`、`async`、`sync`；Web 默认不允许重任务 sync |
| `strategy_variant` | `baseline` | 与 priority board 保持兼容 |

响应要求：

1. 未登录保持现有鉴权行为。
2. 默认返回缓存或快照，不做全量重算。
3. `refresh=async` 只能排队轻量尾盘确认任务。
4. `refresh=sync` 仅管理员或内部任务允许，用于验收和运维。
5. 响应必须兼容前端空态、降级态和部分数据态。

## 12. 后台任务需求

新增轻量 runtime task：

```text
late_session_recommendation_refresh
```

任务职责：

1. 读取当前交易日 priority board read model。
2. 读取候选股票 quote cache 和分钟线。
3. 计算 VWAP、尾盘强度、支撑承接、风险过滤。
4. 写入尾盘快照缓存/快照表。
5. 输出任务结果、item 数量、降级原因和耗时。

任务约束：

1. 不做全市场扫描。
2. 不重新计算生产策略分。
3. 不修改原 priority board 快照。
4. 超时后写降级结果，不阻塞其他 runtime task。
5. 14:50、14:55、14:57 任务使用不同 idempotency key。

## 13. 缓存与快照

建议新增稳定 read model：

```text
late_session_board:{trade_date}:{slot}:{strategy_variant}:{source_epoch}:{user_filter_hash}
```

TTL 建议：

| 缓存 | TTL | 说明 |
| --- | ---: | --- |
| 14:50 预警 | 10 分钟 | 只服务尾盘窗口 |
| 14:55 快照 | 6 小时 | 交易日内稳定展示 |
| 14:57 最终快照 | 7 天 | 支持复盘和回看 |
| overlay 实时价 | 2-5 秒 | 与现有实时 overlay 保持轻量 |

快照固化要求：

1. `final_1457` 不应被 15:00 后实时行情覆盖。
2. 新一轮 priority board 发布后，尾盘榜应通过 `source_epoch` 自动失效。
3. 用户行业过滤不能污染全局快照；用户过滤结果应按 `user_filter_hash` 做派生缓存。

## 14. 前端需求

### 14.1 页面入口

建议在以下位置展示：

1. `/next/monitor`：尾盘时间段显示简洁模块。
2. `/next/monitor/market`：显示市场/板块尾盘状态。
3. `/next/strategy-tracking`：支持尾盘榜复盘和历史对比。
4. `/next/playbook` 或低吸相关页面：展示策略解释和过滤原因。

### 14.2 展示内容

每只票展示：

1. 股票代码、名称、策略来源。
2. 尾盘状态：确认、观察、剔除、数据不足。
3. 尾盘确认原因：VWAP、低点抬高、收盘位置、市场状态。
4. 风险标签：追高、破 VWAP、尾盘砸盘、板块走弱、数据缺失。
5. 快照时间：14:50、14:55、14:57。
6. 数据质量标签。

文案要求：

1. 使用“尾盘确认”“尾盘观察”“不满足尾盘确认”，避免“必涨”“建议买入”“立即买入”等承诺性文案。
2. 数据不足时明确说明“仅供观察，不作为尾盘推荐”。
3. 保留后端返回顺序，不在前端重新计算生产排序。

## 15. 性能需求

| 场景 | 目标 |
| --- | ---: |
| late-session board 热读 p95 | <= 300ms |
| 14:50 轻确认任务 | <= 20s |
| 14:55/14:57 固化任务 | <= 20s |
| 候选数 | 默认读取 priority board 前 30，只返回前 12 |
| 外部行情超时 | 单次 provider 调用 <= 3s，整体可降级 |
| Web 请求 | 不触发全量低吸扫描 |

若 14:50 轻确认任务超过 20 秒，应返回上一快照或降级态，不阻塞页面。

## 16. 降级与异常处理

| 异常 | 用户可见状态 | 系统行为 |
| --- | --- | --- |
| priority board 未物化 | `blocked_by_materialization` | 不启动全量重算，提示等待主榜完成 |
| quote cache 缺失 | `quote_unavailable` | 降级观察，不正式推荐 |
| 分钟线缺失 | `minute_data_missing` | 降级观察 |
| VWAP 不可计算 | `vwap_unavailable` | 降级观察 |
| 市场状态缺失 | `market_context_missing` | 不输出正式推荐 |
| 外部行情源超时 | `partial_data` | 保留已有快照 |
| 任务未完成 | `refresh_queued` | 前端展示后台刷新中 |

## 17. 回测与复盘需求

必须支持以下对比：

1. 原 priority board top N。
2. 尾盘确认榜 `late_confirmed`。
3. 尾盘观察榜 `late_watch`。
4. 被尾盘规则剔除的样本。

指标：

1. T+1 开盘收益。
2. T+1 最高收益。
3. T+1 10:30 前最高收益。
4. T+1 收盘收益。
5. T+2 收盘收益。
6. 净胜率。
7. PF。
8. 平均单笔收益。
9. 最大回撤。
10. 样本留存率。
11. 数据缺失率。

最低研究验收：

1. 样本留存 >= 原生产候选的 60%。
2. OOS 不明显劣化。
3. 数据缺失率明确披露。
4. 不用 `max_gain` 冒充可成交收益。

## 18. 测试需求

### 18.1 后端单元测试

必须覆盖：

1. 策略白名单：只允许 `first_board`、`volume_shrink`、`late_session_strong_support` 进入正式尾盘候选。
2. research/factor 策略只输出观察标签，不进入正式推荐。
3. 无分钟数据时返回 `minute_data_missing`。
4. 低于 VWAP 时降级为 `late_watch` 或 `late_rejected`。
5. 尾盘确认通过时返回 `late_confirmed`。
6. 市场 `block` 时不输出正式推荐。
7. `late_session_strong_support` 受低样本限权。
8. 用户行业排除过滤不改变全局快照。
9. 14:55/14:57 快照不会被 15:00 后实时价覆盖。

### 18.2 API 测试

必须覆盖：

1. 未登录返回 401。
2. `cache` 模式不触发全量扫描。
3. `async` 模式只排队轻量尾盘任务。
4. `sync` 权限受控。
5. 缓存命中返回稳定响应。
6. 降级态响应 schema 完整。

### 18.3 前端测试

必须覆盖：

1. 正常尾盘榜。
2. 空榜。
3. 数据不足。
4. 后台刷新中。
5. 14:55/14:57 快照切换。
6. 权限不足。
7. 接口失败。
8. 文案不出现“必涨”“建议买入”“立即买入”等禁用表达。

### 18.4 性能与线上验收

必须覆盖：

1. `late_session_board` p95 <= 300ms。
2. 14:50、14:55、14:57 任务均 <= 20s 或明确降级。
3. 不增加 priority board p95。
4. 不增加 runtime task 明显积压。
5. 主入口 `/readyz`、`/next/monitor`、`/api/screeners/low-buy/priority-board` 行为不回退。

## 19. 验收标准

### 19.1 功能验收

1. `/api/screeners/low-buy/late-session-board` 可返回当前交易日尾盘榜。
2. 14:50 预警、14:55 快照、14:57 最终快照可区分。
3. 返回项包含策略来源、尾盘状态、确认原因、风险标签和数据质量。
4. 尾盘榜只从当前 priority board 生产候选派生。
5. 原 `priority_board` API 返回顺序和字段语义不变。

### 19.2 策略边界验收

1. `strategy_policy.py` 无变更，除非后续有单独授权。
2. `production_score` 无语义变更。
3. `priority_board` 默认排序 hash 在同输入下不变。
4. research/factor 策略不进入正式尾盘推荐。

### 19.3 运行验收

1. Web 主进程不做尾盘全量扫描。
2. runtime worker 可执行轻量尾盘任务。
3. 数据不足时页面可用且明确降级。
4. 不影响行情缓存、低吸榜物化、priority board 物化、策略追踪。

## 20. 分阶段交付

### Phase 1：后端只读派生与本地验证

1. 新增尾盘榜 service。
2. 新增尾盘确认状态模型。
3. 新增 API，只读返回派生结果。
4. 补齐单元测试和 API 测试。
5. 不写快照、不接调度。

### Phase 2：快照固化与 runtime task

1. 新增 `late_session_recommendation_refresh` 任务。
2. 固化 14:55/14:57 快照。
3. 增加缓存 epoch 和 TTL。
4. 增加任务耗时、降级原因和数据质量指标。

### Phase 3：前端展示

1. `/next/monitor` 增加尾盘模块。
2. `/next/strategy-tracking` 增加尾盘复盘。
3. 增加状态、空态、降级态、错误态。
4. 增加截图和页面冒烟测试。

### Phase 4：研究回测与生产评审

1. 输出尾盘榜 vs 原 priority board 的对比报告。
2. 覆盖至少 3-6 个月样本。
3. 数据足够后再评估是否进入更强生产展示。

## 21. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 14:50 后全量重算超时 | 错过固化窗口，影响服务 | 只做已物化候选轻确认 |
| 分钟数据不足 | 误判尾盘承接 | 显式降级，不正式推荐 |
| 外部行情源异常 | 页面 stale 或无价格 | 使用 quote cache 和降级态 |
| research 策略误入生产 | 策略口径污染 | 白名单和测试守卫 |
| 前端重排 | 与后端事实源不一致 | 前端只展示后端顺序 |
| 用户误解为买入指令 | 合规和使用风险 | 文案使用“确认/观察”，不使用承诺性表达 |
