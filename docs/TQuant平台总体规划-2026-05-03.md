## 总体判断

TQuant 已从行情面板进化为一个 **"策略研究 → 信号评分 → 模拟执行 → 绩效归因 → Agent 交互"的闭环平台雏形**。

当前最核心的矛盾不是功能不足，而是**可信度治理不够**——系统能出信号、能模拟交易、能展示结果，但缺乏足够的证据链来回答：

- 信号为什么出现？
- 交易为什么发生？
- 亏损是策略失效、市场环境不匹配，还是执行摩擦？
- 哪些策略应该加权，哪些应该降权或暂停？
- Agent 是否只能在安全边界内行动？

**核心指导原则**：短期不要继续加策略、加因子、加页面。优先把平台打造成**可复盘、可归因、可控风险**的策略实验系统。下一步最重要的目标不是"更聪明"，而是"更可信"。

## 一、金融策略体系

### 1.1 从"多策略堆叠"转向"策略治理"

当前 12 个策略、21 个因子、4 层分级已经足够。继续加策略的边际收益不高，反而增加噪音。

**每个策略必须定义的标准文档：**

```
├── 适用市场状态（哪些 regime 下可执行）
├── 禁用市场状态（哪些 regime 下自动关闭）
├── 入场条件（精确、可量化、无歧义）
├── 失效条件（什么情况下判定信号作废）
├── 止损规则（硬止损 + 追踪止损）
├── 止盈或退出规则（目标位 / 时间退出 / 信号反转）
├── 最小样本量（至少 N 笔成交才进入统计）
└── 月度绩效归因（策略自身表现 vs 市场基准）
```

**策略四问——每个策略上岗前必须能回答：**

1. 它在哪种市场里有效？
2. 它在哪种市场里亏钱？
3. 它的收益来自胜率，还是盈亏比？
4. 它是不是只在少数极端样本里赚钱？是否与其他策略高度重复？

不能回答这四个问题的策略，只能留在 RESEARCH 层，不得进入自动模拟交易。

### 1.2 策略分层准入标准

| 层级 | 准入条件 | 权限 |
|------|----------|------|
| **CORE** | ≥60 交易日样本 + ≥30 笔模拟成交 + 正期望 + 最大回撤可接受 + 不依赖主观解释 + 有明确止损和退出规则 | 可进入自动交易，参与核心绩效排名 |
| **AUXILIARY** | 可作为 CORE 策略的增强条件 | 不能单独触发重仓，可调节仓位权重 |
| **RESEARCH** | 不限 | 只生成观察信号，不进入自动执行，不参与核心排名 |
| **FACTOR** | 不限 | 只作为评分变量，不直接生成买卖建议 |

### 1.3 策略健康度评分与自动降权/淘汰

**每周自动计算 `strategy_health_score`：**

```
strategy_health_score =
    期望收益得分
  + 盈亏比得分
  + 回撤控制得分
  + 样本稳定性得分
  + 市场适配得分
  - 连续亏损惩罚
  - 低样本惩罚
  - 高换手惩罚
```

**策略状态五级：**

| 状态 | 含义 | 行为 |
|------|------|------|
| `active` | 可执行 | 正常参与信号生成和执行 |
| `watch` | 降权观察 | 仓位权重减半，前端标记黄色 |
| `paused` | 暂停执行 | 不生成新信号，已有持仓按退出规则处理 |
| `research` | 仅研究 | 回到研究层，等待改进 |
| `deprecated` | 下线 | 从生产策略列表中移除 |

**降权触发条件：**
- 连续 N 笔亏损（N 可配置，建议默认 5）
- 当前市场状态与策略适配矩阵不匹配
- 月度回撤超过阈值
- 样本不足（< 最小样本量）

降权不应靠人工记忆处理——系统自动执行，人工确认。

### 1.4 绩效指标标准化

模拟盘和绩效看板必须展示：

| 指标 | 说明 | 重要程度 |
|------|------|----------|
| 胜率 | 盈利笔数 / 总笔数 | 基础 |
| 平均盈利 | 盈利交易的平均收益率 | 基础 |
| 平均亏损 | 亏损交易的平均收益率 | 基础 |
| 盈亏比 | 平均盈利 / abs(平均亏损) | **关键** |
| 期望收益 | 胜率 × 平均盈利 - 亏损率 × 平均亏损 | **最关键** |
| 最大回撤 | 净值曲线最大回撤 | 基础 |
| 平均持仓周期 | 从开仓到平仓的平均时间 | 基础 |
| 单笔交易成本占比 | 佣金 + 印花税 + 滑点 / 成交金额 | 基础 |
| MFE（最大浮盈） | 持仓期间达到的最大浮动盈利 | 进阶 |
| MAE（最大浮亏） | 持仓期间达到的最大浮动亏损 | 进阶 |

**关键提醒**：胜率 65% 但平均亏损是平均盈利的 2 倍 → 期望收益可能为负。不要只看胜率。

### 1.5 市场状态过滤

**市场状态六分类：**

```
├── 强势主升     （激进做多）
├── 震荡轮动     （低吸为主）
├── 弱势修复     （谨慎低吸）
├── 下跌退潮     （停止低吸）
├── 极端风险     （空仓）
└── 缩量无主线   （空仓或极轻仓）
```

**每个信号必须绑定市场状态快照：**

```
market_regime        # 市场状态分类
market_breadth       # 市场宽度（上涨比例、中位涨跌）
limit_up_count       # 涨停数
limit_down_count     # 跌停数
hot_sector_count     # 热点板块数
leading_sector       # 领涨板块
risk_appetite        # 风险偏好指标
turnover_level       # 成交额水平
```

**强制要求**：每个策略必须统计在不同 `market_regime` 下的收益表现。如果某策略只在强势主升有效，弱势退潮时应自动关闭——不靠人工记忆，系统自动阻断。

### 1.6 板块与龙头逻辑

当前策略体系偏量化，但 A 股短线还需要板块结构判断。

**四类补充状态：**

| 类别 | 指标 |
|------|------|
| **板块强度** | 板块涨幅、成交额放大、涨停数、板块内上涨比例 |
| **龙头识别** | 连板高度、首板强度、封单质量、换手承接、是否带动板块 |
| **情绪周期** | 冰点 → 修复 → 主升 → 分歧 → 退潮 |
| **主线确认** | 连续 2-3 日资金回流、多梯队存在、中军趋势股配合 |

个股信号没有板块上下文，可靠度会明显下降——这不是锦上添花，是短线系统的核心组件。

### 1.7 魔法数字治理

70+ 硬编码阈值按性质分为三类：

| 类别 | 性质 | 存放位置 | 可否前端修改 |
|------|------|----------|-------------|
| **制度硬约束** | A 股规则：100 股整数倍、T+1、涨跌停限制、ETF/T+0 | 代码常量 | ❌ 不可改 |
| **风控硬约束** | 单票最大仓位、单日最大买入、最大回撤熔断、连续亏损熔断 | 版本化配置文件 | ❌ 不可前端改 |
| **策略经验参数** | 最低评分、成交额阈值、回撤比例、均线距离 | LowBuyThresholds 数据类 | ✅ 可配置，需审计 |

只有第三类适合开放配置。前两类必须集中管理，版本化，不能被随意改坏。

### 1.8 因子治理

每个因子必须有明确状态标记：

```
active        # 已接入数据源，正常参与评分
stub          # 骨架代码，数据源未接入
experimental  # 实验性因子，结果仅供参考
deprecated    # 已废弃
disabled      # 人工关闭
```

当前 7/21 个因子为 stub 状态（永久返回 0），前端必须明确展示：

```
北向资金因子：未启用，数据源未接入
融资余额因子：研究中，不参与评分
```

不要让未实现因子参与策略解释——这是一个可信度问题，不是功能问题。

## 二、数据与金融工程

### 2.1 数据源分层

免费替代 Tushare 是可行的，但要明确分工：

| 数据类型 | 主数据源 | 备选 | 备注 |
|----------|----------|------|------|
| 实时行情 | 东方财富 / 腾讯 | 新浪 | 已有 4 层降级链 |
| 历史日线 | BaoStock | AkShare | 前复权 |
| F10 / 财务 / 股东 | AkShare | 巨潮接口 | 非实时 |
| 板块与概念 | 东方财富 | AkShare | |
| 新闻与研报 | AkShare / RSS | | 按需 |
| 交易日历 | AkShare / BaoStock | | 缓存在 DB |

不假设一个免费源能解决所有问题。

### 2.2 数据质量标签

所有行情和因子数据必须附带标准质量元数据：

```json
{
  "symbol": "000001",
  "source": "eastmoney",
  "fetched_at": "2026-05-03 10:30:00",
  "trade_date": "2026-05-03",
  "is_stale": false,
  "is_suspended": false,
  "missing_fields": [],
  "adjust_type": "前复权",
  "confidence": 0.95,
  "fallback_level": 1
}
```

**关键规则**：数据为过期缓存或 fallback 到低可信源时，依赖此数据的策略评分应自动降权。

### 2.3 数据异常拦截

以下异常不得进入策略评分管道：

```
价格为零
成交额为零但非停牌
涨跌幅超过 10%（非科创/创业）或 20%（科创/创业）
K 线缺口超过 3σ
分钟线时间戳倒序
复权价格前后不一致
成交量极端跳变（>10x 前日）
```

异常数据标记 `data_quality: rejected`，不进入评分。

### 2.4 AkShare 调用隔离

```
AkShare 所有调用统一走 adapter 层
每个接口有独立 timeout（默认 10s）
失败不阻塞主流程（降级到下一数据源）
关键接口加短期缓存（60s）
全市场扫描避免 per-symbol 串行调用
必要时使用子进程隔离（已有框架）
```

## 三、系统架构

### 3.1 安全基线（P0 — 立即）

| 编号 | 事项 | 措施 |
|------|------|------|
| S1 | `auth_secret_key` 不能为空 | 启动时强校验：生产环境下为空 → 退出并报错 |
| S2 | settings 不得返回明文密钥 | GET 端点拆分：公开字段 + 鉴权字段 |
| S3 | 所有业务路由必须鉴权 | analysis/research/instruments/screeners 统一加 `get_current_user` |
| S4 | admin token 未配置时必须明确拒绝 | 启动时检查，admin 接口返回 503 + 日志告警 |
| S5 | Agent 写工具默认关闭 | `agent_enable_write_tools` 默认 false，写工具开启需显式配置 |
| S6 | 飞书 Webhook 必须签名验证 | 已有，需补全测试覆盖 |
| S7 | 敏感日志脱敏 | API Key、Token 等 12 种敏感 key 写入日志前脱敏 |

**安全不能靠文档，要靠测试锁住：**

```
test_unauthenticated_routes_rejected        # 所有业务路由 401
test_settings_does_not_expose_llm_key       # settings 无密钥泄露
test_admin_requires_token                   # admin 端点 401
test_agent_write_tools_disabled_by_default  # 写工具默认不可用
test_feishu_signature_required              # 飞书签名必验证
```

### 3.2 模块边界

服务层按领域边界收紧：

```
market_data/       # 行情获取、缓存、数据源路由、质量标记
strategy/          # 策略定义、评分管线、信号生成、优先级榜单
paper_trading/     # 订单管理、撮合引擎、持仓管理、风控、绩效
agent/             # 工具注册、Provider、审计追踪、限流
notification/      # 通知渠道（飞书等）、去重账本、日报生成
auth/              # 用户认证、Token 管理、权限控制
settings/          # 系统配置读写
```

每个领域保持分层：

```
routes → service → repository → model/schema
```

规则：
- Route 不直接处理复杂业务逻辑
- Service 之间不横向相互调用（通过事件或接口）
- Repository 只做数据访问，不包含业务判断

### 3.3 SQLite 策略

**当前继续使用 SQLite**，但必须优化写入模式：

| 措施 | 原因 |
|------|------|
| 批量 upsert 替代逐行 upsert | `_upsert_frame` 当前数千行逐行 SELECT+INSERT |
| 后台任务错峰执行 | 避免多个写任务同时争锁 |
| 限流器从 SQLite 改为内存 deque | `SQLiteSlidingWindowRateLimiter` 自身是瓶颈 |
| 模拟盘关键写入加事务边界 | 余额检查和订单创建在同一事务 |
| 减少每请求创建连接 | 添加 `pool_size=5, max_overflow=10` |

**SQLite 的问题不是不能用，而是不能把它当高并发写入队列用。**

MySQL/Redis 迁移在 2-3 个月后评估，前提是先做好写入模式优化。

### 3.4 后台任务统一调度与可观测性

每个后台任务必须记录：

```python
{
    "task_name": "low_buy_full_scan",
    "last_started_at": "2026-05-03 10:00:00",
    "last_finished_at": "2026-05-03 10:02:15",
    "last_success_at": "2026-05-03 10:02:15",
    "last_error": None,
    "duration_ms": 135000,
    "rows_processed": 482,
    "next_run_at": "2026-05-03 11:00:00",
    "enabled": True
}
```

前端或 admin 页应可通过 `GET /api/admin/tasks` 查询所有任务健康度。

### 3.5 API 版本化

新接口从 `v1` 开始：

```
/api/v1/strategy/priority_board
/api/v1/paper/orders
/api/v1/agent/tools
...
```

旧接口保留兼容（逐步迁移），但 App、飞书、Agent 统一走 v1 协议。不一次性迁移，新功能和新终端用 v1。

### 3.6 Agent / Hermes 边界定义

```
┌──────────────────────────────────────────────┐
│  飞书（交互入口）                              │
│  - 展示结果                                    │
│  - 接收确认                                    │
│  - 发送通知                                    │
├──────────────────────────────────────────────┤
│  Hermes（自然语言层）                          │
│  - NLU 意图理解                               │
│  - 命令路由                                   │
│  - 飞书交互式卡片                             │
│  - 不直接访问数据库                           │
│  - 不直接执行交易逻辑                         │
├──────────────────────────────────────────────┤
│  TQuant 后端（安全边界）                       │
│  - 策略结果查询                               │
│  - 模拟盘接口                                 │
│  - 风控判断                                   │
│  - 审计日志                                   │
│  - 控制所有写操作                             │
└──────────────────────────────────────────────┘
```

Hermes 不能绕过 TQuant 后端直接读写数据库、执行 shell、影响交易。

### 3.7 Agent 工具限流

| 工具 | 限制 |
|------|------|
| `get_watchlist_signals` | 30/min |
| `get_priority_board` | 10/min |
| `get_paper_trade_plan` | 10/min |
| `execute_paper_trade_plan` | 3/min |
| `send_notification` | 5/min |
| 写工具（execute_*） | 需 explicit confirm |

写工具必须更严格，且默认只允许模拟盘——实盘需额外权限。

### 3.8 飞书交互卡片化

自然语言入口保留，但交易相关更适合结构化交互：

| 卡片类型 | 内容 | 按钮 |
|----------|------|------|
| 今日信号卡片 | 优先级榜 top 5 | [执行模拟买入] [查看详情] |
| 模拟交易计划 | 建议清单 | [执行] [跳过] [暂停策略] |
| 风险告警卡片 | 风控事件 | [确认] [暂停账户] |
| 策略绩效日报 | 收益率/胜率/期望 | [查看完整报告] |
| 人工确认卡片 | 关键操作确认 | [确认执行] [取消] [查看原因] |

### 3.9 自动交易——长期停留在模拟盘

实盘接入条件（缺一不可）：

```
至少 60-90 个交易日模拟记录
每个 CORE 策略至少 30-50 笔成交
经历至少 2 种不同的 market_regime
最大回撤低于预设阈值
策略归因为正期望
无重大撮合或数据异常
所有写操作有审计
Agent 执行必须人工确认
实盘只允许半自动（不允许全自动）
```

## 四、模拟盘系统

### 4.1 Decimal 全链路统一

以下字段统一使用 Python `Decimal`：

```
金额、价格、费用、持仓成本、成交金额、账户权益
```

指标计算和图表展示可以转 `float`，但存储和计算环节不允许混用。

### 4.2 并发保护

SQLite 下没有完整行锁，至少做到：

```
单账户写操作串行化（account-level threading.Lock）
事务内重新读取余额（避免幻读）
写入 `paper_orders` 和更新 `paper_accounts` 在同一事务
未来换 MySQL 再上 SELECT ... FOR UPDATE
```

### 4.3 交易摩擦真实化

**当前已有的**：5bps 滑点 + 费率计算（印花税/佣金/过户费）+ T+1

**需补充的**：

| 摩擦项 | 措施 |
|--------|------|
| 涨停无法买入 | 检查 `last_price >= limit_up_price` → 阻断 |
| 跌停无法卖出 | 检查 `last_price <= limit_down_price` → 阻断 |
| 停牌不可交易 | 检查 `is_suspended` → 阻断 |
| 小额订单佣金警告 | 交易摩擦 > 0.5% → 前端提示；> 1.0% → 默认阻断 |
| ETF/T+0 识别 | 维护 `symbol_type`，ETF 跳过 T+1 检查 |
| 盘口流动性不足 | 降成交率（远期） |

**小额订单提醒示例**：
> 100 股 × 10 元 = 1,000 元交易，最低佣金 5 元，单边佣金率 0.5%，来回 1.0%+。若策略目标利润仅 1%，已全部被交易成本吃掉。

### 4.4 退出原因标准化

每笔交易平仓时必须记录退出原因，否则绩效归因无意义：

```
stop_loss           # 止损触发
take_profit         # 止盈触发
time_exit           # 时间退出（持仓超期）
signal_invalidated  # 信号失效
risk_circuit        # 风控熔断
manual              # 手动平仓
end_of_day          # 尾盘强制平仓
liquidity_block     # 流动性阻断（涨跌停/停牌）
data_stale          # 数据过期无法判断
```

### 4.5 复盘信息完善

每笔交易在模拟盘页面展示：

```
为什么买：触发策略 + 信号评分 + 市场状态 + 风险等级
为什么卖：退出原因 + 持仓天数 + 是否违反阻断规则
当时快照：market_regime + breadh + hot_sectors
```

这会显著提高复盘价值——比单纯展示收益曲线有用得多。

### 4.6 部分成交

复杂度较高，**当前不做**。优先级低于涨跌停阻断、停牌阻断、小额佣金警告、ETF/T+0、并发余额保护和退出原因标准化。

## 五、前端架构

### 5.1 TradingWorkspace 降级为编排器

当前 856 行 `TradingWorkspace.tsx` 承载了太多。目标状态：

```
TradingWorkspace（< 200 行）:
  ├── 只负责导航
  ├── 只负责布局
  ├── 只负责全局用户状态
  └── 不直接处理各页面业务数据

页面逻辑拆分为独立 Hook:
  ├── useMonitor()
  ├── usePlaybook()
  ├── useAnalysis()
  ├── useResearch()
  ├── usePaperTrading()    # 已存在，318 行
  ├── usePerformance()
  └── useSettings()
```

### 5.2 引入顺序

不要同时上 React Router + Zustand + Tailwind。逐步来：

```
第一步：提取所有页面 Hook（本周）
第二步：统一 loading/error/notice 为结构化状态（本周）
第三步：引入 Error Boundary（本周）
第四步：评估 React Router v6（本月）
第五步：评估 CSS 体系升级（2-3 月）
```

### 5.3 Loading 状态结构化

用类型代替字符串：

```typescript
type LoadingState = {
  monitor?: boolean
  playbook?: boolean
  analysis?: boolean
  research?: boolean
  paper?: boolean
  performance?: boolean
  settings?: boolean
  submitOrder?: boolean
  refreshQuotes?: boolean
}
```

避免多个并行请求互相覆盖 loading 状态。

### 5.4 数据质量可视化

策略结果、信号旁边展示数据质量：

```
行情：东方财富，10:31:22，实时 ✅
K 线：BaoStock，T-1，前复权 ✅
板块：AkShare，延迟数据 ⚠️
北向资金：未接入 ❌
```

颜色标记：绿灯 = 实时，黄灯 = 延迟/缓存，红灯 = 过期/异常、灰灯 = 未接入。
