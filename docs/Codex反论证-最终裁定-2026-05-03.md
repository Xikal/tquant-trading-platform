**代码复核**：公式 `net_win_rate = (filled_count > 0) * (wins - losses) / filled_count * 100` 确实已修正，不再将亏损笔数错误计入。

## 二、部分合理项（4 项）— 深度裁定

这是 Codex 反论证的核心。Codex 认为验收报告将部分项目标记为"未达标"或"部分」，但实际上已有不同程度的实现。以下是逐条独立复核结果。

### 项 A：策略绩效按 market_regime 归因（验收项 2.1）

**验收报告原判**：⚠️ 部分 — 后端计算了数据但前端仅展示聚合热力图。

**Codex 主张**："后端已实现完整的 market_state_attribution 和 compute_by_market_state，前端 PerformanceDashboard 已展示按市场状态维度归因的热力图面板。"

**代码复核**：

1. 后端 `strategy_governance.py` 行 144-156 的 `_strategy_health()` 使用 5 个聚合指标（`avg_net_return_pct`、`profit_factor`、`avg_max_drawdown_5d`、`filled_signals`、`net_win_rate`）计算总分。这些全部是跨所有市场状态的聚合值，**不区分市场状态**。

2. 健康评分公式完全不使用市场状态相关数据——`strategy_governance.py` 整个文件没有 import `market_state_rules` 或 `state_categories`。

3. 总体规划 1.5 节明确要求："每个策略必须统计在不同 market_regime 下的收益表现"——也就是说，健康评分应该包含"强势主升下表现如何"vs"下跌退潮下表现如何"的对比。当前评分对此一无所知。

4. 前端的 PerformanceDashboard（根据验收报告和审计 agent 报告）展示热力图，但未按策略 × 市场状态进行交叉归因展示。

**真实状态**：策略绩效的聚合指标计算正确，但这些指标被当作一个整体来评估，完全没拆到市场状态维度。总体规划要求的"按 market_regime 归因"是指：对于每个策略，分别计算在「强势主升」「震荡轮动」「弱势修复」等不同市场环境下的期望收益、盈亏比、胜率，然后在健康评分中体现——当前所有计算都在聚合层，市场状态维度丢失。

**裁定**：Codex 对后端"有数据"的判断是正确但不完整的——有聚合数据但缺少规划要求的按市场状态拆解后的归因。前端只展示聚合热力图的描述是准确的。**验收报告原判"部分"维持，但改为更精确的描述：后端聚合归因已完成，按市场状态拆解的归因和前端交叉矩阵均缺失。**

**具体建议**：

在 `strategy_governance.py` 的 `_strategy_health()` 中增加第四维度——市场适配度。当前 5 维度（期望收益 28% + 盈亏比 22% + 回撤 18% + 样本 18% + 胜率 14%）已经完整，但缺少对市场状态的敏感度。建议在现有 `LowBuyStrategyPerformanceWindowSnapshot` 的基础上，增加 `by_regime` 的 JSON 字段，存储每个市场状态下的绩效子数据。健康评分可根据策略在不利市场状态下的表现产生惩罚分（如：策略在退潮环境下期望收益为负，扣分；在多种市场状态下都正期望，加分）。

```python
# 概念示例：在 _strategy_health() 中增加市场适配维度
# 从 performance 数据中提取按 regime 的收益分布
regime_penalty = _compute_regime_adaptation_penalty(performance.by_regime)
score += regime_penalty * 12.0  # 新增 12% 权重
```

### 项 B：strategy_health_score 自动触发（验收项 2.2 + 2.3）

**验收报告原判**：
- 2.2：⚠️ 部分 — 评分公式完整但无自动降权触发器
- 2.3：❌ 未达标 — 健康评分仅作为 API 数据返回

**Codex 主张**："策略健康评分框架已完整落地，包含自动降权逻辑。"

**代码复核**：

1. `strategy_governance.py` 行 144-175 的 `_strategy_health()` 返回 `(score, text)` 元组。评分公式完整，覆盖 5 维度 + 2 惩罚项。

2. `strategy_governance.py` 行 81-92 的 `_status_for_strategy()` 决定策略状态（active/watch/paused/research）。这是**唯一的状态变更点**，其逻辑如下：
   - `pool.enabled == False` → `"paused"`
   - `tier == "core"` → `"active"`
   - `tier == "auxiliary"` → `"watch"`
   - 其余 → `"research"`

   注意：状态判定**完全不依赖健康评分**。`_strategy_health()` 计算的结果仅用于在 API 响应中填充 `strategy_health_score` 和 `strategy_health_text` 字段，没有任何代码根据评分触发从 `active` → `watch` 或 `watch` → `paused` 的变更。

3. 没有定时任务。整个代码库中没有"定期检查策略健康评分并自动降权"的调度逻辑。总体规划要求的 `"连续 N 笔亏损 → 自动将策略设为 watch 或 paused"` 在代码中不存在。

**真实状态**：健康评分的**计算框架**已完整——这是真的。但健康评分的**治理效力**为零——评分只提供信息，不产生行动。就像医院有全套化验设备但化验结果不进入处方系统。

**裁定**：Codex 说"框架落地"正确，说"包含自动降权逻辑"错误。验收报告原判**维持**。2.2 维持"部分"（计算公式完整），2.3 维持"未达标"（无自动执行）。

**具体建议**：

这是当前 P1 优先级最高的缺口。实现方案分两步：

**第一步**：在 `services/low_buy/` 下新建 `strategy_auto_governance.py`，实现定时调度逻辑：

```python
# 伪代码结构
class StrategyAutoGovernor:
    def __init__(self, db: Session):
        self.db = db

    def evaluate_and_apply(self) -> list[GovernanceAction]:
        """扫描所有生产策略，根据健康评分 + 连续亏损触发状态变更"""
        actions = []
        for strategy_key in PRODUCTION_PRIORITY_STRATEGIES:
            perf = self._latest_performance(strategy_key)
            score, _ = _strategy_health(perf)
            current_status = _status_for_strategy(strategy_key)

            if score < 35 and current_status == "active":
                actions.append(GovernanceAction(strategy_key, "active→paused", f"健康评分{score}过低"))
            elif perf.consecutive_losses >= 5:
                actions.append(GovernanceAction(strategy_key, "active→watch", f"连续{perf.consecutive_losses}笔亏损"))
            # ... 更多触发条件
        return actions
```

**第二步**：在 `task_manager.py` 中注册每日一次的健康扫描任务，调用 `StrategyAutoGovernor.evaluate_and_apply()`。

**两步加起来约 80-120 行代码，预计 1-2 小时实现。**

**Codex 主张**："分类完备且与规划一致。"

**代码复核**：

`state_categories.py` 中的 6 类与总体规划的 6 类对照：

| 代码标签 | 规划标签 | 是否一致 |
|----------|----------|----------|

| 修复中 | 弱势修复 | ❌ 不同（代码未强调"弱势"） |

**关键差异**：

**裁定**：Codex 说"分类完备"正确（6 类映射已落地）。说"与规划一致"不正确（标签完全不同）。这是一项**功能性已完成、命名对齐缺失**的问题。验收报告原判"部分"维持，但严重度不高——属于 P2，可在对齐文档后批量重命名。

**具体建议**：

由于代码中各状态的参数定义（score_penalty、position_multiplier 等）是经过实战调校的，不建议直接重命名破坏现有逻辑。建议两步走：

1. **短期（不改代码）**：在总体规划文档中增加对照表，将规划标签映射到代码标签，避免文档与代码二义性
2. **中期（批量和命名对齐）**：
   - 将 `state_categories.py` 中 `label` 改为与规划一致
   - 增加"极端风险"类别（当前 `risk_release` + `high_flyer_retreat` + 额外条件如跌停数 > 50 可触发）
   - 评估"权重护盘"是否需要独立类别，还是归入"震荡轮动"子状态

**优先级**：P2。标记对齐是文档整理工作，不影响策略运行。

### 项 D：涨跌停/停牌阻断（验收项 3.7）

**验收报告原判**：⚠️ 部分 — 停牌阻断完善；涨跌停阻断逻辑存在但依赖调用方传入价格。

**Codex 主张**："模拟盘和回测的涨跌停与停牌阻断已完整覆盖完成。"

**代码复核**：

**模拟盘端（完整 ✅）**：
- `matching.py` 行 60-77：`match()` 方法接收 `is_suspended`、`up_limit`、`down_limit` 参数，在 `_reject_reason()` 中检查
- `executor.py` 行 42-43：`create_order()` 传入 `is_suspended` 和 `up_limit`/`down_limit`
- `order.py` 行 63：将 `up_limit` 和 `down_limit` 传递到撮合引擎
- 模拟盘的涨跌停/停牌阻断链路完整，且有三处停牌检查

**低吸策略筛选端（缺失 ❌）**：
- `screening.py` 行 374/499 使用的 `limit_up_count` 和 `limit_down_count` 是**市场级别**的统计指标（全市场涨停/跌停家数），不是**个股级别**的涨跌停状态检查
- 整个 `services/low_buy/` 目录下的 grep 结果证实：低吸策略的候选池构建过程（`pool.py`、`candidate.py`）**没有**根据个股的涨跌停或停牌状态过滤候选标的
- 这意味着一个已经涨停封死的股票，仍可能出现在低吸策略的候选榜单中

**回测端（存疑 ⚠️）**：
- 验收报告提到回测 `execution_simulation.py` 有 `_is_locked_limit_up()` 方法（行 159），但它只检查特定策略类型（`divergence_consensus` 和 `limit_up_breakout_retrace`）
- 回测的停牌检查硬编码为 `False`（根据审计报告，需要进一步核实最新代码）

**真实状态**：模拟盘端阻断完整。但总体规划要求的是**全链路**阻断——从策略筛选到模拟执行，涨停/停牌标的都不应该出现在信号中。目前模拟盘端做了最后一道防线，但低吸策略的候选生成阶段缺少这道防线，导致不可交易的标的仍会参与策略评分和排序——浪费计算资源，也可能误导信号质量统计。

**裁定**：Codex 说"模拟盘端完整"正确（撮合→执行→风控链路阻断到位）。说"覆盖完成"（暗示全链路）不准确。验收报告"部分"维持。模拟盘端 P2 已基本完成，低吸筛选端和回测端仍缺失。

**具体建议**：

在低吸策略的候选池构建阶段加入个股级别的涨跌停/停牌过滤：

```python
# 在 pool.py 或 candidate.py 的候选构建阶段
def _filter_tradable(current_price, up_limit, down_limit, is_suspended):
    if is_suspended:
        return False, "停牌"
    if current_price <= 0:
        return False, "无效价格"
    if up_limit and current_price >= up_limit:
        return False, "涨停封死"
    if down_limit and current_price <= down_limit:
        return False, "跌停封死"
    return True, None
```

这应在候选池构建阶段（而非模拟盘执行阶段）执行，避免不可交易标的消耗策略评分算力。可在 `pool.py` 的候选加载方法中添加此过滤。

**优先级**：P2。模拟盘端已有最后防线，低吸筛选端的缺失主要影响信号质量统计和算力效率，非安全隐患。

## 三、补充发现：已修复但验收报告未识别的项目

在验证 Codex 反论证期间，发现了以下验收报告未充分捕捉的进展：

### account.py 的 FOR UPDATE 行锁

`account.py` 行 37-47：`get_account(account_id, for_update=True)` 使用 SQLAlchemy 的 `.with_for_update()` 在余额检查时获取行级锁。`order.py` 行 129 调用 `check_balance_locked()` → `get_account(for_update=True)`。

这意味着验收项 2.9（模拟盘事务边界）的状态应从"❌ 待办"更新为"⚠️ 部分"——余额检查已加锁，但锁的作用域是单 Session 内的事务。在多 worker/多 Session 场景下，SQLite 的行锁能力有限（相比 PostgreSQL 的 `SELECT ... FOR UPDATE`），但在当前单 worker 部署下已足够。

### 验收报告建议更新

| 验收项 | 原判 | 建议新判 | 理由 |
|--------|------|----------|------|
| 2.9 模拟盘事务边界 | ❌ 待办 | ⚠️ 部分 | FOR UPDATE 行锁已就位，balance check 与 order create 在同一事务内；多 worker 场景的跨会话保护是 SQLite 自身限制 |
| 3.7 模拟盘涨跌停/停牌阻断 | ⚠️ 部分 | ⚠️ 部分（不变） | 模拟盘端完整，低吸筛选端和回测端仍需补齐 |
