# 下一步演进计划：策略质量验证闭环 + 盘中实时决策增强

**日期**：2026-05-02
**前序文档**：`全方位评估报告-2026-05-02.md`

---

## 一、为什么这两个方向要并行推进

| 如果只做验证闭环 | 如果只做盘中增强 |
|---|---|
| 策略结论是历史回测级别，与实盘脱节 | 信号精度提升但没有验证，可能是在噪声上优化 |
| 无法判断"时机不准"是策略问题还是执行问题 | 分钟线因子可能过拟合，因为缺乏样本外 PBO 检验 |

并行推进的正确姿势：**用盘中增强提升模拟盘信号的执行质量 → 积累高质量交易样本 → 用验证闭环确认策略真实正期望**。

## 二、整体架构变更

当前数据流：

```
日线数据 → 全量筛选 → 候选列表 → 低吸信号 → 手动下单
```

目标数据流：

```
日线数据 → 全量筛选 → 候选列表 → 低吸信号
                                         ↓
分钟线数据 → 盘中确认信号 ← 分时模式识别 + 盘口深度
                ↓
         入场时机评分 → PaperTradingExecutor → 模拟/实盘下单
                                                      ↓
                                              绩效统计 + PBO检验
                                                      ↓
                                              策略正式评级
```

两个核心新增模块：

- **IntradayConfirmer**：盘中确认引擎，对日线信号做分钟级二次验证
- **StrategyValidationPipeline**：策略验证管线，串联模拟盘 → 绩效 → PBO → 评级

## 三、阶段一（30 天）：策略验证管线 + 盘中数据基础

### 3.1 StrategyValidationPipeline

目标：让 4 个核心策略各自跑出可量化的样本外绩效。

**新增模块**：`backend/app/services/paper/validation.py`

```
StrategyValidationPipeline
├── run_validation(strategy_key, lookback_days) → ValidationReport
│   ├── 回放历史 priority_board 信号
│   ├── 对每个信号执行 PaperMatchingEngine.match()
│   ├── 跟踪持仓 → T+1 卖出 → 绩效
│   └── 输出ValidationReport
│
├── ValidationReport
│   ├── total_trades, win_rate, profit_factor, sharpe
│   ├── by_market_state: {bull, bear, sideways} 分组统计
│   ├── by_industry: 板块分组统计
│   ├── max_drawdown, max_consecutive_losses
│   ├── PBO_score（shuffle 1000 次信号序列）
│   └── is_positive_expectation（Profit Factor >1.2 且 PBO >0.5 且 trades>=50）
│
└── compare_strategies(strategy_keys[]) → StrategyRanking
    └── 按 Profit Factor 排序的横向对比
```

**验收标准**：
- 4 个核心策略各有至少 50 笔回放交易
- 每个策略有 PBO 数值
- 至少 1 个策略利润因子 >1.2

## 四、阶段二（60 天）：盘中确认引擎 + 策略正式评级

### 4.1 IntradayConfirmer

目标：日线低吸信号出现后，盘中用分钟线做二次确认，输出置信度评分。

**新增模块**：`backend/app/services/low_buy/intraday_confirmer.py`

```python
class IntradayConfirmer:
    """
    盘中确认引擎：对日线精选信号做分钟级二次验证。
    输入：symbol, strategy_key, daily_signal
    输出：ConfirmationResult（确认/观望/否定 + 最优入场区间）
    """

    def confirm(self, symbol, strategy_key, daily_signal) -> ConfirmationResult:
        # 四维度评分，权重可配置
        scores = {
            "volume_pattern": self._check_volume_pattern(),      # 权重 0.30
            "price_structure": self._check_price_structure(),    # 权重 0.30
            "support_test": self._check_support_test(),          # 权重 0.25
            "big_order_flow": self._check_big_order_flow(),      # 权重 0.15
        }
        total = weighted_sum(scores)
        return ConfirmationResult(
            confirmed=(total >= 60),
            score=total,
            best_entry_zone=self._compute_entry_zone(),
            reasons=self._build_reasons(scores),
            warnings=self._build_warnings(scores),
        )

    # --- 四个盘中确认维度 ---

    def _check_volume_pattern(self) -> float:
        """
        缩量止跌确认：前一小时量比 < 全日均量 60%，且价格不创新低。
        放量反弹确认：当前 15 分钟量 > 前 15 分钟量 1.5x，且价格向上。
        
        评分逻辑：
        - 缩量止跌 + 放量反弹连续出现 → 85+
        - 仅缩量止跌 → 60
        - 仅放量反弹 → 50
        - 放量下跌 → 0（否决）
        """
    
    def _check_price_structure(self) -> float:
        """
        分时价格结构分析：
        - 开盘后是否出现"开盘下探 → 回升翻红"的 V 型结构
        - 分时均线（黄色均线）是否走平或向上
        - 分时价格是否在均线上方运行
        - 是否有"双底"、"头肩底"等经典分时形态
        
        评分逻辑：
        - V 型翻转 + 站稳均线 → 90+
        - 横盘企稳 + 均线走平 → 65
        - 持续下跌 + 均线向下 → 0（否决）
        """
    
    def _check_support_test(self) -> float:
        """
        支撑位测试：
        - 当日最低价是否触及关键支撑位（MA5/MA10/前低/整数关口）
        - 触及后是否快速反弹（15 分钟内回升 >0.3%）
        - 支撑位的"硬度"（之前被测试的次数）
        
        评分逻辑：
        - 触及关键支撑 + 快速反弹 → 90+
        - 触及支撑 + 缓慢企稳 → 60
        - 跌破关键支撑未收回 → 0（否决）
        """
    
    def _check_big_order_flow(self) -> float:
        """
        大单资金流向（复用 factor_external.py 的缓存逻辑）：
        - 近 30 分钟特大单 + 大单是净流入还是净流出
        - 净流入占成交额的比例
        - 是否有连续大单买入
        
        评分逻辑：
        - 大单净流入 + 流入比例 >15% → 80+
        - 大单平衡 → 50
        - 大单净流出 + 流出比例 >10% → 0（否决）
        """

@dataclass
class ConfirmationResult:
    confirmed: bool           # 是否确认入场
    score: float              # 0-100 确认强度
    best_entry_time: str      # 最优入场时间段，如 "10:00-10:30"
    entry_price_low: float    # 入场价格下限
    entry_price_high: float   # 入场价格上限
    stop_loss_intraday: float # 盘中动态止损价
    reasons: list[str]        # 确认理由
    warnings: list[str]       # 风险提示
```

**四种确认结果与动作映射**：

| 确认结果 | 条件 | PaperTradingExecutor 动作 |
|---------|------|-------------------------|
| strongly_confirmed | score >= 80 | 全自动模式下直接执行 |
| confirmed | score >= 60 | 全自动模式下执行，半自动模式下列出待确认 |
| watch | score >= 40 | 不执行，下轮继续观察 |
| rejected | score < 40 或否决项触发 | 不执行，当日该信号标记为跳过 |

### 4.2 确认引擎与 PaperTradingExecutor 集成

PaperTradingExecutor 每 120 秒轮询的逻辑增强：

```
1. 读 priority_board → 获取日线信号列表
2. 对每个 buy_now / near_entry 信号：
   a. 检查是否已有当日盘中确认结果（intraday_confirmations 表）
   b. 若无，调用 IntradayConfirmer.confirm()
   c. 若 strongly_confirmed：
      → 应用准入过滤器（资金/仓位/T+1/熔断）
      → 生成委托（限价单，价格区间 = entry_zone）
      → 全自动模式下直接提交
   d. 若 confirmed：
      → 全自动模式：同 strongly_confirmed（更低仓位）
      → 半自动模式：加入待确认列表，等待用户手动确认
   e. 若 watch：跳过本轮，保留日线信号待下轮重新确认
   f. 若 rejected：标记该信号为"已否决"，当天不再检查
3. 收盘后（15:05）：
   → 清理当日盘中确认缓存
   → 调用 AiService.generate_daily_report()
```

### 4.3 策略正式评级

在 4 个核心策略各积累 100 笔+盘中确认后的模拟交易样本后，执行正式评级：

```
策略评级矩阵：
┌─────────────────┬────────────┬──────────────┬─────────────┐
│                 │ Profit     │ PBO          │ 样本量       │
│                 │ Factor     │              │             │
├─────────────────┼────────────┼──────────────┼─────────────┤
│ PRODUCTION      │ >1.3       │ >0.5         │ >=100       │
│ CANDIDATE       │ >1.1       │ >0.4         │ >=50        │
│ UNDER_REVIEW    │ >0.9       │ >0.3         │ >=30        │
│ DEPRECATED      │ <0.9       │ <0.3         │ any         │
└─────────────────┴────────────┴──────────────┴─────────────┘
```

评级后策略自动调整 tier：
- PRODUCTION → `strategy_policy.py` 中提升到 CORE
- UNDER_REVIEW → 降级到 RESEARCH
- DEPRECATED → 从优先榜移除

## 五、阶段三（90 天）：盘中信号推送 + 全自动闭环

### 5.1 盘中实时信号推送

目标：App 端在盘中收到实时信号变化推送。

**技术选型**：
- 短期（单机）：Server-Sent Events (SSE) —— FastAPI 原生支持，无需额外依赖
- 长期（多机）：WebSocket + Redis Pub/Sub

**新增接口**：`GET /api/app/stream/signals`

```
SSE 事件类型：
├── signal_update    → 某自选股信号变化（hold → positive_t / near_entry → buy_now）
├── confirmation     → 某信号完成盘中确认（confirmed / rejected）
├── order_executed   → PaperTradingExecutor 执行了一笔委托
├── risk_alert       → 熔断触发 / 连续止损 / 大额浮亏
└── heartbeat        → 每 30 秒，确认连接存活
```

**App 端**：EventSource 连接 SSE → 信号变化即时刷新卡片，不再依赖轮询。

### 5.2 全自动模拟交易闭环

在策略评级完成（至少 2 个策略达到 PRODUCTION 级别）且盘中确认引擎稳定后，开启全自动模式：

```
工作流：
07:00  后台全量筛选完成 → 物化快照就绪
09:15  开盘 → priority_board + watchlist signals 更新
09:25  盘中确认引擎启动 → 对日线信号做首次确认
09:30-14:57  每 120 秒：
            → PaperTradingExecutor 读取最新 signals + confirmations
            → 准入过滤 → 自动委托
            → SSE 推送执行结果
14:57  最后一轮确认（尾盘信号特殊处理：需要更强的确认强度）
15:05  收盘 → 清理缓存 → 生成日报 → 推送日报
15:30  StrategyValidationPipeline 更新策略绩效 → 检查是否需要降级
```

### 5.3 风控熔断（必须同步实现）

```
熔断规则（按优先级）：
1. 单日亏损熔断：当日已实现亏损 > 总资产 2% → 暂停所有自动交易
2. 连续止损熔断：连续 3 笔交易止损 → 暂停该策略的自动交易
3. 策略回撤熔断：策略滚动 20 笔交易 Profit Factor <0.7 → 自动降级到 RESEARCH
4. 异常信号熔断：单策略单日信号数 > 历史均值 3σ → 暂停该策略
5. 资金占用熔断：已占用资金（含挂单）> 总资产 60% → 暂停新开仓
```

## 七、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 分钟线数据质量差（akshare 数据缺失/延迟） | 中 | 盘中确认引擎无法工作 | 降级到仅依赖日线信号；加入数据质量告警 |

| SSE 连接在 App 后台断开 | 中 | 用户错过信号变化 | 保底轮询机制（3 分钟兜底拉取） |

## 九、不做的事情（明确边界）

以下方向在当前 90 天计划中**不做**，避免精力分散：

- Level2 盘口深度接入（数据成本高，先验证分钟线信号有价值再投入）
- 多策略组合优化 / 马科维茨配置（单策略验证优先于组合优化）
- 实盘券商 API 对接（模拟盘闭环完成后再考虑）
- AI Agent 实时决策（LLM 只做盘后日报，不做实时交易——此原则不变）
- 期权/期货/可转债扩展（聚焦 A 股股票 + ETF）
