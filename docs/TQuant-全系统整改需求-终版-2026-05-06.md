## 二、确认 Bug 清单（P0 — 上线前必须修复）

### P0-1: 通知未配置时返回"假成功"

**当前问题**: `agent_notification_service.py:73-78`，当无 webhook 且无 Hermes CLI 时，`send_test()` 返回 `ok=True, message="notification adapter not configured"`。`send_signal()` 在第 100-102 行信任这个 `ok=True`，递增 `notification_count` 并更新 `last_notified_at`，导致信号进入冷却期但用户实际未收到任何通知。

**修复要求**:
1. `send_test()` 在未配置通知通道时返回 `ok=False`
2. `send_signal()` 仅在 `send_result.ok == True` 且确认消息已成功送达时才更新 `notification_count` 和 `last_notified_at`
3. 增加日志：未配置通知通道时记录 WARNING 级别日志

**验收标准**:
- 未配置 webhook 且 Hermes CLI 不可用时，`send_test` 返回 `ok=False`
- `send_signal` 在未配置时不增加 `notification_count`，不更新 `last_notified_at`
- 日志中出现 "Notification channel not configured, skipping signal notification"（WARNING 级别）

**验证方式**: 单元测试 — 清空 webhook 和 hermes_path 配置后调用 `send_test`，断言 `ok=False`

**风险等级**: Critical — 信号推送全部静默失效

**影响范围**: 飞书通知、Hermes 通知、信号冷却机制

### P0-2: `main.py` 定时任务时间仍未统一为北京时间

**当前问题**: `main.py` 中 4 处仍使用本地 `datetime.now()` / `date.today()`：
| 行号 | 上下文 | 当前代码 | 问题 |
|------|--------|---------|------|
| 150 | 快照 freshness 检查 | `(datetime.now() - updated_at).total_seconds()` | 用服务器本地时间比较北京时间戳 |
| 200 | 纸笔归档日期判断 | `today = date.today()` | 用服务器本地日期而非北京日期 |
| 280 | `_paper_archive_due()` | `datetime.now().time() >= archive_time` | archive_time 是北京时间 15:05，但用本地时间比较 |
| 284 | `_agent_daily_report_push_due()` | `now = datetime.now()` | 同上，用本地时间比较北京时间 15:10 |

**修复要求**:
1. 第 150 行快照 freshness → `(beijing_now() - updated_at).total_seconds()`（需先确认 `updated_at` 的时区语义）
2. 第 200 行 → `today = beijing_now().date()`
3. 第 280、284 行 → `now = beijing_now()`
4. 封装 `beijing_today()` 工具函数（如有必要），统一所有日期比较路径

**验收标准**:
- 设置系统时区为 UTC 后，纸笔归档在北京时间 15:05 后触发
- 设置系统时区为 UTC 后，Agent 日报在北京时间 15:10 后触发
- 快照 freshness 判断不受服务器时区影响

**验证方式**: 单元测试 — 设置 `TZ=UTC` 后运行，Mock `beijing_now()` 返回期望时间，断言 `_paper_archive_due()` 返回值正确

**风险等级**: Critical — UTC 服务器上归档和日报永远不触发，快照 freshness 可能误判

**影响范围**: 模拟盘绩效归档、Agent 日报推送、低吸快照刷新

### P0-3: Android Release 构建允许明文 HTTP 流量

**当前问题**: `AndroidManifest.xml:10` 中 `android:usesCleartextTraffic="true"` 作用于所有构建变体。Release APK 允许任意 HTTP 明文连接，存在中间人攻击风险。

**修复要求**:
1. Release 构建禁止 cleartext traffic
2. Debug 构建保留 cleartext（方便本地和内网调试）
3. 使用 `network_security_config.xml` 按构建类型分别配置

`frontend/android/app/src/main/res/xml/network_security_config.xml`（新建）:
```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <domain-config cleartextTrafficPermitted="false">
        <domain includeSubdomains="true">your-production-domain.com</domain>
    </domain-config>
</network-security-config>
```

Debug 构建的 `AndroidManifest.xml`（`src/debug/`）保留 `usesCleartextTraffic="true"`。

**验收标准**:
- Release APK 不允许 HTTP 明文连接
- Debug APK 仍可连接本地开发服务器（HTTP）
- 生产后端域名配置为 HTTPS only

**验证方式**: 构建 Release APK → 抓包确认无 HTTP 请求

**风险等级**: Medium — 中间人攻击风险，不影响功能但涉及安全合规

**影响范围**: Android App 网络安全

### P1-1: `screening.py` 在外部传入 session 上执行 `commit()`

**当前问题**: `screening.py:48` 中 `_rebuild_materialized_snapshot(db)` 对传入的 `db: Session` 调用 `db.commit()`。如果调用方有未提交的更改，会被意外提交。注意：`refresh_full_scan_cache`（行 60）使用自有 `SessionLocal()` 且内部已完成提交，该路径不受影响。

**修复要求**:

2. 在函数文档中明确声明"不管理事务，调用方负责 commit"

**验收标准**:
- `_rebuild_materialized_snapshot` 内部无 `db.commit()` 调用

**风险等级**: Medium — 仅在特定调用路径下触发（外部 session + 调用方有未提交更改）

**影响范围**: 低吸扫描数据一致性

### P1-3: 模拟盘 API 边界异常处理不一致

**当前问题**: `PaperOrderService.get_order()` 在 service 层抛 `LookupError`，route 层（`paper.py:260`）做了翻译，但这个模式不统一：部分路由翻译为 404，部分路由（如 cancel 在 `paper.py:277`）翻译为 400。需澄清并统一。

**修复要求**:
1. 保持 service 层抛业务异常（`LookupError`、`ValueError`），不引入 HTTP 层依赖
2. Route 层统一翻译规则：
   - `LookupError` → 404（资源不存在）
   - `ValueError`（参数校验） → 400（请求参数错误）
   - 其他未捕获异常 → 500（内部错误，记录日志）
3. 所有 paper 路由确认遵循此规则
4. 文档化异常边界约定

**验收标准**:
- `GET /api/paper/orders/{id}` 对不存在的订单返回 404
- `POST /api/paper/orders/{id}/cancel` 对不存在的订单返回 404（非 400）
- 参数非法（如负数量）返回 400
- Service 层无任何 HTTP 依赖

**验证方式**: curl 测试 + 代码审查

**风险等级**: Low — 影响 API 语义一致性，不影响核心功能

**影响范围**: Paper Trading API

### P1-4: 通知成功语义须明确

**当前问题**: 与 P0-1 关联但范围不同。P0-1 只修"未配置时假成功"。此处要求定义：**什么算通知成功？**

**修复要求**:
1. 对于飞书 webhook：HTTP 200 不够，需检查飞书返回体中的 `code` 字段（`code=0` 为成功）
2. 对于 Hermes CLI：subprocess 返回码为 0 且 stdout 无错误标记才算成功
3. 对于 Hermes HTTP Gateway：HTTP 200 且响应体 `status=="success"` 才算成功
4. 仅上述条件全部满足时，才递增 `notification_count` 和更新 `last_notified_at`
5. 通知发送失败（网络错误、业务错误码）时记录详细日志（含错误原因），但不计入通知计数

**验收标准**:
- 飞书 webhook 返回 `{"code": 1, "msg": "invalid webhook"}` → `ok=False`，不更新计数
- Hermes CLI 返回非 0 退出码 → `ok=False`，不更新计数
- 网络超时 → `ok=False`，不更新计数，记录 ERROR 日志

**验证方式**: Mock 飞书/Hermes 返回错误响应，断言 `send_signal` 不更新通知计数

**风险等级**: Medium — 信号通知可靠性

**影响范围**: 飞书通知、Hermes 通知

## 十二、澄清问题回答

### Q1: 哪些问题是当前代码已确认存在，哪些是历史报告遗留？

**确认存在（本次修复）**：
- 通知假成功（agent_notification_service.py:73-78）
- main.py 时区未统一（4 处 bare datetime.now()）
- screening.py 外部 session commit（line 48）
- 策略列表多源硬编码（workspaceConstants.ts + backtestDisplay.ts + strategy_metadata_service.py）
- Android cleartext（AndroidManifest.xml:10）

**历史遗留/已过期（不修复，仅验收）**：
- Paper LookupError → 404（route 已翻译）
- 零价撮合拒绝（matching.py 已检查）
- 自动交易时区（scheduler.py 已用 beijing_now）
- Agent 限流（base.py 已接入 rate_limiter）
- Agent 审计脱敏（audit.py 已有 sanitize_arguments）
- 策略回放 lookback（strategy_meta.py 已有参数）
- WS expire_all（strategy_stream.py 已调用）

### Q2: 策略阈值外置化是否要求影响历史回测？

如果进行阈值外置化，会影响历史回测的可复现性。因此本轮不做阈值外置化。如果未来要做，必须同时实现：配置版本号、每次回测记录配置版本、版本化管理所有调参记录、支持配置回滚。这需要独立的架构专项。

### Q3: 策略列表"唯一真源"是否允许前端 fallback？

允许。前端可在 API 不可用时使用内置降级数据。但降级数据必须来自后端种子数据的自动同步脚本，不能独立维护。验收标准：API 可用时用 API 数据；API 不可用时用降级数据；两者的 key/name/category 必须一致。

### Q4: 通知成功的业务定义是什么？

- 飞书 webhook：HTTP 200 且响应体 `code == 0`
- Hermes CLI：subprocess 返回码 0 且 stdout 无错误标记
- Hermes HTTP Gateway：HTTP 200 且 `status == "success"`
- 仅满足以上条件时计入通知计数

HTTP 200 不等于通知成功。

### Q5: Android cleartext 是只修 release，还是 debug 也禁用？

Release 必须禁止 cleartext。Debug 保留 cleartext 用于本地和内网调试。通过 `network_security_config.xml` + 构建变体分别配置。

### Q6: WebSocket 重连是针对所有任务流，还是只针对 backtest/optimization/validation？

仅针对 backtest/optimization/validation 三种任务进度流。当前系统无其他 WebSocket 使用场景。

### Q7: Hermes CLI 是必须替换为 HTTP，还是仅作为性能优化项？

性能优化项（P2 增强），非 P0/P1。CLI subprocess 功能正确，仅启动延迟较高（10-50ms）。HTTP Gateway 可降低延迟但不对功能正确性产生影响。

### Q8: 哪些整改必须本轮上线前完成，哪些可以进入 Phase 4？

**本轮上线前（P0+P1）**：
- P0-1 通知假成功修复
- P0-2 时区统一
- P0-3 Android cleartext 分环境
- P1-1 screening 事务修复
- P1-2 策略列表去硬编码
- P1-3 异常边界统一
- P1-4 通知成功语义明确

**Phase 4 或独立专项**：
- 策略阈值外置化平台（独立专项）
- Hermes HTTP Gateway 替换
- 后台 Worker 独立进程
- DI 容器化
- WebSocket 真 push 化
- Agent 结果质量自动评分
- 数据源多活
