## P0-1：visibility="hidden" 唯一定义

**问题**：v9.1 一处说 hidden 对所有人不展示，另一处表格说 admin 可见。

**裁决**：

`visibility="hidden"` 的唯一语义：**策略已废弃/归档，所有常规入口不可见**。

| 用户/入口 | 行为 |
|----------|------|
| `/api/strategies/meta`（无参数） | **不返回** hidden 策略（任何角色） |
| `/api/strategies/meta?include_hidden=true` | 仅 admin 角色可传此参数，此时返回 hidden 策略 |
| 普通用户 / researcher / optimizer | 传 `include_hidden=true` 时忽略参数，仍不返回 hidden |
| Playbook / 优先榜 / 回测预设 / App | 永不含 hidden |
| 回测选择器 | 永不含 hidden |
| DB 行 | 保留（不物理删除，用于审计追溯） |

对比 `enabled=false`（策略暂停）和 `visibility="backtest_only"`（仅回测研究）：

| 状态 | meta API 返回？ | Playbook | 回测选择器 | 优先榜 | 预设 |
|------|---------------|----------|-----------|-------|------|
| `enabled=true, visibility=full` | ✅ | ✅ | ✅ | ✅（需 tier） | ✅（需 tier） |
| `enabled=false, visibility=full` | ✅（灰色标记） | ❌ | ✅（灰色） | ❌ | ❌ |
| `enabled=true, visibility=backtest_only` | ✅（badge） | ❌ | ✅（badge） | ❌ | ❌ |
| `visibility=hidden` | ❌（仅 admin+include_hidden） | ❌ | ❌ | ❌ | ❌ |

## P0-2：Factor 策略权限模型

**问题**：v9.1 说"回测 API 不做 role 阻断"但"UI 隐藏入口"——这不是权限，只是 UI 混淆。

**裁决**：Factor 策略是权限边界，后端必须校验。

回测创建 API（`POST /api/backtests`）新增 role 检查：

```python
@router.post("/api/backtests")
def create_backtest(body: BacktestCreateRequest, current_user=Depends(get_current_user), db=Depends(get_db)):
    # 新增：factor 策略权限校验
    factor_keys = [s for s in body.strategies if get_strategy_tier(s) == StrategyTier.FACTOR]
    if factor_keys and not _has_role(current_user, {"backtest_optimizer", "backtest_research", "admin", "administrator"}):
        raise HTTPException(403, detail="factor 策略回测需要研究权限（backtest_research / backtest_optimizer）")
    # ... 原有逻辑
```

**对照 `/api/strategies/meta`**：

| 角色 | meta 返回的 factor 策略 | POST backtest 含 factor key |
|------|------------------------|---------------------------|
| 普通用户 | ❌ 不返回 | ❌ 403 |
| backtest_research | ✅ 返回 | ✅ 200 |
| backtest_optimizer | ✅ 返回 | ✅ 200 |
| admin | ✅ 返回 | ✅ 200 |

**之前"回测 API 不做阻断"的错误假设废弃**。如果只是隐藏 UI 入口但不校验后端，安全审计不通过。两个端点（meta + backtest）的权限判断使用同一个 `_has_role()` 函数。

## P0-3：Quick Backtest API 契约

**问题**：v9.1 的"一键回测"说"策略=preset quick_check"，但当前回测接口接受的是 `strategies` 数组，不是 `preset_key`。

**裁决**：**前端展开 preset，不新增后端 preset_key 接口**。

理由：
1. 当前 `POST /api/backtests` 接受 `BacktestCreateRequest`，内含 `strategies: list[str]`
2. 前端已有 `GET /api/strategy/presets` 返回完整 config（含 strategies 数组）
3. 新增 preset_key 参数 → 后端需新增 preset 展开逻辑、缓存、错误处理、测试
4. 前端展开 preset 零后端改动，仅前端一行代码：`body = {...preset.config}`
5. 如果 preset 在后端展开，每次 preset 更新（新增策略、改默认参数）需发版；前端展开可跟随 API 动态变化

**一键回测的完整流程**：

```
用户点击"一键快速回测"
    ↓
前端 GET /api/strategy/presets（取 quick_check.config）
    ↓
前端展开 config 为 BacktestCreateRequest：
    {
      strategies: config.strategies,        // 已由后端 filter 为仅生产层
      date_range: config.range,             // "6m"
      initial_capital: config.initial_capital,
      execution_model: config.execution_model,
      // ... 其余字段取 preset config 默认值
    }
    ↓
POST /api/backtests（现有接口，零改动）
    ↓
toast "已提交回测" → 跳转历史 Tab
```

**不改** `POST /api/backtests` 的 schema。**不改** `GET /api/strategy/presets` 的 schema。预设的 strategies 数组已在 Phase 2 中通过 `_default_production_strategy_keys()` 过滤为仅生产层。

## P0-5：新策略预过滤指标的可行性

**问题**：`board_count_20d`、`drawdown_from_high_pct`、`recent_avg_volume`、`ma_volume_20` 等字段在 `CandidateMetrics` 中不存在或未验证。

**裁决**：逐字段给出处理方式。

### ma_channel_band 依赖的指标

| 预过滤条件中的指标 | 是否存在？ | 处理方式 |
|------------------|-----------|---------|
| `item.amount` | ✅ `ScanCandidate.amount` | 直接使用 |
| `metrics.ma20 > metrics.ma60` | ✅ `DailyBarSnapshot.ma20` / `ma60` | 直接使用 |
| `metrics.close_to_ma20` | ❌ 不存在 | **新增计算**：`(latest_close - ma20) / ma20 * 100`，在 `candidate_rules.py` 中实时计算，或新增为 `DailyBarSnapshot` 派生字段。建议在 prefilter 中实时计算（单次除法，无 DB 开销） |
| `metrics.distribution_risk_score` | ❌ 不存在 | **替换为现有字段**：改为 `not metrics.false_breakout_flag`（已有）。出货判断用已有 `distribution_score` 或简化为"排除近 5 日跌停" |
| `metrics.volume_ratio_value` | ❌ 不存在 | **新增计算**：`volume / MA(VOL, 5)`。在 prefilter 中实时计算（已有 volume 和 ma_volume 字段） |
| `metrics.false_breakout_flag` | ✅ 已有 | 直接使用 |

**修正后的 ma_channel_band prefilter**（使用已有字段 + 实时计算）：

```python
if strategy == "ma_channel_band":
    # 实时计算
    close_to_ma20 = (item.latest_close - item.ma20) / item.ma20 * 100 if item.ma20 else 999
    vol_ratio = item.volume / item.ma_volume_5 if item.ma_volume_5 else 0
    return (
        item.amount >= 50_000_000.0
        and item.ma20 > item.ma60                                           # 已有
        and -4.0 <= close_to_ma20 <= 0                                      # 实时计算
        and not item.false_breakout_flag                                    # 已有（替代 distribution_risk_score）
        and vol_ratio >= 0.8                                               # 实时计算
        and item.latest_change_pct > -9.7                                  # 已有（替代"近5日跌停"判断）
    )
```

依赖的已有字段：`latest_close`, `ma20`, `ma60`, `volume`, `ma_volume_5`, `false_breakout_flag`, `amount`, `latest_change_pct`——全部在 `DailyBarSnapshot` 中。

### leader_pullback_band 依赖的指标

| 预过滤条件中的指标 | 是否存在？ | 处理方式 |
|------------------|-----------|---------|
| `item.amount` | ✅ | 直接使用 |
| `metrics.board_count_20d` | ❌ 不存在 | **新增**：从 `limit_up_pool` 聚合表查询。`passes_strategy_prefilter()` 中不再做此检查（prefilter 是逐标的，无法做跨时间聚合）。移到 `score_candidate()` 中实现 |
| `metrics.drawdown_from_high_pct` | ❌ 不存在 | **新增计算**：`(latest_close - high_20d) / high_20d * 100`。`high_20d` 从 `DailyBarSnapshot` 的窗口函数获取 |
| `metrics.recent_avg_volume` | ❌ 不存在 | **新增计算**：近 3 日均量。在 prefilter 中实时计算 |
| `metrics.ma_volume_20` | ❌ 不存在 | **新增**：`DailyBarSnapshot` 需支持 `MA(VOL, 20)` 或 prefilter 中实时计算 |
| `metrics.latest_close` | ✅ | 直接使用 |
| `metrics.ma10` / `metrics.ma20` | ✅ | 直接使用 |
| `metrics.latest_change_pct` | ✅ | 直接使用 |
| `metrics.false_breakout_flag` | ✅ | 直接使用 |

**修正后的 leader_pullback_band prefilter**：

```python
if strategy == "leader_pullback_band":
    # 实时计算
    high_20d = _high_20d(item)            # 从 DailyBarSnapshot 窗口函数
    drawdown = (item.latest_close - high_20d) / high_20d * 100 if high_20d else 0
    recent_vol_3d = _avg_volume_3d(item)  # 近 3 日均量
    vol_ratio = recent_vol_3d / item.ma_volume_20 if item.ma_volume_20 else 999
    return (
        item.amount >= 50_000_000.0
        and drawdown <= -6.0                                                # 实时计算
        and vol_ratio <= 0.75                                               # 实时计算
        and item.latest_close >= item.ma10 * 0.995                          # 已有
        and item.latest_close <= item.ma20 * 1.005                          # 已有
        and item.latest_change_pct > -9.7                                   # 已有
        and not item.false_breakout_flag                                    # 已有
        # board_count_20d 不在 prefilter 中检查——移到 score_candidate()
    )
```

**需要新增的底层能力**：
1. `DailyBarSnapshot` 新增 `ma_volume_20` 字段（或 prefilter 中实时聚合）
2. `_high_20d()` 辅助函数（从日线窗口取 20 日最高价）
3. `_avg_volume_3d()` 辅助函数（近 3 日均量）
4. `score_candidate()` 中为 leader_pullback_band 新增龙头识别逻辑（查询 limit_up_pool 聚合近 20 日涨停次数 + 行业内排名）

**Phase 3 改动量增加**：`candidate_rules.py` 约 +50 行（原估算 +80 行，因部分指标需在 prefilter 中实时计算，部分逻辑移到 score_candidate）。`pool.py` 约 +40 行（新增 leader 行业排名分支 + 窗口函数辅助）。

```python
# 20260506_v9_workbench.py upgrade() 内

    ]:
        if col_name not in [c["name"] for c in inspector.get_columns("strategy_metadata")]:

        UPDATE strategy_metadata
        SET enabled = TRUE,
            probe_status = 'not_required',
            probe_summary = '',
            visibility = 'full'
        WHERE enabled IS NULL
          AND probe_status IS NULL
          AND probe_summary IS NULL
          AND visibility IS NULL

    # 3. MySQL 下可加 NOT NULL 约束（SQLite ALTER COLUMN 不支持，保持 nullable + 业务层保证）
```

```python
@router.get("/strategies/meta")
def list_strategy_meta(
    current_user = Depends(get_current_user),

    resolver = StrategyTierResolver(db)

    return StrategyMetaResponse(strategies=items)
```

## P1-2：Promote/Demote 后 Resolver 缓存失效

**裁决**：

```python
# POST /api/strategy/governance/promote handler
def promote(body: PromoteRequest, current_user=Depends(require_admin_auth), db=Depends(get_db)):
    # ... 写表逻辑 ...
    db.commit()

    # 立即失效当前进程缓存
    resolver = StrategyTierResolver(db)
    resolver.invalidate(body.strategy_key)  # 清除进程级缓存

    # 其他 worker 的 TTL 窗口内仍使用旧值（最大 300s），可接受
    # 如需立即全局生效，admin 可在 promote 后手动调用 GET /api/strategies/meta?force_refresh=true
```

**force_refresh 参数**（可选优化）：`GET /api/strategies/meta?force_refresh=true` → resolver 跳过缓存，直接从 DB 读取。用于 promote/demote 后的即时验证。

**多 worker 不一致窗口**：

| 时间 | Worker A（收到 promote 请求） | Worker B |
|------|---------------------------|---------|
| T+0 | cache.invalidate() → 下次请求读 DB | 缓存仍是旧值 |
| T+1s ~ T+300s | 正确值 | 旧值（TTL 过期前） |
| T+300s+ | 正确值 | 缓存过期 → 读 DB → 正确值 |

**判定**：300s 不一致窗口可接受。如需 0 延迟，后续可加 Redis Pub/Sub（不在 v9 范围）。

```python
        "visibility": getattr(seed, "visibility", "full"),

# 写入 frontend/src/generated/strategyMetaFallback.ts
```

## P1-5：Elasticity Cache 数据质量标签

**裁决**：`elasticity_data_quality` 唯一值域及语义：

| 值 | 含义 | 弹性评分行为 | 展示 |
|----|------|------------|------|
| `"ok"` | 缓存命中，今日盘前刷新 | 真实评分参与 `is_actionable` 降级 | "弹性 ★★★★☆（今日刷新）" |
| `"stale"` | 缓存存在但超过 1 日未刷新（盘前预热失败） | **不参与** `is_actionable` 降级。评分仍展示但标注"昨日数据" | "弹性 ★★★★☆（昨日数据，今日未刷新）" |
| `"partial"` | 部分数据可用（如分钟线缺失超过 30%） | **不参与** `is_actionable` 降级 | "弹性 ★★★☆☆（数据不完整）" |
| `"backtest_estimated"` | 回测环境，用日线代理计算（非真实分钟线） | 回测中参与统计但不标识为阻断 | "弹性估计值（回测模式）" |
| `"unavailable"` | 无弹性缓存且无法实时计算 | **不参与** `is_actionable` 降级 | "弹性暂无数据" |

**关键**：仅 `"ok"` 状态的弹性评分参与 `is_actionable` 降级。`"stale"`/`"partial"`/`"unavailable"` 不降级——宁可放过不可误杀。

## P1-6：probe_status 完整生命周期

```
初始状态（meta 种子创建时）
    probe_status = "not_required"          ← core/auxiliary 策略保持此状态
    visibility = "full"

探针触发（仅 leader_pullback_band 需要）
    ↓
probe_status = "pending"                   ← 脚本开始执行时设置（可选，用于 UI 展示"探针运行中"）
    ↓
    ├── 全部通过 → probe_status = "passed"
    │              visibility = "full"
    │              probe_summary = ""
    │
    └── 任一不通过 → probe_status = "failed"
                     visibility = "backtest_only"
                     probe_summary = "近24月仅11/24月满足...日均候选0.1个（需≥0.3）..."

手动重新探针（admin 触发脚本重新执行）
    ↓
probe_status = "pending" → 重新判断 → passed 或 failed

策略废弃
    ↓
visibility = "hidden"                      ← admin 手动设置
probe_status 保持原值
```

**探针失败后的行为**：

| 入口 | 行为 |
|------|------|
| `/api/strategies/meta` | 返回该策略，`visibility="backtest_only"`，`probe_status="failed"` |
| 策略工作台·卡片 | 显示"数据探针未通过 — 仅回测研究"标签 |
| Playbook research tabs | 不出现（visibility != "full"） |
| 回测选择器 | 可选中，带 badge"仅回测研究" |
| 优先榜 | 不出现（tier=research 且 visibility != "full"） |
| 回测预设 | 不出现（非生产层） |
| App | 不出现（非 core/auxiliary） |

## P1-7：策略预设的生产策略隔离

**裁决**：`DEFAULT_PRESETS` 三处预设的 `strategies` 数组必须使用 `_default_production_strategy_keys()`，该函数返回：

```python
def _default_production_strategy_keys() -> list[str]:
    """仅返回 production 层策略（core + auxiliary），且 enabled + visibility==full。"""
    from app.services.low_buy.strategy_policy import StrategyTier

    PRODUCTION_TIERS = {StrategyTier.CORE.value, StrategyTier.AUXILIARY.value}
    return [
        seed.key
        for seed in DEFAULT_STRATEGY_META
        if seed.tier in PRODUCTION_TIERS
        and getattr(seed, "enabled", True)
        and getattr(seed, "visibility", "full") == "full"
    ]
```
