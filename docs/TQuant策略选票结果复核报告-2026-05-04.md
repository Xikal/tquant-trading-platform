## 三、发现的问题

### 问题 1 (严重): RESEARCH 层策略违规发出 buy_now/soft_buy_now 信号

**涉及策略**: classic_retrace, ma_support
**严重程度**: P1 — 违反策略管理制度

**现象**:
- `ma_support` (RESEARCH 层) 发出 68 条 `buy_now` + 29 条 `soft_buy_now`
- `classic_retrace` (RESEARCH 层) 发出 20 条 `buy_now` + 26 条 `soft_buy_now`

**预期行为**:
根据 `strategy_policy.py` 的 `strong_buy_paused()`，RESEARCH 层和 FACTOR 层策略的强买应被暂停：

```python
# strategy_policy.py, lines 47, 103-104
STRONG_BUY_PAUSED_STRATEGIES = RESEARCH_STRATEGIES | FACTOR_STRATEGIES

def strong_buy_paused(strategy_key: str) -> bool:
    return get_strategy_tier(strategy_key) in {StrategyTier.RESEARCH, StrategyTier.FACTOR}
```

信号解析管线 `signals.py` 中，`_can_hard_buy_now()` 和 `_can_soft_buy_now()` 的第一道检查即为 `strong_buy_paused`：

```python
# signals.py, lines 294-301
def _can_hard_buy_now(self, candidate, entry_position, hard_confirmed):
    if strong_buy_paused(candidate.strategy_key):
        return False  # ← 应在此阻断
    ...
```

**代码逻辑分析**:

数据流程为 `_build_candidate_output` → 初始信号状态（仅 watch/avoid）→ `_apply_live_quotes` → `_refresh_buy_signal` → `_resolve_signal_state`。在 `_resolve_signal_state` 中，只有当 `_can_hard_buy_now()` 或 `_can_soft_buy_now()` 返回 True 时，才会将状态设为 `buy_now`/`soft_buy_now`。这两个方法的第一行都是 `if strong_buy_paused(...): return False`。

按代码逻辑，ma_support 和 classic_retrace 不应有任何 buy_now/soft_buy_now 候选。但数据库中存在大量此类记录。

**可能原因**:
1. 数据库快照是 `strong_buy_paused` 实现之前生成的旧数据，未被刷新
2. 存在绕过 `_resolve_signal_state` 的信号设置路径

**建议**:
1. 触发一次全量重新扫描，验证新生成的结果是否正确
2. 在 `_build_candidate_output` 中增加防御性检查：对 RESEARCH/FACTOR 策略强制 `buy_signal_state` 不超过 `near_entry`
3. 对存量数据库结果增加版本标记，旧版本自动失效

### 问题 2 (严重): volume_shrink 策略出现低于分数阈值的 buy_now 候选

**涉及策略**: volume_shrink
**严重程度**: P1 — 违反买入分数门槛

**现象**:
数据库中存在 1 条 volume_shrink 策略的 `buy_now` 候选，score 仅为 79.0：

```
001269 欧晶科技 score=79.0 buy_signal_state=buy_now
  entry_zone=[22.167, 22.48] stop_loss=21.38 latest_price=21.84
```

**预期行为**:
`_hard_buy_min_score` 对 volume_shrink 的定义为 80.0：

```python
# signals.py, lines 614-622
def _hard_buy_min_score(candidate):
    base = {
        "limit_up_breakout_retrace": 88.0,
        "divergence_consensus": 90.0,
    }.get(candidate.strategy_key, 80.0)  # volume_shrink → 80.0
    if candidate.risk_tier == "degrade":
        base += 3.0
    return base + max(candidate.dynamic_threshold_adjustment, 0.0)
```

`_can_hard_buy_now` 中检查 `candidate.score < self._hard_buy_min_score(candidate)`，分数 79.0 < 80.0（假设 dynamic_threshold_adjustment 非负）应返回 False。

此外，该候选价格为 21.84，而 entry_zone 为 [22.167, 22.48]，即价格处于 `below_zone`。对于 volume_shrink，`_below_zone_hard_buy_allowed` 返回 False（volume_shrink 不在允许 below_zone 硬买的策略集合中）。同样，`_can_soft_buy_now` 对 below_zone 也无路径通过（仅允许 in_zone 和 near_above_zone）。

**代码逻辑分析**:
分数 79.0 的候选应无法通过 `_can_hard_buy_now`（79.0 < 80.0），也无法通过 `_can_soft_buy_now`（in_zone 需 85.0，near_above_zone 需 89.0，且 near_above_soft_buy_allowed 对 volume_shrink 返回 False）。处于 below_zone 时两个方法都应返回 False。

**结论**: 这是明确的信号分类错误。该候选绝不应为 `buy_now` 状态。

**建议**:
1. 排查该条记录的生成时间，确认是否为旧代码产物
2. 增加 `_can_hard_buy_now` 和 `_can_soft_buy_now` 的单元测试，覆盖分数边界、各 entry_position 和各策略
3. 在 `_initial_signal_state` 到最终状态的转换路径上增加断言/日志，捕获不可能的 buy_now 分配

### 问题 3 (中等): 平均分数异常偏高

**涉及策略**: 所有 4 个有结果的策略
**严重程度**: P2 — 评分有效性值得审视

**现象**:

| 策略 | buy_now 平均分 | buy_now 最低分 | buy_now 最高分 |

| classic_retrace | 95.0 | 89.3 | 99.0 |
| first_board | 94.9 | 89.0 | 99.0 |
| ma_support | 95.1 | 86.8 | 99.0 |
| volume_shrink | 93.9 | 79.0 | 99.0 |

**分析**:
- 所有 buy_now 候选的平均分 > 93，在 0-100 的评分范围内高度集中
- 最高分全部触及 99.0 天花板
- 分数区分度极低：buy_now 候选的实际分数范围仅 79.0-99.0，其中 79.0 本身是违规的（见问题 2）；合规范围内的最低分为 86.8
- `near_entry` 和 `watch` 状态候选的分数没有在数据库中直接查询，但从评分公式来看，分数的总体压缩会影响信号层的区分能力

**评分公式回顾**:
```
adjusted_score = max(0, base_score + signal_bonus + factor_bonus - score_penalty)
```

其中各策略的 `score_candidate()` 内 bonus 范围为 3-6 分，retracement bonus 在回踩第 3 天达到峰值 +8 分，market_state penalty 当前市场状态下可能为 0 或低值。

**建议**:
1. 查询 `near_entry`、`watch`、`avoid` 状态的分数分布，评估分数是否在全范围内均匀分布
2. 考虑提高评分天花板或引入更陡峭的惩罚曲线
3. 验证 `PULLBACK_HEALTH_MAX_SCORE = 94.0` 是否真正限制了分数上限

### 问题 4 (严重): 仅 4/12 策略产生结果，8 个策略零覆盖

**涉及策略**: 全部 12 个策略
**严重程度**: P0 — 系统功能缺失

**根因**:
`backend/app/main.py` 第 56-59 行：

```python
def _background_low_buy_strategies() -> list[str]:
    if settings.database_url.startswith("sqlite"):
        return [DEFAULT_PRODUCTION_LOW_BUY_STRATEGY]  # 仅 "first_board"
    return list(PLAYBOOKS.keys())
```

在 SQLite 模式下，后台任务只运行 `first_board` 一个策略。而 `DEFAULT_PRODUCTION_LOW_BUY_STRATEGY = "first_board"`。

**影响**:
- 3 个 AUXILIARY 生产策略：late_session_strong_support、core_midcap_vwap_ma5_retrace、sector_mainline_first_divergence_low_buy —— **完全无扫描结果**
- 2 个 CORE 策略中的 volume_shrink —— 有结果但来自手动触发，非自动更新
- 5 个 RESEARCH 策略中仅 classic_retrace 和 ma_support 有结果（说明有人手动触发了 API 扫描）
- 2 个 FACTOR 策略默认 disabled（`strategy_pool_config.py` 中 `enabled=False`），无结果属预期

**注**: 用户环境中 `volume_shrink`、`classic_retrace`、`ma_support` 有数据，应是此前通过 API 手动触发了 `scan_mode=full`。

**建议**:
1. 最直接的方案：将 SQLite 模式的单策略限制扩展为所有 PRODUCTION 策略（CORE + AUXILIARY，共 5 个）
2. 更彻底的方案：串行轮询全部 12 个策略，对每个策略使用合理的 scan_limit
3. 短期折中：至少将 `_background_low_buy_strategies()` 的返回值改为 `list(PLAYBOOKS.keys())`（等同于非 SQLite 模式），在低并发 SQLite 环境串行执行不会造成写冲突

### 5.2 limit_up_pool 池源（9 个策略）

**池源数据规模**: 数据库 `low_buy_pool_snapshots` 包含 709 个独立股票、5946 条记录（2026-04-03 至 2026-04-27），来源于 `ak.stock_zt_pool_em` 接口（涨停板股票池）。board_count 分布：首板 5328 条（89.6%）、2 板 448 条（7.5%）、3+ 板 170 条（2.9%）。日均成交额 11.5 亿元。

**池源使用流程**: 所有 9 个极限池策略共享同一个底层池，通过以下步骤差异化筛选：

1. `_prefilter_scan_targets` — 池规模 > 80 时，滤除成交额 < 3000 万的标的，至少保留 25%（最低 30 个）
2. `_load_strategy_scan_pool` — 尝试加载策略专用持久池（表 `low_buy_strategy_pool_snapshots` 不存在，总是回退到 `build_from_ranked`），仅做去重 + 数量截断
3. `_prepare_strategy_scan_targets` — 对 `requires_mainline_industry` 的策略（仅 daily_history 3 个）过滤热点行业
4. `_passes_candidate_filters` — 排除 ST 和 68/4/8 开头标的
5. `_passes_common_prefilter` — 通用条件：board_gain_ok, volume_burst >= 0.85, support_watch_ok, latest_change_ok, board_count <= 4（daily_scan 策略为 <= 2）
6. `passes_strategy_prefilter` — 策略特定的深度筛选规则

**关键发现**: `low_buy_strategy_pool_snapshots` 表在数据库中不存在（虽然 ORM 实体已定义），因此 `StrategyPoolBuilder.persist()` 总是静默失败。这意味着每个策略 pool_key 的配置在当前环境中实际上没有生效——所有 4 个活跃策略实质上从相同的 709 只股票池出发，仅靠策略特定的 prefilter 区分。

### 5.3 策略特定 prefilter 规则对比

各策略的 `candidate_rules.passes_strategy_prefilter` 定义了第一道深度筛选。以下是核心差异：

**first_board (CORE)**:
- `board_count == 1`（严格首板）
- `retracement_days`: 1-6
- `board_low_held == True`
- `volume_burst_ratio >= 1.25`
- `latest_close <= board_high * 1.045`
- `distribution_risk_score < 5.8`

### 5.5 board_window 和 retracement_days_max 合理性

**classic_retrace 的异常配置**:
- `board_window_days = 13`: 比 first_board 的 10 天更宽，这在策略逻辑上合理（"十日内有涨停启动"），但 `_resolve_active_structure_trade_date` 在最长的窗口基础上取最大交易日数
- `retracement_days_max = 12`: **与策略描述严重不符**。策略文档说"回调 2-4 天最优"，但 `_build_retracement_buckets` 使用 max_days=12 构建分桶，意味着会考虑回踩 1-12 天的股票。12 天的回踩时间远超"2-4 天最优"的范畴。对比 first_board 的 retracement_days_max=7，classic_retrace 的 12 天过于宽松

**divergence_consensus 的时间窗口**:
- `board_window_days = 13`，`retracement_days_max = 12`：该策略寻找"底部涨停 → 分歧横盘 → 倍量突破"的结构，需要较长观察窗口，配置合理

**daily_history 策略的统一配置**:
- 3 个主线策略统一使用 14 天 window + 8 天 retracement max：对于 daily_history 源，window 控制从日线数据中取多少交易日历史，合理

### 5.7 策略预过滤器的问题汇总

**classic_retrace 缺少专用 prefilter**:
该策略使用默认 fallback prefilter（`board_count <= 2, retracement 1-6, volume >= 1.05`），这个规则极为宽松且与策略文档不符。策略要求"十日内有涨停启动，缩量回踩均线"，但 fallback 规则没有检查 board_low_held、board_open_held 等首板关键位置条件。建议为其实现专用 prefilter。

**ma_support 的 board_count 上限偏高**:
`board_count <= 3` 允许 2 板和 3 板股票进入，但这些高连板标的回撤后往往不再是"基本面趋势良好"的均线支撑标的，而是高位博反弹的投机品。建议收窄为 `board_count <= 2` 或增加额外的趋势强度要求。

**volume_shrink 缺少 board_count 限制**:
与其他策略不同，volume_shrink 没有显式限制 board_count，仅通过 score_candidate 中 `board_count >= 3 → penalty -4` 间接约束。建议显式添加 `board_count <= 2` 以明确策略意图。

**daily_history 策略的入口条件**:
3 个 AUXILIARY 策略的 pool 构建依赖 `daily_bar_is_tradable_for_low_buy`（排除涨停/跌停板收盘），锚点筛选依赖 `daily_anchor_matches_strategy_pool`（量比 >= 1.15 或金额 >= 1.8亿，且强阳线）。这些条件与策略描述一致。但当前无法验证，因为数据不足。

### 5.8 daily_history 策略数据不足详解

- `_load_daily_rows_by_symbol` 从 `daily_bar_snapshots` 表读取所有符合热点行业的股票日线数据（每批 800 只）

`_resolve_latest_completed_trade_date` 的 Stage 6 修复（`pool.py`）已处理数据不足时的回退逻辑，但需要先解决问题 4（后台扫描限制）使策略能运行后，才能验证日线策略的完整扫描流程。

## 六、market_state 影响分析

查询 first_board 的 market_state 分布：全部 334 条记录中 `market_state=None`。这可能表示：
1. 数据库中的快照是在 market_state 字段被引入之前生成的
2. 或者当前的 market_state 未被正确写入结果快照

如果 market_state 全为 None/空，则 `resolve_strategy_market_profile` 会 fallback 到 `"low_volume_wait"` 状态，这是一个相对中性的市场状态。在这种情况下：
- first_board: `hard_buy_allowed=True`, `soft_buy_allowed=True`（score_penalty=2.8, ranking_bonus=-1.4, position_multiplier=0.72）
- volume_shrink: `hard_buy_allowed=True`, `soft_buy_allowed=True`

这意味着当前所有候选都在"低量无主线"的默认市场假设下评估，比实际市场可能偏宽松或偏紧。

## 八、结论

当前 12 个策略中仅 4 个有实际的选票结果，主要受限于 SQLite 模式下后台扫描仅运行单一策略。在有数据的 4 个策略中：

- **first_board** 表现基本正常，符合 CORE 策略规范
- **volume_shrink** 存在 1 条明确的信号分类错误（score=79.0 标记为 buy_now），且缺少显式 board_count 限制
- **classic_retrace / ma_support** 存在严重的 RESEARCH 层管理制度违反——总计 143 条不应出现的 buy_now/soft_buy_now 信号

**扫描范围方面的主要发现**：
- 所有 4 个活跃策略共享同一个 709 只股票的涨停池，策略池差异化依赖 prefilters 而非独立池（策略池持久化表缺失）
- classic_retrace 的 retracement_days_max=12 与其"回调 2-4 天最优"的策略描述不符
- classic_retrace 缺少专用 prefilter，使用宽松的默认 fallback 规则
- ma_support 的 board_count <= 3 偏宽，与均线支撑策略定位存在张力
- 3 个 daily_history 策略完全无数据，需先扩展后台扫描再验证

核心修复路径：扩展 SQLite 后台扫描 → 清理旧数据 → 修复策略池参数 → 全量重新扫描 → 验证所有策略的信号分类正确性。
