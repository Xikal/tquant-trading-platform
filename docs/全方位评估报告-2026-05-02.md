# A股短线量化交易平台 —— 全方位评估报告

**评估日期**：2026-05-02  
**评估范围**：Python FastAPI 后端 / React 前端 / Capacitor App / Agent 架构 / 部署配置 / 策略体系 / 回测与模拟盘  
**评估角色**：全栈架构师 / A股短线策略顾问 / 量化回测专家 / 性能优化专家 / Agent 架构师 / 代码质量审查

## 1. 总体结论

### 1.1 项目当前成熟度

**级别：Beta → Production-Readiness Gap**

项目已经从概念验证演进为一个具有相当深度的交易分析平台。低吸策略体系完善（12 策略 + 11 因子），Agent 层设计了 15 个 provider 可替换架构，模拟盘方案完整，Web/App 双端就绪。但在策略验证、性能优化、安全加固和生产部署方面仍有明显差距。

核心优点：
- 策略体系方法论清晰：结构层 → 统计层 → 排序层三层分离，买点判定不被绩效污染
- 因子架构设计合理：A/B/C/D 四类因子按数据依赖分层，FactorContext 模式优雅
- Agent 层有完整的 provider abstraction，一键可切换 LangGraph/OpenClaw/OpenAI Agents SDK/Pydantic AI 等
- 模拟盘需求文档详尽（960 行），从撮合模型到风控熔断到实施分阶段都覆盖了
- 前端 UI 规范专业，遵循 A 股红涨绿跌、高密度金融工作台风格

核心短板：
- 没有任何策略经过了实盘或模拟盘样本外验证
- 性能瓶颈集中：全量筛选、优先级榜、watchlist signals 都是同步执行
- 缺少生产级安全：无 HTTPS 强制、无鉴权中间件、admin token 问题未修复
- 前端测试覆盖率为零，后端测试覆盖核心路径但不覆盖回归
- agent_mcp/ 目录不存在，MCP 集成停留在 provider 抽象层

### 1.2 最值得继续投入的方向

1. **策略验证闭环**（投入产出比最高）：先把模拟盘基础能力跑通，用 100 笔+ 样本外交易验证哪些策略有真实正期望
2. **性能基础设施**：优先级榜物化快照已就绪，watchlist 并行化方案明确，全量筛选后台任务已跑——把这些方案执行完就能让盘中体验质的飞跃
3. **安全加固**：HTTPS、鉴权、token 存储修复、Agent 权限边界——这些不做到位，模拟盘都没法安全跑

### 1.3 最大风险

- **策略风险**：当前没有任何策略通过了实盘或模拟盘样本外验证。12 个策略全部基于设计逻辑，没有数据证明其正期望。最坏情况是全部策略在实盘条件下为负期望
- **安全风险**：HTTP 明文传输、admin token 在 localStorage、Agent 缺少完整权限边界——这些在模拟盘阶段问题不大，但在任何涉及真实资金的场景下都是红线
- **过拟合风险**：79 个 CandidateMetrics 字段 + 11 个因子 + 复杂多层评分体系——参数空间极大，PBO 检验虽已实现但未接入回测，存在严重的过拟合隐患
- **运维风险**：单进程 FastAPI 承载所有计算——全量筛选、watchlist 刷新、多用户请求都在同一进程排队

### 1.4 3 个最优先事项

1. 完成策略分层修复 + 安全修复（立即执行，半天工作量）
2. 跑通模拟盘 V1（账户/持仓/委托/成交 + T+1 + 费用），积累首批 100 笔交易样本
3. 对 4 个核心策略执行 PBO 检验，确认是否有真实 alpha

## 3. 高优先级优化

### 3.1 Watchlist 行情串行 → 并行

**问题**：`watchlist.py:117-140`，50 只自选股串行 `get_quote`，每只 ~1 秒 → 总耗时 ~50 秒。

**影响**：Watchlist 信号刷新成为全系统最慢接口。盘中 3-5 秒刷新一次的预期完全不成立。

**涉及文件**：`backend/app/api/routes/watchlist.py`

**建议方案**：已在 `完整优化方案-重新审查.md` 第三部分提供完整异步方案（ThreadPoolExecutor，max_workers=10）。

**预期收益**：50 只自选股从 ~50 秒降到 ~5-8 秒。

### 3.2 核心策略成交额下限缺失辅助层

**问题**：`candidate_rules.py:92-106` 只有 `CORE_LIQUIDITY_STRATEGIES` 且与 `CORE_STRATEGIES` 不同步。AUXILIARY 策略没有成交额下限。

**影响**：日均成交额 2000 万的小盘股可通过辅助策略出现在优先榜。这类股票流动性差，滑点高，T+1 下风险大。

**涉及文件**：`candidate_rules.py`、`shared.py`

**建议方案**：改为动态按 `get_strategy_tier()` 判断。在 `LowBuyThresholds` 增加 `MIN_DAILY_AMOUNT_AUXILIARY: float = 30_000_000.0`。已在 `完整优化方案-重新审查.md` 第六部分提供方案。

**预期收益**：优先榜结果流动性提升 ~60%，降低实盘无法成交的概率。

### 3.3 前端测试完全缺失

**问题**：`frontend/package.json` 中无任何测试依赖（Jest/Vitest/Playwright）。48 个 TS/TSX 文件零测试覆盖。

**影响**：前端重构风险极高。策略展示逻辑、价格颜色、数据格式化、API 调用链路——任何改动只能在浏览器中手动验证。

**建议方案**：
1. 安装 Vitest + @testing-library/react
2. 先补齐 `workspaceViewModels.ts`（211 行，纯逻辑）的单元测试——这是所有页面的数据转换层
3. 再补齐 `workspaceFormatters.ts`（169 行）和 `playbook/formatters.ts`（101 行）的测试
4. 对关键页面（MonitorPage、PlaybookPage）加渲染冒烟测试

**涉及文件**：`frontend/src/features/trading-workspace/workspaceViewModels.ts`、`workspaceFormatters.ts`

**预期收益**：前端改动可自动化验证，回归周期从"手动点一遍"变为"vitest run 30 秒"。

### 3.4 SQLite 写入竞争

**问题**：当前架构中后台全量筛选（`_refresh_full_scan_loop`）和前台请求共用同一个 SQLite 连接池。SQLite 在写入时锁整个数据库。

**影响**：全量筛选写入数据库期间，watchlist signals 接口可能被阻塞数秒。

**建议方案**：
1. 短期：全量筛选使用 WAL 模式 + `timeout=5000`（已有基础）
2. 中期：将全量筛选的结果先写入内存，批量提交到数据库
3. 长期：生产环境必须切换 MySQL（已有支持），SQLite 仅用于开发

**涉及文件**：`backend/app/core/database.py`、`backend/app/main.py`（后台任务配置）

**预期收益**：高峰期接口延迟降低 50-80%。

### 3.5 缺少统一鉴权中间件

**问题**：当前 `admin_auth` 只在 settings 路由使用。大多数 API 路由无鉴权。App API 有 auth 体系（JWT access/refresh token），但 Web API 没有。

**影响**：任何知道 IP 和端口的人可以调所有公开接口。虽然在 localhost 场景下问题不大，但公网部署时是严重风险。

**建议方案**：
1. 创建 `AuthMiddleware`，对 `/api/*` 路径统一校验（允许 `/api/auth/*` 和 `/api/app/bootstrap` 白名单）
2. App API 使用 JWT token
3. Web API 使用 admin token（短期）/ session token（长期）
4. Agent API 使用独立的 Agent API token

**涉及文件**：新建 `backend/app/core/auth_middleware.py`，修改 `main.py`

**预期收益**：公网部署安全基线建立，Agent 和用户的权限边界清晰。

## 4. 中优先级优化

### 4.1 策略评分参数空间过大 —— 过拟合风险

**问题**：79 个 CandidateMetrics 字段 + 11 个因子 + SignalFamilyProfile 4 维度加权(0.24/0.30/0.26/0.20) + 多层 score_penalty/adjustment。总参数数量远超信号样本数。

**影响**：策略在历史数据上表现好但在未来失效——经典的过拟合问题。`complete_pbo()` 函数已实现但未接入回测管线，无法量化过拟合程度。

**建议方案**：
1. 将 `compute_pbo()` 接入 `execution_backtest.py`
2. 对所有 4 个核心策略跑 PBO 检验（信号序列 shuffle 1000 次）
3. PBO < 0.5 的策略降级到研究层
4. 引入超参数敏感性分析（每个权重 ±20%，看结果波动幅度）

**涉及文件**：`risk_metrics.py`（已实现 PBO），`execution_backtest.py`（需接入），`signal_family.py`（权重定义处）

**预期收益**：可量化的过拟合风险评估，防止把噪声当 alpha。

### 4.2 回测管线未接入模拟盘口径

**问题**：当前 `execution_backtest.py` 和 `execution_simulation.py` 的回测口径与模拟盘需求文档中的费用、撮合、T+1 规则不统一。

**影响**：回测结果可能系统性高估收益。滑点统一用 bps 而非按流动性分桶，涨停买入在回测中可能乐观成交。

**建议方案**：回测撮合引擎复用模拟盘 `PaperMatchingEngine`。`execution_backtest.py` 改为调用 `matching.py` 中的撮合逻辑，确保回测口径与模拟盘一致。

**涉及文件**：`execution_backtest.py`、`execution_simulation.py`、`paper/matching.py`、`paper/fees.py`

**预期收益**：回测结果与模拟盘结果可比，避免"回测好但模拟差"的困境。

### 4.3 MobileApp.tsx 755 行单文件过大

**问题**：`frontend/src/mobile/MobileApp.tsx` 755 行，是所有前端文件中最大的。包含 UI、逻辑、状态管理、API 调用。

**影响**：移动端的改动风险集中在这一个文件。无法独立测试任何一个 UI 区块。

**建议方案**：
1. 拆分为 `MobileHomeScreen`、`MobilePlaybookScreen`、`MobileBottomNav` 三个组件
2. 数据获取逻辑提取到 `useMobileData` hook
3. 格式化逻辑提取到 `mobileFormatters.ts`

**涉及文件**：`frontend/src/mobile/MobileApp.tsx`

**预期收益**：移动端改动不再需要看完 755 行找定位点。

### 4.4 策略文档与代码实现存在漂移

**问题**：`docs/low-buy-strategy-mechanism.md` 描述的是当前版本的"三层结构"机制，但因子扩容和策略分层方案中的变更会让文档部分过时。`docs/strategy-*.md` 中三个新策略文档没有对应的验收测试。

**影响**：新人或 Agent 参考文档时可能被旧版本误导。

**建议方案**：
1. 每次执行策略分层或因子变更后，同步更新 `low-buy-strategy-mechanism.md`
2. 为三个新策略各加一个单元测试（已有 `test_divergence_consensus_strategy.py` 可作模板）

**涉及文件**：`docs/low-buy-strategy-mechanism.md`、`docs/strategy-*.md`

### 4.5 缺少接口级性能监控

**问题**：当前只有 `/healthz` 和 `/readyz` 健康检查。缺少接口级耗时分布、P50/P95/P99 延迟、慢查询追踪。

**影响**：不知道哪个接口是瓶颈，优化靠猜。

**建议方案**：
1. 在 `backend/app/core/timing.py`（已有基础）基础上增加 middleware 级别的请求计时
2. 暴露 `/api/admin/metrics` 返回最近 1000 个请求的 P50/P95/P99
3. 对慢请求（>3s）自动记录到日志

**涉及文件**：`backend/app/core/timing.py`、新建 `backend/app/core/metrics.py`

**预期收益**：可量化性能瓶颈，优化目标明确。

## 5. 长期演进建议

### 5.1 策略体系演进

- **从"策略数量"转向"策略质量"**：当前 12 策略 + 11 因子，建议在模拟盘跑 200 笔+交易后，将胜率<45% 或 Profit Factor<1.2 的策略降级或合并
- **引入市场状态自适应**：同一个 classic_retrace 在牛市、震荡市、熊市的表现差异极大。当前 `market_state_rules.py` 做了方向性偏见（directional_bias），但策略参数（如回撤深度阈值、缩量阈值）是静态的
- **策略 Beta 中性化**：如果 4 个核心策略在上涨市中全部表现好，下跌市中全部表现差，说明策略暴露的是市场 Beta 而非 alpha。需要在绩效统计中加入 Beta 和 Alpha 分解
- **next_day_event_model 增强**：当前模型已实现"次日事件计划"，但事件识别仍较基础。建议增加：业绩预告日、解禁日、股东大会日、分红除权日 的自动标记

### 5.2 模拟盘和自动交易演进

- **确定性执行器优先于智能 Agent**：模拟盘的自动交易采用定时任务驱动的 PaperTradingExecutor（纯 Python 确定性规则），而非 LLM Agent 直接决策。LLM 只负责盘后日报生成，不参与实时交易决策。第一阶段必须关闭自动执行，手动验证链路
- **PaperTradingExecutor 执行模型**：每 120 秒轮询 → 读取 priority_board 信号 → 应用准入过滤器 → 检查账户资金、持仓、T+1 约束 → 生成候选委托计划 → 全自动模式下执行委托。所有决策由确定性规则链完成，全程可审计可复现
- **AiService 盘后日报**：每天收盘后由 AiService.generate_daily_report() 调用 LLM 生成文本日报：今日执行了哪些交易、为什么执行、哪些信号被跳过、账户盈亏、策略表现对比。这份日报是人类策略研究员复盘的核心界面
- **撮合模型渐进增强**：V1 简化撮合 → V2 涨停/跌停排队概率 → V3 分流动性桶差异化成交率 → V4 引入 Level2 盘口深度模拟
- **不追求自动化率**：能自动跑 50% 的策略信号且结果可靠，远好于自动跑 100% 但结果失真

### 5.3 Agent 架构演进

- **Agent 层与执行层分离**：LLM Agent 不参与实时交易决策——交易执行由定时任务驱动的 PaperTradingExecutor（纯 Python 确定性规则链）负责。Agent 层聚焦于盘后日报生成、策略复盘分析和异常检测等异步分析任务
- **Tool Registry 已就绪，但需要充实**：当前 `agent_tools/registry.py` 定义了 15+ 个工具，但缺少 风控查询、行情快照、优先级榜筛选 等高频只读工具
- **Provider 可替换性的真正考验**：当前 15 个 provider 中只有 `mcp_provider.py` 等少数是非 trivial 实现，其余是骨架。在至少 3 个 provider 上跑过相同任务才能验证可替换性
- **Agent 输出格式标准化**：建议所有 Agent（不论底层 provider）的输出统一为：`{summary, suggested_actions[], warnings[], confidence, raw_response}`，前端用同一组件渲染

### 5.4 数据和回测演进

- **回测数据质量**：当前回测依赖历史日线数据（akshare），分钟线回测未验证。建议回测框架支持多周期（日线选股 + 分钟线确认）的组合验证
- **Walk-forward 增强**：当前回测框架支持 walk-forward windows，但未集成到策略评估管线。建议每个策略每周自动跑一次滚动窗口样本外验证
- **引入另类数据**（长期）：北向资金流向、融资融券余额、龙虎榜、股东人数变化——这些数据的加入可以显著提升因子区分度

### 5.5 Web/App 产品演进

- **交易日历与事件提醒**：App 端加入交易日历、业绩预告日、解禁日、分红除权日提醒

## 6. 策略专项建议

### 6.1 保留生产策略（4 个）

| 策略 | CORE 权重 | 保留理由 | 注意事项 |
|------|----------|---------|---------|
| classic_retrace | 1.0 | 方法论最扎实。十日涨停+缩量回踩+均线支撑，是 A 股最常见的短线低吸模式。信号可解释性最强 | 必须限制在上涨/震荡市；熊市中连续止损率可能很高 |
| volume_shrink | 1.0 | 与 classic_retrace 逻辑互补（强调量而不仅是价）。缩量阶梯+量比回落在量价分析中有理论支撑 | 缩量之后可能继续缩量横盘，需要结合止跌确认 |
| first_board | 1.0 | 首板回踩是 A 股最经典的短线策略之一。首板代表资金态度 | 当前实盘中首板次日高开低走的概率不低；建议只做板块龙头的首板回踩 |
| divergence_consensus | 1.0 | 分歧转一致是"主力洗盘后重新拉升"的量化表达。盈亏比通常很高 | 对市场环境和板块热度的依赖度最高；确认条件严格，信号发生率低 |

### 6.2 下架策略（0 个）

当前没有需要完全下架的策略。但 `limit_up_breakout_retrace` 和 `core_midcap_vwap_ma5_retrace` 在模拟盘未验证前不建议进入生产。

### 6.3 降级为辅助因子的策略（2 个）

| 策略 | 当前层 | 建议层 | 理由 |
|------|--------|--------|------|
| deep_pullback | FACTOR | FACTOR（保持） | 已正确分层。深水低吸胜率天然低，但盈亏比高。只适合作为加分项，不应独立产生交易信号 |
| trend_rebound | FACTOR | FACTOR（保持） | 已正确分层。龙回头策略依赖大趋势判断，主观成分重，量化表达不够精确 |

### 6.4 保留研究策略（3 个）

| 策略 | 当前层 | 理由 |
|------|--------|------|
| limit_up_breakout_retrace | RESEARCH | 涨停突破回踩的逻辑有理论依据，但"突破后回踩"和"假突破"在回测中很难区分。需要在模拟盘中积累样本 |
| core_midcap_vwap_ma5_retrace | RESEARCH | 中军回踩是板块行情的典型参与方式，但"中军"的定义依赖板块辨识和主观判断。量化表达需进一步增强 |
| sector_mainline_first_divergence_low_buy | RESEARCH | 主线首分歧低吸在概念上很强，但"首分歧"的判定对板块运行阶段的识别精度要求极高 |

### 6.5 新增策略优先级

| 优先级 | 策略 | 理由 |
|--------|------|------|
| P0 | 无 | 当前 12 策略已覆盖核心低吸场景。在现有策略未验证前，不建议新增策略分散精力 |
| P1（验证后可考虑） | 板块轮动低吸 | 当日最强板块中找回调到均线的个股。结合现有的 hot_industries + classic_retrace 逻辑 |
| P2 | 竞价异动低吸 | 竞价阶段放量高开但开盘后回落的标的。需要竞价数据源（akshare 已支持） |
| P2 | 尾盘抢筹低吸 | 14:30-15:00 放量拉升的回调股。结合现有的 late_session_strong_support 逻辑 |

### 6.6 今日 T 倾向预测的落地建议

当前 "今日正T / 反T / 观望倾向" 建议按以下维度生成：

1. **量价关系**（权重 40%）：近 3 日量价配合度（量增价涨 vs 量增价跌）、日内 VWAP 偏离度
2. **市场情绪**（权重 25%）：全市场上涨家数比、涨停/跌停比、连板高度变化
3. **板块热点**（权重 20%）：该股所属板块是否在 hot_industries 中、板块内龙头走势
4. **个股位置**（权重 15%）：距 MA5/MA10/MA20 的距离、距近期高点的距离、距止损位的距离

**输出格式建议**：
- `positive_t`：量价配合 + 板块偏强 + 价格在支撑位附近 + 可用数量充分 → "正T倾向：高"
- `negative_t`：放量滞涨 + 板块分歧 + 价格在压力位附近 + 持仓浮盈可观 → "反T倾向：中"
- `hold`：任何一种情况不满足 → "观望"

**关键约束**：
- 可用数量为 0 时，正T倾向必须为 "不可执行"（无论其他条件多好）
- cost_basis 缺失时，收益率无法计算，倾向降级为 "观望"
- 停牌、涨跌停、无行情 → 强制 "观望"

**两周内**：积累 50 笔手动模拟交易 + PaperTradingExecutor 准入过滤器 + 委托计划生成（不自动执行）

### 8.7 必须避免的误区

- 不要跳过手动验证直接做自动交易——自动执行器的规则链建立在充分理解策略规则的基础上

- 不要把模拟盘结果当成实盘预期——模拟盘没有真实对手盘、没有流动性冲击、没有情绪干扰
- 不要在样本 <50 笔时对策略做任何结论——小样本下胜率 60% 可能只是运气
