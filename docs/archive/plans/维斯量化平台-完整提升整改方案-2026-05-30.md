## 1. 总体结论

**平台底子成熟、历史问题治理认真，但最近一次 `front-row + analytics` 变更引入了必须先处理的 P0/P1。**

- 上一版自评（2026-05-01）的 4 个 P0 已全部闭环：Agent 端点鉴权、`net_win_rate` 公式、httpOnly cookie、admin 503。
- 回测工程扎实：前视守卫（信号次日入场）、T+1、真实费用、保守滑点+市场冲击、涨跌停/停牌拒单、**真实组合 max5/max10 约束齐全**。
- 新功能边界设计严谨：`production_score` 只允许 `buy_now/soft_buy_now`、`near_entry` 恒为 null、`front_row_only` 强制 watch-only、`production_sort_replaced=false` 全程成立、前端零 `useState/useReducer`、契约类型已接入。
- **但**：① 24M 回测证据没有回写到生产分层（-88%/-51% 回撤的 N 字仍是 CORE）；② DuckDB/Analytics 写完未接入线上；③ 线上裸 IP+HTTP 承载会话 cookie；④ DuckDB 报告口径误导；⑤ 复杂度/表面积仍偏大（low_buy ~130 文件、19 后台 loop、Python+Go+Rust+ML/RL）。

**四个核心判断：**

| 决策 | 结论 | 理由 |
|---|---|---|
| 继续保持线上运行 | **可以，但裸 IP+HTTP 不接真实用户/数据** | 平台不下真单；安全短板在传输层 |
| 进入小流量生产观察 | **否** | front_row readiness 未通过 + 生产基准榜被 N 字污染（P0-S1） |
| 替换生产排序 | **否（代码也确实没换，正确）** | `production_sort_replaced=false`，替换前须先修 P0 并过 OOS |
| 是否存在必须立即修复 | **是** | 1 个 P0 + 3 个 P1（见第 3 节） |

**最优先方向（顺序即执行顺序）：**
1. **S1 生产策略分层按 24M 证据一次性收口**（P0）
2. **SEC1 线上切域名+HTTPS**（P1）
3. **D2 DuckDB 报告口径修复**（P1）+ **T1 CI 加契约/前端门禁**
4. **D1 Analytics 一等公民上线**，让 24M 报告成为可复现、驱动分层门禁的权威输入（P1）
5. 再做瘦身、性能、长期治理（P2/P3）

**总策略：先收口与硬化，不扩功能；生产集合“宁可少而真”。**

## 4. 策略与回测：最终收口方案（对应 S1/S2/S3/D2）

### 4.1 生产分层门禁（永久规则，读最新 24M 报告）
| 准入 | 阈值 |
|---|---|
| 生产可评估下限 | 成交 ≥ 50 且 PF ≥ 1.2 且 最大回撤 ≥ -25% 且 平均单笔 > 0 |
| 升 CORE | 再加：成交 ≥ 400 且 PF ≥ 1.5 且 回撤 ≥ -20% |
| 入 AUXILIARY | 达下限未达 CORE；成交<100 标 `low_sample_capped`（限 cap、降权） |
| 落 RESEARCH | 未达下限（样本不可评估/PF<1.2/回撤<-25%/平均单笔≤0） |

## 5. 数据与分析层：Analytics 一等公民上线（对应 D1/D3/D4 + 闭环）

**决定：部署上线，不保留离线形态**——分层门禁要求 24M 报告在服务器可复现、可被守卫测试读取。

1. **镜像**：`Dockerfile` 加 `ARG INSTALL_ANALYTICS=0`（照搬现有 `WITH_RL` 模式 :46-49），为 1 时装 `requirements-analytics.txt`；产独立 tag `tquant-analytics:mysql`，默认镜像不变胖。
2. **compose**：新增 `analytics-worker`（照搬 worker 范式 :144-265）：`command: python backend/scripts/analytics_worker.py --poll-interval-seconds 2`（入口已存在）；`depends_on migration+mysql`；env 复用 + `TQUANT_ANALYTICS_ENABLED=true`/`TQUANT_ANALYTICS_ROOT`/`TQUANT_DUCKDB_THREADS`；挂 `app_runtime_data`；限 cpus/mem；healthcheck `import duckdb,pyarrow`。队列天然隔离（runtime-worker 只 claim 自己 allowlist，`runtime_worker.py:64`）。
3. **编排**：按需 `POST backtest_all_strategies_24m` + 每周定时 `enqueue strategy_24m_duckdb_report`；数据不足 `blocked_by_data` 硬门禁保留（`analytics_handlers.py:122-127`）；**常驻消费后孤儿任务从根上消失**。
4. **D4**：`analytics/__init__` 增依赖显式探测 fail-fast；**D3**：LONGTEXT 迁移 staging 计时+低峰执行。
5. **就绪/运维**：`/readyz` 增 analytics 维度；runbook 增 analytics 启动/补跑(`--once`)/排错/构建/回滚章节。

### 5.1 闭环（A 与 B 的核心价值）
```
analytics-worker 跑 24M（真实组合口径）→ 报告 keep/default_off/delete_candidate
  → 4.1 门禁 → strategy_policy 生产集合 ←守卫测试强制一致
  → baseline 榜 / production_score / 模拟盘自动交易 只用通过门禁的策略
```
单一事实源 = 24M 报告；自动纠偏（退化即降级、达标即回升），无人工过渡。

## 7. 性能优化方案

- **前端（F1）**：已 lazy+echarts 分包+30s 轮询+SSE；进一步拆 `MonitorPage`/`trading-workspace`/`backtest` 大组件、大表虚拟化、研究面板按需加载。

- **Agent（已良好）**：默认 `none`、write/notify 默认关、审计+限流。保持并加冒烟固化只读边界。
- **生产默认关闭项（E4）**：研究/模型治理 loop、RL、因子挖掘、自进化默认 false。
- **合规**：低吸榜/策略跟踪常驻“非荐股、不保证收益、不自动下单”免责；P0 修复后杜绝“-88% 策略出现生产强买”的展示合规风险。
