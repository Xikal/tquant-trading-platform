# A 股短线智能交易辅助平台 — 全方位架构评估报告

**评估日期**：2026-05-01  
**评估范围**：全仓库 162 个后端 Python 模块 + 50 个前端 TypeScript/TSX 文件  
**评估角色**：资深全栈架构师 / A 股短线策略顾问 / 性能优化专家 / 代码质量审查专家

---

## 一、总体结论

### 1.1 项目成熟度判断

本项目已经有很高的完成度，不是原型或演示项目——策略矩阵（12 个低吸策略 + 正T/反T量化引擎）、多端覆盖（Web + App）、后台任务、回测归因、生命周期管理都已经落地。但从"可投入真实资金生产"的标准来看，**当前版本定位为「高级回测验证阶段的策略工作站」更为准确**，距离全自动实盘还有 3-6 个月的扎实工作。

### 1.2 核心优势

- **策略矩阵设计思路清晰**：12 个低吸策略 + 量化做 T 引擎形成双层策略体系，从首板回调到深度低吸覆盖了主要低吸场景。
- **回测口径严谨**：从"触达最高价即算赢"升级为"真实执行口径"（先判断 2 日内买点触达，再按止损/止盈/移动防守退出，扣除 16bps 成本），这在同类项目中罕见。
- **架构分层可见**：FastAPI router → service mixin → repository → ORM 的分层虽然还有问题，但骨架是对的。
- **Agent 接入有前瞻性**：已规划了 7 个 Agent 框架适配器，Safe API 隔离层设计合理。

### 1.3 核心风险

1. **安全面严重不足**：大量 API 无鉴权、Agent 工具调用完全开放、auth token 存 localStorage、admin 回路绕过可被利用。
2. **策略体系缺乏市场情绪/板块热度/个股地位的顶层约束**：当前 12 个策略统一打分、统一排名，但市场环境不同时，首板回调策略和分歧转一致策略不应该同等权重。
3. **前后端均存在巨型单体组件**：TradingWorkspace.tsx（558行，48+ useState）、MobileApp.tsx（756行）难以测试和维护。
4. **回测指标存在 Bug**：`net_win_rate` 的计算与 `win_rate` 完全一致（`execution_backtest.py:123`），净值胜率字段名存实亡。
5. **无生产部署基础设施**：健康检查有、就绪检查有，但没有告警、没有指标导出、没有优雅关闭、后台任务没有监控。

## 二、立即处理（必须本周修复）

### [IM-1] Agent 工具调用端点完全无鉴权

**问题**：`POST /api/agent/provider/invoke`（`agent.py:93`）接受任意 `tool_name` 和 `arguments`，调用 `provider.invoke_tool()`，且无任何认证检查。目前注册的 6 个工具中包含 `push_notification`（可发送通知）和 `execute_query`（可执行数据库查询）。

**影响**：任何知道 URL 的人可以调用 Agent 工具，包括可能产生实际交易或数据泄露的操作。

**建议方案**：
1. 立即为该端点添加 `require_admin_auth` 依赖
2. 在 `agent_tools/policy.py` 中为每个工具标注风险等级（read_only / sensitive / dangerous）
3. `invoke_tool` 之前校验工具是否存在、是否允许调用、参数是否合法

**涉及模块**：`api/routes/agent.py`、`agent_tools/policy.py`、`agent_tools/registry.py`

**预期收益**：消除最大安全漏洞。

---

### [IM-2] `net_win_rate` 与 `win_rate` 完全相同（Bug）

**问题**：`execution_backtest.py:122-123`：

```python
win_rate=_rate(len(winners), len(filled)),
net_win_rate=_rate(len(winners), len(filled)),
```

两行完全相同。`net_win_rate` 应该 = `(winners - losers) / filled`，而不是 `winners / filled`。

**同样的问题** 存在于 `performance.py:352-353`：

```python
hit_rate=round(hit_count / max(filled_signals, 1) * 100, 2),
net_win_rate=round(hit_count / max(filled_signals, 1) * 100, 2),
```

**影响**：回测面板显示的"净胜率"指标与"胜率"完全相同，无法区分策略的盈亏结构。一个胜率 55% 但平均亏损远超平均盈利的策略，在净胜率上应该显著低于 55%。

**建议方案**：`net_win_rate = (len(winners) - len(losers)) / max(len(filled), 1) * 100`

**涉及模块**：`execution_backtest.py:123`、`performance.py:353`

**预期收益**：修复关键回测指标，避免策略评估失真。

---

### [IM-3] Auth Token 存储于 localStorage（XSS 风险）

**问题**：`api/base.ts` 将 access_token 和 refresh_token 存储于 `localStorage`。任何注入页面的恶意脚本（通过第三方 CDN 依赖或反射型 XSS）都可以读取这些 token。

**影响**：Token 泄露后攻击者可以无限制访问用户的所有接口。

**建议方案**：
1. 短期：access_token 缩短过期时间到 15 分钟
2. 中期：改用 httpOnly cookie + CSRF token 方案
3. 目前在 API 客户端中加 `Authorization` header 的做法保留，但 token 值从 cookie 中由后端注入的中间件读取

**涉及模块**：`api/base.ts`、`core/auth.py`、`routes/auth.py`

**预期收益**：消除 Token 窃取风险。

---

### [IM-4] admin_auth 回路绕过可被利用

**问题**：`admin_auth.py:52-53` 允许当 `ADMIN_API_TOKEN` 为空时，任何来自 loopback 的请求直接通过。如果应用部署在反向代理后面，且代理没有正确剥离 `X-Forwarded-For` header，攻击者可以伪造 `X-Forwarded-For: 127.0.0.1` 并携带 `Host: 127.0.0.1:8000`，绕过 admin 认证。

**影响**：Admin API（数据库迁移、系统配置修改等）可能被未授权访问。

**建议方案**：
1. 移除 loopback 绕过逻辑，强制要求 admin token
2. 或在 `_is_loopback_host` 中只信任 `request.client.host`（socket 级别 IP），不信任任何代理 header

**涉及模块**：`core/admin_auth.py`

**预期收益**：消除 admin 权限提升风险。

## 三、高优先级问题

### 3.1 策略体系

#### [S-1] 缺市场情绪与板块热度的上层约束

**问题**：12 个低吸策略各自独立评估候选股，统一打分后合并到优先级榜。但是：市场处于"高标退潮"（high_flyer_retreat）时，`limit_up_breakout_retrace` 和 `first_board` 策略的打板后回调逻辑天然不适合；而 `core_midcap_vwap_ma5_retrace` 和 `sector_mainline_first_divergence_low_buy` 策略在中军修复环境中反而更适用。当前系统只在 `dynamic_adjustments.py` 中做了粗粒度的 score_floor_shift（如 risk_release +5.0），但这是事后调整，不是事前过滤。

**建议方案**：
1. 在 `market_state_rules.py` 中为每个 market_state 定义"今日推荐策略优先序"，而非仅定义 score 调整
2. 引入"今日正 T / 反 T / 观望倾向"顶层判断：综合 `regime_scoring`（市值风格）、`emotion.py`（涨跌停情绪）、`mainline_strength.py`（主线热度）产出单一 directional_bias
3. 正 T 倾向日：优先展示 `classic_retrace`、`ma_support`、`volume_shrink`；反 T 倾向日：优先展示 `divergence_consensus`、`breakout_support`
4. 观望倾向日：所有策略统一降级为 "near_entry" 以下，不在优先级榜上展示 "buy_now"

**涉及模块**：`market_state_rules.py`、`dynamic_adjustments.py`、`priority_board.py`、`emotion.py`、`mainline_strength.py`

**预期收益**：解决"逆势打板被套"的核心痛点，显著降低回撤。

---

#### [S-2] 策略下架/降级建议

**建议降级为辅助因子的策略**（不再独立展示，只作为加分/减分项）：

| 策略 | 理由 | 行动 |
|---|---|---|
| `deep_pullback` | 回撤 -3% 到 -8% 的低吸在 A 股 T+1 制度下极高的跳空风险。无差异化信号源（量价、均线条件与 classic_retrace 高度重叠）。 | 合并到 `classic_retrace` 的深度回踩子场景 |
| `trend_rebound` | "N 字回拉" 的条件过于模糊（"前面明显主升浪" 是事后判断），样本量可能不足以支撑统计显著性。 | 降级为 `ma_support` 的风险加分因子 |

**建议保留生产的核心策略**（当前数据最扎实、逻辑最清晰）：

| 策略 | 优势 | 注意事项 |
|---|---|---|
| `first_board` | 首板后回踩是最经典的 A 股低吸模式，信号明确、止损清晰 | 需市场情绪过滤配合 |
| `classic_retrace` | 十日涨停+缩量回踩是最稳健的框架 | 需增加涨停性质的识别（游资/机构/消息驱动） |
| `volume_shrink` | 量价关系是最难造假的信号 | 需排除对倒放量的情况 |
| `divergence_consensus` | 分歧转一致是经典的右侧确认逻辑 | 需降低止损距离（当前 1.2% 止损对于分歧票偏紧） |

**涉及模块**：`strategy_pool_config.py`、`holding_policy.py`、`PLAYBOOKS`

#### [S-3] 过拟合与样本不足风险

**问题**：
- 部分策略（如 `core_midcap_vwap_ma5_retrace`）要求同时满足"主线板块、容量核心、VWAP确认、5日线回踩"四个条件，在 A 股当前市场宽度下可能每周只有 0-2 个样本。
- `performance.py` 中的 `RELIABILITY` 门槛：<20 样本 = 0 权重。但对于新策略，可能在 6 个月后才能积累到 20 个样本，这期间策略评分无意义。
- `signal_family.py` 中的 pullback_health 评分在回踩第 3 天达到峰值（96 分），这隐含了"回踩 3 天最优"的假设，但没有统计证据支持。

**建议方案**：
1. 对所有策略增加"有效样本量"的实时展示（当前只在 priority_scoring 中使用，但不对外暴露）
2. 样本量 < 30 的策略在优先级榜上显示"样本不足"标识，不参与排名
3. `signal_family.py` 的 pullback_health 曲线改为基于历史回测数据的动态曲线，而非硬编码
4. 引入"策略年龄"概念：上线 < 90 天的策略自动降权 50%

**涉及模块**：`priority_scoring.py`、`signal_family.py`、`performance.py`

#### [S-4] 新策略方向建议

| 新策略 | 逻辑 | 与现有策略的差异 | 验证指标 |
|---|---|---|---|
| **板块轮动低吸** | 当某板块连续 2 日资金净流入且板块指数回踩 5 日线时，低吸板块内未启动的跟风股 | 新增板块维度的择时信号，对应现有 `sector_mainline_first_divergence` 但更偏轮动而非分歧 | 板块轮动胜率、跟风股补涨率 |

### 3.2 后端架构

#### [A-1] Mixin 继承链过长且隐式耦合

**问题**：`LowBuyScreenerService`（定义在 `service.py`）通过多重 Mixin 继承组合了至少 8 个 Mixin 类：

```
LowBuyScreenerService(
    LowBuyScreeningMixin,       # screening.py
    LowBuyQuoteRefreshMixin,    # screening_quotes.py
    LowBuyPriorityBoardMixin,   # priority_board.py
    LowBuyCandidateMixin,       # candidate.py
    LowBuyResultStoreMixin,     # results.py
    LowBuyPerformanceMixin,     # performance.py
    LowBuyCloseReviewMixin,     # close_review.py
    LowBuyLifecycleMixin,       # lifecycle.py
    ...
)
```

每个 Mixin 都通过 `getattr(self, "_some_method", None)` 或直接调用 `self._method()` 来访问其他 Mixin 的方法。这会带来：
- 无法通过 IDE 跳转到定义
- 添加新 Mixin 时可能意外覆盖方法
- 测试时需要构造完整的 Mixin 组合，无法单独测试

**建议方案**：
1. 将 Mixin 之间的跨模块调用改为显式注入或策略模式
2. 例如：`LowBuyCandidateMixin` 不应该直接调用 `self._load_daily_history()`（该方法定义在其他 Mixin 中），而应该接收一个 `history_loader` 参数
3. 逐步拆分为独立的 Service 类，通过构造函数注入依赖

**涉及模块**：所有 `services/low_buy/*.py` Mixin 类

**预期收益**：可测试性提升、代码可追踪、降低新增策略时的出错概率。

### 3.3 性能与稳定性

#### [P-1] 行情刷新存在 24 只上限瓶颈

**问题**：`screening_quotes.py` 和 `priority_board.py` 中的 `max_symbols=24` 硬限制。当策略池有 480 只候选股时，只有 24 只能获得盘中实时分时数据更新。这导致：
- 25+ 只 `buy_now` 信号股中有 1+ 只被静默排除
- 优先级榜的实时性对超出 24 只的候选股不生效

**建议方案**：
1. 短期：将 `max_symbols` 提升到 60（多数数据源能支撑）
2. 中期：按优先级分段刷新（前 12 只 30s 刷新，13-36 只 60s 刷新，37-60 只 120s 刷新）
3. 长期：引入 WebSocket 推送替代轮询

**涉及模块**：`screening_quotes.py:267`、`priority_board.py:412`

---

#### [P-2] 数据库同步 Session 阻塞事件循环

**问题**：`database.py` 使用 SQLAlchemy 同步 Session，但 FastAPI 运行在异步模式。在高并发下，长时间数据库查询会阻塞整个事件循环。`watchlist_quotes` 端点（`watchlist.py:118`）在循环中为每只股票同步调用 `market_data.get_quote()`，50 只股票意味着 50 次串行 HTTP 请求 + 50 次数据库查询。

**建议方案**：
1. 短期：在 `watchlist_quotes` 中使用 `asyncio.to_thread()` 包装同步调用
2. 中期：将行情获取改为异步 HTTP 客户端（httpx.AsyncClient）+ `asyncio.gather`
3. 长期：迁移到 SQLAlchemy 2.0 async session（需要较大改动）

**涉及模块**：`database.py`、`watchlist.py`、`instruments.py`

---

#### [P-3] 启动时的全表扫描开销

**问题**：`schema_compat.py` 在每次启动时遍历所有表进行列检查和索引检查。`_add_nullable_column()` 对每个缺失列执行 `ALTER TABLE`。在有数百张表且含大表的情况下，启动时间可能达到 30-60 秒。

**建议方案**：
1. 引入 Alembic 迁移管理，替代代码中的自动 schema 修复
2. 将 schema_compat.py 改为仅在有 `--migrate` 启动参数时执行
3. 为索引创建添加 `IF NOT EXISTS`（MySQL 8.0+ / SQLite 3.25+ 支持）

**涉及模块**：`schema_compat.py`、`main.py`

---

#### [P-4] ECharts 在前端反复重算

**问题**：`MiniKline` 组件在每次 render 时重新计算所有的 MA 指标线并构造完整的 ECharts option 对象。`WorkspaceComponents.tsx` 中没有对 chart option 做 memoization。

**建议方案**：
1. 使用 `useMemo` 缓存 MA 计算和 chart option
2. ECharts 实例使用 `useRef` 保持，避免反复 init/dispose
3. 考虑使用 lightweight-charts 替代 ECharts（更轻量，专为金融图表设计）

**涉及模块**：`WorkspaceComponents.tsx`

## 四、中优先级优化

### 4.1 数据与回测

#### [D-1] 回测未区分样本内/样本外

**问题**：`execution_backtest.py` 的 `execution_backtest()` 方法使用最近的 `lookback_days`（默认 60 天）作为回测窗口。没有区分参数优化期和验证期。

**建议方案**：
1. 增加 `walk_forward` 参数，将回测期分割为训练窗口 + 验证窗口
2. 策略参数的优化必须在训练窗口内完成，验证窗口仅做评估
3. 在回测响应中明确标注"该结果基于样本内/样本外 XX 天数据"

**涉及模块**：`execution_backtest.py`、`performance.py`

---

#### [D-2] 模拟执行的止损退出价过于乐观

**问题**：`execution_simulation.py:109`：

```python
exit_price = min(row.open_price, stop_loss) if row.open_price < stop_loss else stop_loss
```

当开盘价低于止损价时，代码以 `stop_loss` 退出。但在真实市场中，如果开盘价已经在止损价下方，实际成交价是开盘价（或更低），而非止损价。这意味着回测的止损退出价系统性偏高，低估了真实亏损。

**建议方案**：开盘价 < 止损价时，以 `row.open_price` 退出（反映开盘跳空亏损的真实情况）。加滑点更佳。

**涉及模块**：`execution_simulation.py:109`

---

#### [D-3] 缺少流动性过滤

**问题**：回测和执行模拟中没有检查信号的日均成交额是否足以容纳假设的仓位。以 30% 仓位买 10 万元为例，需要个股日均成交额至少 5000 万才能保证不显著影响价格。

**建议方案**：
1. 在 `candidate_metrics.py` 的 prefilter 中增加 `min_daily_amount` 参数
2. 根据假设仓位动态调整：`min_amount >= position_value * 20`
3. 小盘股（日均成交 < 3000 万）标记为"流动性不足"，降低仓位上限

**涉及模块**：`candidate_metrics.py`、`candidate_rules.py`

#### [D-4] 策略验收指标标准化建议

当前回测输出已有 15+ 指标。建议增加以下核心指标体系：

| 指标 | 计算方式 | 阈值建议 |
|---|---|---|
| 净胜率 | (胜-负) / 总成交 × 100 | > 8% 合格，> 15% 优秀 |
| 平均净收益 | 含成本的每笔平均收益% | > 0.5% 合格 |
| 止损率 | 止损退出 / 总成交 × 100 | < 35% 合格 |
| 最大回撤（序列） | 连续亏损的最大累计亏损% | < 8% 合格 |
| 样本量 | 回测窗口内的成交笔数 | > 30 笔合格 |
| 月交易频率 | 月均信号数 | 5-20 笔合理 |
| 夏普近似值 | 日均收益 / 日收益标准差 × √250 | > 0.8 可用 |
| 市场环境覆盖 | 回测期包含几种 market_state | ≥ 3 种合格 |

在回测面板中展示这些指标，并对不合格指标标红。

**涉及模块**：`execution_backtest.py`、`performance.py`、`ResearchPage.tsx`

### 4.3 代码质量

**涉及模块**：`signals.py`、`candidate.py`、`candidate_rules.py`、`signal_resolution.py`、`execution_simulation.py`

## 五、长期演进建议

### 5.1 技术架构

| 方向 | 当前 | 目标 | 时间 |
|---|---|---|---|
| 数据库 | SQLAlchemy 同步 + SQLite | SQLAlchemy 2.0 async + PostgreSQL 16（支持 JSONB、窗口函数、并行查询） | 3-6 月 |
| 任务队列 | threading.Timer daemon | Celery + Redis / ARQ，支持重试、监控、定时 | 2-4 月 |
| 缓存 | 内存 dict + deepcopy | Redis 集中缓存（跨 worker 共享、自动过期、pub/sub 失效） | 2-3 月 |
| 行情接入 | 串行 HTTP 调用 | WebSocket 长连接 + 本地行情网关（如 xtquant） | 3-6 月 |
| 前端架构 | 单体组件 | 每页独立数据流 + React Query（SWR）缓存 + 代码分割 | 2-4 月 |
| 测试 | 无自动化测试 | 核心策略回测回归测试 + API 集成测试 + 前端组件测试 | 持续 |
| CI/CD | 无 | GitHub Actions: lint → test → build → deploy | 1-2 月 |

### 5.2 策略演进

1. **日内 T+0 信号**：当前做 T 引擎（quant_engine）和低吸引擎（low_buy）是两套相对独立的体系。长期应融合为统一的"日内+隔夜"混合策略框架，根据个股波动率和持仓成本自动推荐做 T 还是隔夜低吸。
2. **自适应参数**：策略中的止损 multiplier（当前固定 0.988）、逆回购比率阈值（当前固定 0.26/0.35）应该基于近期市场波动率（ATR percentile）动态调整。
3. **多因子归因**：在回测归因中增加 Fama-French 风格的多因子分析（市场 beta、市值因子、动量因子、波动率因子），分离 alpha 和 beta 收益。

### 5.3 生产部署

1. **容器化**：编写 Dockerfile + docker-compose.yml（当前只有 `.env.docker.example` 但没有 compose 文件）
2. **可观测性**：集成 OpenTelemetry（FastAPI instrumentation）+ Prometheus metrics + Grafana dashboard
3. **告警规则**：后台任务失败率 > 5%、API 响应 P95 > 3s、数据库连接池耗尽、行情源超时 > 30s
4. **灾备**：数据库每日自动备份，回测结果导出到云存储，配置文件版本化管理

### 5.4 Agent 安全

1. **权限分层**：定义 `read_only`（可查询行情/信号）、`suggest`（可生成交易建议）、`execute`（可下单）三级 agent 权限
2. **二次确认机制**：任何 execute 级别的操作必须经过用户 App 端确认（推送通知 + 手动确认）
3. **操作审计**：所有 agent 操作记录到不可篡改的审计日志（append-only 表或外部审计服务）
4. **资金隔离**：Agent 可管理的最大资金量设置硬限制（如单笔不超过总资金的 5%，单日不超过 20%）
