## 一、裁定总纲

经过两轮交叉审查（Claude 初次复核 → Codex 复审 → 最终裁定），确认 TQuant 低吸策略系统存在 6 个可明确的代码级问题。所有问题已在本次整改中一次性修复，不设过渡方案。

本裁定区分了三类发现：

- **A 类：确认的代码缺陷** → 已修复，见第二章
- **B 类：确认的配置/数据问题** → 已修复，见第三章
- **C 类：误报（由数据库旧快照导致的虚假信号）** → 不予修改，见第四章

## 二、A 类：确认的代码缺陷（共 5 项，已全部修复）

### A1. SQLite 后台扫描仅覆盖 1 个策略

**文件**: `backend/app/main.py`
**原代码**（行 56-59）:
```python
def _background_low_buy_strategies() -> list[str]:
    if settings.database_url.startswith("sqlite"):
        return [DEFAULT_PRODUCTION_LOW_BUY_STRATEGY]  # 仅 first_board
    return list(PLAYBOOKS.keys())
```

**问题**: SQLite 环境后台仅扫描 `first_board`，导致 3 个 AUXILIARY 策略完全无结果（late_session_strong_support、core_midcap_vwap_ma5_retrace、sector_mainline_first_divergence_low_buy），3 个 RESEARCH 策略无自动更新。

**裁决**: 将 SQLite 扫描范围扩展至所有 PRODUCTION 策略（CORE + AUXILIARY，共 5 个）。SQLite 单写者模式下串行执行不产生写冲突，5 个策略的扫描量完全在承受范围内。完整 12 策略扫描留待 PostgreSQL 生产环境。

**修复后代码**:
```python
def _background_low_buy_strategies() -> list[str]:
    if settings.database_url.startswith("sqlite"):
        return list(PRODUCTION_PRIORITY_STRATEGIES)
    return list(PLAYBOOKS.keys())
```

### A2. classic_retrace 的 retracement_days_max 配置错误

**文件**: `backend/app/services/low_buy/pool.py`
**原代码**（`_STRATEGY_RETRACEMENT_DAYS_MAX` dict）: classic_retrace 未显式列出，由 fallback `max(retracement_buckets)` 和 `_strategy_retracement_days_max()` 的默认值 7 兜底。但 `_STRATEGY_BOARD_WINDOW_DAYS[classic_retrace] = 13` 使得 `_build_retracement_buckets` 使用 `max_days=7`（fallback），而在 board_window 为 13 时，回踩桶实际可能包含 1-13 天的股票。

**问题**: 策略文档描述"回调 2-4 天最优"，但扫描池实际可纳入回踩长达 13 天的股票。

**裁决**: 显式设定 `"classic_retrace": 7`，与 first_board 保持一致。同时 candidate_rules 中的 prefilter 已将 `retracement_days` 约束为 1-6（见 A3）。

**修复后代码**:
```python
_STRATEGY_RETRACEMENT_DAYS_MAX = {
    "classic_retrace": 7,
    ...
}
```

### A3. classic_retrace 缺少专用 prefilter

**文件**: `backend/app/services/low_buy/candidate_rules.py`
**原代码**（行 163-176 区域的 fallback）: `passes_strategy_prefilter` 中 `classic_retrace` 未定义专用分支，落入返回 `None` 的 fallback，意味着不施加任何策略特定筛选（仅靠 common_prefilter 的宽松条件）。

**问题**: 策略要求"十日内有涨停启动，缩量回踩均线，首板低点未破"，但 fallback 不检查 `board_low_held`、`board_open_held` 等关键条件。

**裁决**: 实现专用 prefilter，与 first_board 共享回踩结构逻辑但保持独立的宽松度和均线位置要求。关键差异：volume_burst_ratio 门槛从 1.25（first_board）降至 1.05（classic_retrace 更包容），distribution_risk_score 从 5.8 放宽至 6.0，不使用 false_breakout 排除。

**修复后代码**（`candidate_rules.py` 行 170-181）:
```python
if strategy == "classic_retrace":
    return (
        item.board_count <= 2
        and 1 <= metrics.retracement_days <= 6
        and metrics.board_low_held
        and metrics.volume_burst_ratio >= 1.05
        and metrics.support_distance_pct <= 3.0
        and metrics.latest_close >= metrics.ma10 * 0.98
        and metrics.distribution_risk_score < 6.0
        and not metrics.false_breakout_flag
        and (metrics.shrink_basic_ok or metrics.momentum_exhaustion or metrics.post_volume_ratio <= 1.22)
    )
```

### A4. ma_support 的 board_count 上限偏宽

**文件**: `backend/app/services/low_buy/candidate_rules.py`
**原代码**: `item.board_count <= 3`

**问题**: 允许 2-3 连板股票进入均线支撑策略。这些高连板标的回撤后往往不再是健康的均线支撑标的，而是高位博反弹的投机品。策略定位"基本面趋势良好，均线多头排列"与此矛盾。

**裁决**: 收窄为 `board_count <= 2`。2 连板的标的有可能仍处于健康的均线趋势中（如放量涨停后次日缩量分歧再封板），3 连板则大概率已进入纯情绪驱动阶段。

**修复后代码**: `item.board_count <= 2`

### A5. volume_shrink 缺少显式 board_count 限制

**文件**: `backend/app/services/low_buy/candidate_rules.py`
**原代码**: strategy prefilter 无 `board_count` 检查，仅通过 common_prefilter 的 `board_count <= 4` 间接约束。

**问题**: volume_shrink 策略描述"启动日量能明显放大，缩量回踩"，对应的是首板/二板启动场景。4 连板的量能结构完全不同（多日分歧后的缩量可能只是暂时休整而非健康回调）。

**裁决**: 在 strategy prefilter 的第一行增加 `item.board_count <= 2`，明确策略意图。

**修复后代码**（`candidate_rules.py` 行 123-124）:
```python
if strategy == "volume_shrink":
    return (
        item.board_count <= 2
        ...
    )
```

## 三、B 类：确认的配置/系统问题（共 2 项，已全部修复）

### B1. SQLite 环境下 performance 计算被禁用

**文件**: `backend/app/main.py`
**原代码**: `_refresh_materialized_low_buy_snapshots` 调用处 `compute_performance=not settings.database_url.startswith("sqlite")`，导致 SQLite 下不计算 performance 快照。

**裁决**: 改为 `compute_performance=True`。此前的顾虑（SQLite 下数据不足导致 performance 全零）已由 `pool.py` 的 Stage 6 数据完整性检查解决——当日线数据不足时，系统会自动回退到有完整数据的最近交易日，不再产生误导性的全零 performance。

### B2. 启动快照堆积旧版本数据

**文件**: `backend/app/main.py`（新增函数）

**问题**: 当 `LOW_BUY_RESULT_VERSION`（当前为 8）因代码升级而递增时，旧版本的 result snapshots 和 scan snapshots 仍残留在数据库中。这些旧快照虽已被 API 层 `_response_payload_is_current()` 拒绝，但会污染直接 SQL 查询结果（如复核报告所使用的数据库查询）。

**裁决**: 新增 `_cleanup_stale_low_buy_snapshots()`，在 `init_db()` 之后（确保表已存在）和 `_warm_runtime_caches` 之前（确保清理后新扫描写入的是当前版本数据）执行。清理逻辑：遍历 `low_buy_result_snapshots.payload_json` 检查 `payload_version`，遍历 `low_buy_scan_snapshots.filters_json` 检查 `_result_version`，删除不匹配的记录。

**附加说明**: `low_buy_strategy_pool_snapshots` 表的 ORM 实体已在 `entities.py` 中定义，但数据库中尚不存在该表。这不是本次修复的重点——`init_db()` → `Base.metadata.create_all()` 会在下次应用启动时自动创建该表。创建后，`StrategyPoolBuilder.persist()` 将正常工作，每个策略将拥有独立的预制池。

## 四、C 类：误报（不予修改）

以下问题在初次复核中被标记为严重，但经 Codex 复审指正和代码追踪确认，属于数据库旧快照导致的虚假信号，代码逻辑本身正确。

### C1. RESEARCH 策略在数据库中显示 buy_now 信号

**现象**: `low_buy_result_snapshots` 中 ma_support 有 68 条 buy_now、classic_retrace 有 20 条 buy_now。这些快照的 `payload_version` 不匹配当前 `LOW_BUY_RESULT_VERSION`。

**现有防御**: 代码中已存在两层防御：

**第一层（信号管线）**: `signals.py` 的 `_can_hard_buy_now()` 和 `_can_soft_buy_now()` 第一行即检查 `strong_buy_paused()`，对 RESEARCH 层策略返回 False。按当前代码逻辑，RESEARCH 策略不可能产生新的 buy_now/soft_buy_now 信号。

**第二层（API 响应）**: `results.py` 的 `_normalize_candidate_policy_state()`（行 367-378）对从缓存/DB 读取的候选进行二次检查，将 RESEARCH 策略的 buy_now/soft_buy_now 强制降级为 near_entry。这意味着即使旧快照中存在违规信号，API 返回给前端时也会被修正。

**第三层（快照有效性）**: `_response_payload_is_current()`（行 449-459）检查 `_result_version`，不匹配当前版本的快照整体拒绝。

**裁决**: 不予额外修改。现有三层防御充分。B2 修复的启动清理会在下次启动时自动删除这些旧快照。

### C2. volume_shrink score=79.0 的 buy_now 候选

**现象**: 数据库中存在 score=79.0 的 volume_shrink buy_now 记录。

**分析**: `_can_hard_buy_now` 中硬买最低分阈值对 volume_shrink 为 80.0（`_hard_buy_min_score` 默认值）。当前代码逻辑下，score=79.0 的候选不可能通过硬买检查。该记录必然是 old-version 快照中的残留数据。

**裁决**: 不予修改。B1+B2 修复后，重新扫描将自动消除此类记录。

### C3. 评分分布过于集中

**现象**: buy_now 候选的分数集中在 89-99 区间，区分度低。

**分析**: 这是评分公式设计意图的体现——硬买候选本就应该在 85+ 的区间。数据库中的异常低分（如 79.0）属于旧快照残留。near_entry/watch/avoid 各层应有更宽的分值分布。评分公式的校准属于持续优化范畴，非缺陷。

**裁决**: 不予本次修改。建议在后续迭代中单独评估评分校准，当前评分公式能正确区分信号层级即可。

## 五、各策略信号状态 — 当前代码行为预期

以下为本次修复后，按当前代码逻辑分析的各策略信号状态预期：

| 策略 | 层级 | strong_buy_paused | pool 源 | 最大 buy 状态 |
|------|------|-------------------|---------|-------------|
| first_board | CORE | 否 | limit_up_pool | buy_now |
| volume_shrink | CORE | 否 | limit_up_pool | buy_now |
| late_session_strong_support | AUXILIARY | 否 | daily_history | **near_entry** (AUX 层 `_can_show_auxiliary_near_entry` 控制) |
| core_midcap_vwap_ma5_retrace | AUXILIARY | 否 | daily_history | **near_entry** |
| sector_mainline_first_divergence_low_buy | AUXILIARY | 否 | daily_history | **near_entry** |
| classic_retrace | RESEARCH | 是 | limit_up_pool | **near_entry** |
| ma_support | RESEARCH | 是 | limit_up_pool | **near_entry** |
| breakout_support | RESEARCH | 是 | limit_up_pool | **near_entry** |
| limit_up_breakout_retrace | RESEARCH | 是 | limit_up_pool | **near_entry** |
| divergence_consensus | RESEARCH | 是 | limit_up_pool | **near_entry** |
| deep_pullback | FACTOR | 是 | limit_up_pool | **near_entry** |
| trend_rebound | FACTOR | 是 | limit_up_pool | **near_entry** |

注：AUXILIARY 层的 buy_now/soft_buy_now 由 `_can_show_auxiliary_near_entry` 逻辑控制——该策略 `_is_auto_trade_strategy` 返回 False（不在 `AUTO_TRADE_STRATEGIES` 中），因此即使通过 hard/soft buy 检查，API 层也会将其限制为 near_entry。此逻辑不受本次修改影响。

## 七、下一步操作

1. **重启应用**：重启后 `init_db()` → `_cleanup_stale_low_buy_snapshots()` → `_warm_runtime_caches()` 依次执行。清理函数会自动删除所有 version 不匹配的旧快照；预热函数会立即对 5 个 PRODUCTION 策略执行一次全量扫描。

2. **验证扫描结果**：等待启动扫描完成后（SQLite 下约需 2-5 分钟），检查以下指标：
   - `low_buy_result_snapshots` 中是否出现新的、`payload_version` 匹配当前版本的记录
   - 5 个策略是否均有最新交易日的扫描结果
   - RESEARCH 策略的新记录中 `buy_signal_state` 是否仅为 near_entry/watch/avoid
   - 3 个 AUXILIARY daily_history 策略是否首次产生结果（依赖日线数据完整性）

3. **验证策略池持久化**：确认 `low_buy_strategy_pool_snapshots` 表是否已创建（`init_db()` 自动创建），并检查 `StrategyPoolBuilder.persist()` 的写入效果。

4. **生产环境（PostgreSQL）全量验证**：生产环境中 `_background_low_buy_strategies()` 返回全部 12 个策略，启动预热和后台定时扫描会覆盖所有策略。重点验证 3 个 daily_history 策略的数据完整性和 performance 快照的正确性。

## 八、裁定结语

本次复审最终裁定：TQuant 低吸策略系统的核心信号管线（`signals.py` 的 `_can_hard_buy_now` / `_can_soft_buy_now` + `results.py` 的 `_normalize_candidate_policy_state` / `_response_payload_is_current`）逻辑正确，RESEARCH 策略的 buy_now 阻断机制完备。所有 A 类和 B 类问题均为外围配置/数据层面的缺陷，已一次性修复。剩余 5 个 RESEARCH 策略和 3 个 AUXILIARY/day 策略的扫描结果应在重启后自动生成，此后可进行第二轮策略有效性验证。
