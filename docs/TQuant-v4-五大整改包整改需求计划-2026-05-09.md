# TQuant v4 五大整改包整改需求计划

生成日期：2026-05-09  
来源报告：`/Users/j/Downloads/TQuant_v4_五大整改包深度报告.html`  
适用项目：TQuant 维斯量化平台  
文档目标：将 Claude v4 审查报告中提到的问题、优化建议和后续演进方向整理为可执行、可验收、可排期的需求文档。

> 说明：本文档是基于审查报告提取和工程化整理形成的整改需求计划。正式开发前仍需逐项做代码核验，避免报告与当前代码状态存在偏差。

---

## 1. 总体结论

Claude v4 报告认为当前项目在金融交易能力、ETF T+0、ML 序列特征、容量分析、runtime 解耦和服务拆分方面有明显进展，但安全认证、前端隐私、Provider 熔断、回测并发控制、缓存性能和若干金融指标口径仍存在生产级风险。

本轮整改目标不是继续堆功能，而是优先补齐生产闭环的短板：

1. 安全认证必须先修，避免 refresh token、XSS、暴力破解、全局限速失效等基础风险。
2. 金融指标必须口径可信，避免 Kyle Lambda 容量分析、ML 空特征、陈旧行情止损等误导用户。
3. Provider 必须具备超时、熔断、降级和健康监控，避免外部源拖垮 API。
4. 回测和 ML 必须具备并发保护、取消响应、市场状态感知和可复现实验能力。
5. 前端必须补齐 CSP、异常兜底、GZip、隐私缓存策略和 AI 批量限速。

## 2. 优先级定义

| 优先级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 生产安全、资金风控、核心 API 可用性、可能造成误导交易的问题 | 当前版本必须修复，修复后才能继续部署 |
| P1 | 高风险稳定性、性能、权限、数据准确性问题 | 本轮必须修复，允许按模块分批上线 |
| P2 | 重要体验、可维护性、长期扩展能力问题 | 纳入短期迭代，不能长期挂起 |
| P3 | 中长期能力增强、研究功能、架构演进 | 制定方案和验收口径，按阶段实施 |

## 3. 整改包 PKG-01：安全认证整改包

### 3.1 背景

报告指出安全类问题已连续多轮未完全修复，尤其是 refresh token 明文传输、缺少安全响应头、登录限速过宽、全局限速多 worker 失效等问题。TQuant 涉及用户持仓、模拟委托、策略信号和 Agent API，安全等级应高于普通信息展示系统。

### 3.2 P0 需求

#### SEC-01：Refresh Token Cookie 生产默认必须安全

问题：

- `auth_cookie_secure=False` 默认值不适合生产。
- `SameSite=Lax` 对金融平台偏宽。
- HTTPS 环境下若仍允许不安全 cookie，会暴露 refresh token。

实现要求：

1. 配置层默认值调整：
   - `AUTH_COOKIE_SECURE=true`
   - refresh cookie 的 `samesite` 改为 `strict`
2. 启动时校验：
   - 如果 `cors_origins` 或部署域名包含 HTTPS，而 `auth_cookie_secure=false`，启动应拒绝或至少进入 degraded 并输出明确错误。
3. 开发环境兼容：
   - 本地 HTTP 开发允许通过 `.env` 显式设置 `AUTH_COOKIE_SECURE=false`。
   - 生产 compose/runtime 配置必须显式为 true。

验收标准：

- HTTPS 下 Set-Cookie 包含 `HttpOnly; Secure; SameSite=Strict`。
- 本地开发不被误阻断。
- 单元测试覆盖生产配置校验。

#### SEC-02 / FE-01：补齐安全响应头和 CSP

问题：

- 后端无 CSP、X-Frame-Options、X-Content-Type-Options 等响应头。
- 前端 `index.html` 无 CSP meta，XSS 防护弱。

实现要求：

1. 在 FastAPI 中间件层统一设置：
   - `Content-Security-Policy`
   - `X-Frame-Options: DENY`
   - `X-Content-Type-Options: nosniff`
   - `Referrer-Policy: strict-origin-when-cross-origin`
   - `Permissions-Policy`
2. CSP 初始建议：
   - `default-src 'self'`
   - `script-src 'self'`
   - `style-src 'self' 'unsafe-inline'`，后续逐步去除 inline style
   - `img-src 'self' data: https:`
   - `connect-src 'self' https://weisilianghua.cloud http://43.143.243.97:18090`
   - `frame-ancestors 'none'`
3. 前端 `index.html` 增加 CSP meta 或构建时注入。
4. 对现有图表、字体、API 调用做兼容验证，避免 CSP 误杀。

验收标准：

- 所有主页面响应头包含安全头。
- 浏览器控制台无 CSP 误报阻断核心功能。
- 不允许页面被 iframe 嵌套。

#### SEC-04：登录限速与账号锁定

问题：

- 当前登录限速过宽，不适合金融账号。
- 缺少连续失败锁定机制。

实现要求：

1. 登录限速：
   - 同账号：5 次 / 300 秒。
   - 同 IP：可配置，建议 20 次 / 300 秒。
2. 用户表增加字段：
   - `failed_login_count`
   - `locked_until`
   - `last_failed_login_at`
3. 登录逻辑：
   - 连续失败达到 10 次锁定 15 分钟。
   - 成功登录后清空失败计数。
   - 锁定状态返回明确错误，不暴露是否账号存在。
4. 告警：
   - 连续失败或锁定触发通知事件，可接飞书。

验收标准：

- 连续错误密码后账号被锁。
- 锁定期间正确密码也不能登录。
- 到期后可正常登录。
- 错误响应不泄露账号枚举信息。

### 3.3 P1 需求

#### SEC-05 / SEC-06：CORS 收敛与 Redis 限速

问题：

- `allow_headers=["*"]`、`allow_methods=["*"]` 过宽。
- memory 限速在多 worker 下不准确。

实现要求：

1. CORS 配置改为枚举：
   - methods：`GET, POST, PUT, PATCH, DELETE, OPTIONS`
   - headers：`Authorization, Content-Type, X-Request-ID, X-Admin-Token`
2. 新增 RedisRateLimiter：
   - 使用 Redis Lua 或原子操作实现滑动窗口。
   - `REDIS_URL` 存在时默认启用。
   - Redis 不可用时敏感接口 fail-closed，全局普通接口可降级但必须打日志。
3. 登录、AI、Agent invoke、settings 修改使用独立限速策略。

验收标准：

- 多 worker 下限速一致。
- Redis 不可用时登录接口不放开暴力破解。
- CORS 预检正常。

#### SEC-NEW-01：UserSession 索引

问题：

- refresh token hash 查询缺少唯一索引。
- 有效 session 查询缺少复合索引。

实现要求：

1. Alembic 迁移：
   - `refresh_token_hash` 唯一索引。
   - `(user_id, revoked_at, expires_at)` 复合索引。
2. schema compatibility 保持一致。
3. 迁移前检查重复 token hash，存在重复时输出修复脚本或迁移阻断。

验收标准：

- MySQL Alembic upgrade 成功。
- refresh 查询走索引。
- 回滚脚本可用。

#### SEC-NEW-02：PairedHedge 研究接口认证核验

问题：

- 新增配对对冲研究可能暴露优先榜信号和策略数据。

实现要求：

1. 确认所有 paired hedge 路由都在认证路由组。
2. 普通用户只读。
3. 若涉及策略研究参数，至少要求 research 权限。
4. 返回文案必须声明“研究用途，不构成交易建议”。

验收标准：

- 未登录访问返回 401。
- 无权限访问返回 403。
- 不泄露完整策略内部 payload。

### 3.4 P2/P3 演进需求

| 方向 | 目标 | 初步实现 |
|---|---|---|
| TOTP 二次验证 | 下单权限用户强制 MFA | User 增加 TOTP secret，登录二阶段校验 |
| 操作审计全链路 | 登录、委托、参数、通知全记录 | 新增 operation_audit_log，只追加不可删除 |
| 细粒度 RBAC | read_only / paper_trade / strategy_config / admin | 路由级权限装饰器 + 前端菜单过滤 |

## 4. 整改包 PKG-02：金融指标与交易规则整改包

### 4.1 P0 需求

#### FIN-NEW-01：Kyle Lambda 容量分析量纲修正

问题：

- 当前容量分析中 Kyle Lambda 计算可能量纲不一致，导致冲击成本严重偏低。
- 策略容量上限可能被高估，误导资金配置。

实现要求：

1. 明确容量模型：
   - 短期先使用 Square-Root Market Impact：
     `impact_pct = eta * volatility_pct * sqrt(order_amount / average_daily_amount)`
   - 保留 Kyle Lambda 作为研究指标，不作为默认生产容量结论。
2. StrategyCapacityPoint 增加字段：
   - `impact_model`
   - `impact_assumption`
   - `average_daily_amount`
   - `volatility_pct`
   - `order_amount`
   - `impact_pct`
3. 参数化：
   - `capacity.impact_eta`
   - `capacity.min_avg_amount`
   - `capacity.max_impact_pct`
4. 单元测试：
   - 日均成交 2 亿、资金 100 万时，冲击成本应在合理区间，如 0.05%-0.5%。
   - 小成交额股票冲击成本应显著更高。

验收标准：

- 容量报告不再给出明显不合理的低冲击成本。
- 报告明确模型假设和适用边界。

### 4.2 P1 需求

#### FIN-NEW-02：ML 超参数纳入参数系统

问题：

- XGBoost / LightGBM 超参数硬编码。
- 研究人员无法做参数版本管理和敏感性分析。

实现要求：

1. 新增参数命名空间 `ml.training`：
   - `xgb_n_estimators`
   - `xgb_max_depth`
   - `xgb_learning_rate`
   - `lgb_n_estimators`
   - `lgb_max_depth`
   - `lgb_learning_rate`
   - `cv_folds`
   - `min_train_samples`
2. ML 训练代码统一读取参数版本系统。
3. UI 系统配置增加 ML 参数展示和编辑入口。
4. 回测/训练报告记录参数版本号。

验收标准：

- 修改参数无需改代码。
- 训练 artifact 中记录参数快照。
- 参数越界被校验拒绝。

#### FIN-NEW-03：ML 空特征处理

问题：

- `sector_relative_strength_5d/10d` 当前可能长期为 0，误导模型。

实现要求：

方案 A，短期：

- 若板块相对强弱无法计算，从 `FEATURE_NAMES` 中移除。
- 历史 artifact 标记为旧特征版本。

方案 B，中期：

- 通过行业 ETF 代理或板块指数计算真实板块相对强弱。
- 不可用时使用 `NaN`，模型训练显式处理缺失。

验收标准：

- 不存在“所有样本该特征恒为 0”的情况。
- 特征报告能显示缺失率。

#### FIN-NEW-04：自动退出行情失败时不使用陈旧价

问题：

- 批量行情失败时回退持仓表 `latest_price`，可能用昨日价执行止损/止盈。

实现要求：

1. `latest_prices()` 失败时返回数据质量状态。
2. 自动退出计划：
   - 无实时/当日有效价时跳过本轮执行。
   - 记录跳过原因：行情不可用，自动退出暂停本轮。
3. 前端模拟盘显示：
   - “自动退出暂停：行情数据不可用，等待下轮刷新。”

验收标准：

- 外部行情失败不会用陈旧价下单。
- PaperAgentRun 有清晰 skipped reason。

### 4.3 P2 需求

#### FIN-NEW-05：ATR 口径统一文档化

问题：

- 波动率仓位上限的 ATR 来源和回测 ATR 口径可能不一致。

实现要求：

1. 统一 ATR 默认口径：
   - 日线 14 日 ATR。
   - 计算公式写入文档和代码注释。
2. 回测、优先榜、模拟盘使用同一 ATR 计算函数。
3. 响应字段增加：
   - `atr_window`
   - `atr_source`
   - `atr_pct`

验收标准：

- 同一标的同一日期，回测与实时口径一致。

### 4.4 可扩展金融功能

| 方向 | 目标 | 实现计划 |
|---|---|---|
| 板块相对强弱特征 | 完成序列特征全链路 | 通过行业 ETF 代理计算板块 5/10 日收益，与个股收益比较 |
| 在线增量训练 | 信号结果实时反哺 | 平仓后写 ML 样本，每周增量训练 |

## 5. 整改包 PKG-03：Provider 服务层与缓存并发整改包

### 5.1 P0 需求

#### PROV-01：Provider Router 增加超时、熔断和降级

问题：

- Provider 串行调用缺少单次超时。
- 外部源挂起会阻塞请求线程。
- 连续失败没有熔断，容易拖垮全站。

实现要求：

1. Provider 调用统一包装：
   - 单次调用超时。
   - 捕获异常并结构化返回。
   - 记录 provider、耗时、错误码。
2. 熔断器：
   - 连续失败/超时 3 次后 open 5 分钟。
   - half-open 只允许 1 个探测请求。
   - 成功后关闭熔断。
3. 降级链路：
   - 当前 provider 熔断后尝试下一个 provider。
   - 全部失败时返回 `UNAVAILABLE`，不能抛未处理异常。
4. 指标：
   - `provider_calls_total`
   - `provider_failures_total`
   - `provider_latency_ms`
   - `provider_circuit_state`

验收标准：

- 模拟 provider 超时不会阻塞超过配置秒数。
- 熔断期间不再调用失败 provider。
- API 返回 stale/degraded/unavailable 标记。

### 5.2 P1 需求

#### PROV-03：factor_external 双重检查锁定

问题：

- 缓存读写存在 TOCTOU，并发时会重复请求外部源。

实现要求：

1. 所有 `resolve_xxx` 外部因子函数改为：
   - 锁外快速读。
   - 未命中后进锁。
   - 锁内二次检查。
   - 仍未命中才请求外部源并写缓存。
2. 请求失败写入短 TTL 的失败缓存，避免瞬时风暴。

验收标准：

- 并发 10 个请求同一因子，只触发一次外部调用。

#### PROV-N1：cache_helpers 使用 JSON 序列化缓存

问题：

- `model_copy(deep=True)` 对大 Pydantic 响应较慢。

实现要求：

1. 缓存值由模型对象改为 JSON 字符串。
2. 写入：`model_dump_json()`。
3. 读取：`model_validate_json()`。
4. 保留非 Pydantic 对象兼容分支。

验收标准：

- 优先榜缓存读写性能不低于现有方案。
- 深拷贝语义不丢失，调用方修改返回对象不会污染缓存。

#### PROV-02：外部因子多 Provider 补齐

问题：

- 外部因子主要依赖 AkShare，EastMoney/Tencent fallback 不完整。

实现要求：

1. 梳理外部因子接口：
   - sector fund flow
   - northbound flow
   - LHB statistic
   - sector heatmap
2. 对无法通过 EastMoney/Tencent 获取的数据，明确返回 `UNAVAILABLE` 和原因。
3. 不允许静默归零。

验收标准：

- Provider 失败时因子有明确质量标记。
- 策略评分不会把不可用因子当作 0 分正常值。

### 5.3 演进需求

| 方向 | 目标 | 实现计划 |
|---|---|---|
| Redis 分布式缓存 | 多 worker 共享优先榜、市场状态、行业热点 | Redis 可用时写 Redis，不可用降级进程缓存 |
| Provider 健康监控 | 自适应 provider 优先级 | 滑动窗口统计成功率和延迟 |
| 行情数据本地化 | 降低 AkShare 依赖 | 定时同步日线、交易日历、涨跌停池 |

## 6. 整改包 PKG-04：策略参数、ML、回测治理整改包

### 6.1 P0 需求

#### STR-02：回测任务并发限制

问题：

- 回测任务并发无上限，可能耗尽 CPU 和数据库连接。

实现要求：

1. BacktestJobService 增加并发控制：
   - 默认最多 2 个 running backtest。
   - 其余进入 queued 状态。
2. API 响应包含：
   - queue_position
   - running_count
   - estimated_wait_seconds
3. 取消任务后释放槽位。
4. 多 worker 环境下需要 DB 原子 claim 或 Redis lock，不能只用进程内 semaphore。

验收标准：

- 同时提交 5 个大回测，最多 2 个 running。
- queued 任务可继续执行。
- 取消 running 任务后下一任务接续。

### 6.2 P1 需求

#### STR-N1：取消令牌响应速度优化

问题：

- DB 轮询取消有延迟。

实现要求：

1. `DatabaseStatusCancelToken` 增加 `poll_interval=0.5s`。
2. 同进程内增加 `EventCancelToken`。
3. 取消接口：
   - 设置 DB 状态。
   - 若 job 在当前进程，同时触发内存 Event。

验收标准：

- 用户点击取消后 1 秒内任务进入 cancelling/cancelled。

#### STR-07：测试缓存隔离

问题：

- LowBuy runtime 类级缓存可能跨测试污染。

实现要求：

1. 增加统一 `clear_all_runtime_caches()`。
2. `conftest.py` 增加 autouse fixture。
3. 覆盖低吸、优先榜、quote refresh、history 缓存。

验收标准：

- 测试顺序随机化仍通过。

#### STR-N2：Paired Hedge 合规免责声明

问题：

- 研究接口可能被误认为可执行对冲交易。

实现要求：

1. API 顶层增加 `disclaimer` 必填字段。
2. 前端红色 Banner 展示。
3. 文案：
   - “纯研究功能，不代表可执行交易方案。”
   - “A 股 ETF 做空受融券资格、保证金和交易规则限制。”

验收标准：

- API 缺 disclaimer 测试失败。
- 前端页面固定展示。

### 6.3 P2 需求

#### STR-03：市场状态感知 Walk-forward

目标：

- 当前训练窗口按日历划分，不能适配不同市场状态。

实现要求：

1. 增加 `regime_aware_walk_forward()`。
2. 按市场状态分桶：
   - broad_rally
   - repair
   - low_volume_wait
   - fast_rotation
   - weight_support
   - high_flyer_retreat
   - risk_release
3. 输出每个状态下的最佳参数、样本数、OOS 表现。
4. 参数版本系统支持 state-specific 参数。

验收标准：

- 报告中可看到不同市场状态的 IS/OOS 指标。

### 6.4 演进需求

| 方向 | 目标 | 实现计划 |
|---|---|---|
| 策略组合 Sharpe 优化 | 不再只按分数排序 | 引入策略相关性矩阵、HRP、Mean-Variance |
| 强化学习仓位分配 | 动态策略组合权重 | 离线训练 PPO/SAC，仅研究，不进入自动交易 |
| 状态专属参数版本 | 不同市场状态加载不同参数 | 参数版本增加 market_state_scope |

## 7. 整改包 PKG-05：前端隐私与架构整改包

### 7.1 P0 需求

#### FE-03：全局异常处理

问题：

- 500 错误可能返回内部路径或堆栈。

实现要求：

1. FastAPI 注册全局异常处理器。
2. 响应结构：
   ```json
   {
     "detail": "服务内部错误，请稍后重试",
     "request_id": "req_xxx"
   }
   ```
3. 日志记录完整异常，但响应不返回堆栈。

验收标准：

- 人为抛异常时，响应不包含本地路径、SQL、密钥。

#### FE-04：GZip 压缩

问题：

- 大型 JSON 响应移动端传输慢。

实现要求：

1. FastAPI 增加 `GZipMiddleware(minimum_size=1000)`。
2. 确认静态资源、API JSON 均可压缩。

验收标准：

- 请求带 `Accept-Encoding: gzip` 时响应包含 `content-encoding: gzip`。

#### FE-02：离线缓存 TTL 缩短与退出清理

问题：

- localStorage 明文存低吸候选和日报摘要，TTL 过长。

实现要求：

1. Offline cache TTL 从 6 小时缩短至 30 分钟。
2. logout、token 失效、切换账号时调用 `clearOfflineCache()`。
3. 不缓存敏感字段：
   - token
   - API key
   - admin token
   - database url
4. 长期方案预留 SubtleCrypto AES-GCM 加密。

验收标准：

- 退出登录后 localStorage 中无低吸候选缓存。
- 30 分钟后自动失效。

### 7.2 P1 需求

#### FE-01：CSP 双层防护

见 SEC-02。

#### FE-05：analyzeBatch 独立限速与数组上限

问题：

- 批量 AI 分析可能消耗模型额度。

实现要求：

1. `POST /analyze/batch` 增加专用限速。
2. 请求数组长度最大 10。
3. 每个 symbol 做格式校验。
4. 权限不足或模型未配置返回明确错误。

验收标准：

- 超过 10 个请求返回 422。
- 高频请求触发 429。

### 7.3 P2 需求

#### FE-NEW-01：ETF 自动下单参数化

问题：

- ETF 自动下单现金比例默认值硬编码。

实现要求：

1. 参数命名空间加入：
   - `sector_etf_t0.paper_auto_cash_pct`
   - `sector_etf_t0.paper_auto_max_orders`
   - `sector_etf_t0.paper_auto_enabled`
2. 调度读取参数版本系统。
3. 系统配置页面展示。

验收标准：

- 改参数后无需改代码即可影响下一轮自动交易。

### 7.4 演进需求

| 方向 | 目标 | 实现计划 |
|---|---|---|
| Web / Native API Client 解耦 | 消除运行时分支 | `IApiClient` + web/native 注入 |
| Service Worker 安全缓存 | 替代 localStorage 离线缓存 | Cache Storage + 版本化清理 |
| 个性化 SSE 推送 | 只推用户关注标的 | symbol 订阅、last-event-id、断线恢复 |

## 10. 风险与回滚方案

| 风险 | 影响 | 回滚方案 |
|---|---|---|
| CSP 过严导致前端资源加载失败 | 页面白屏或图表失败 | CSP 配置 feature flag，可临时放宽 |
| Redis 限速异常导致误封 | 用户无法登录/API 429 | 降级到 SQLite/内存，但登录接口 fail-closed 需谨慎 |
| Cookie Secure 默认导致本地 HTTP 登录失败 | 开发环境受影响 | 本地 `.env` 显式 `AUTH_COOKIE_SECURE=false` |
| 回测并发队列影响用户等待 | 回测变慢但服务稳定 | UI 展示队列位置，管理员可调整并发数 |
| Provider 熔断误判 | 数据降级 | 半开探测 + 手动清除熔断状态接口 |
| 容量模型修正导致容量指标下降 | 用户感知策略“变差” | 文案说明旧模型过度乐观，新模型更保守 |
